# Storage and protocol contracts

This document is for engineers implementing compatible vault, sync, and client adapters. The formats the code reads and writes today are frozen: [Frozen formats](#frozen-formats-phase-6-stop-1) lists them, the files that pin them, and the rule for changing one. Sections that describe a target rather than the implementation say so. [Implementation status](implementation-status.md) separates code from planned contracts.

## Ownership and interfaces

| Component | Owns | Must not own |
| --- | --- | --- |
| Vault core | Lock state; encryption; records; revision validation; backup/recovery; TOTP; generators; import parsing | Webviews, browser permissions, network listeners |
| Sync service | Peer transport; pairing; ciphertext queues; anti-entropy; durable consensus adapters | Record plaintext or password-derived keys |
| Desktop adapter | Core session lifecycle; narrow commands; explicit confirmation; the owner's choice of a login for a browser fill; clipboard and operating-system events | Independent cryptographic or origin-policy implementations |
| Browser extension | Browser-derived tab/frame identity; the owner's explicit request; fill | Persistent vault keys, automatic fill, any list of vault items |
| Native host | Bounded framing; extension allowlist; the connection to the desktop session; origin/request binding | A vault, a key, or a plaintext credential cache |

The core exposes create/open/unlock/lock, record list/read/write/delete, conflict inspection/resolution, encrypted backup/restore, password change, generator, TOTP, and import preview/commit operations. Locked access returns an explicit locked error. A ciphertext ingress API has a separate result type: `stored_pending`, `accepted`, `duplicate`, or `rejected`; successful storage is not equivalent to successful validation.

Adapters translate errors to stable categories: locked, authentication failed, invalid input, unsupported format, conflict, not authorized, missing dependency, quorum unavailable, storage failure, and unavailable. Errors and logs must not embed submitted passwords, decrypted records, invitations, or private key bytes.

## Serialization rules

Every persisted envelope and network message has an explicit format version. Unknown versions fail closed. Cryptographic encodings must be deterministic and domain-separated; ordinary JSON object iteration order is not a canonical signature format. Do not sign a map in one language and reconstruct it with a different key order in another.

The Rust implementation's serde struct serialization, field order, integer representation, optional-field behavior, and byte encoding are frozen in fixtures (see Frozen formats). What is signed or used as AAD is always a hand-written byte encoding, never serde output. The messages around it are postcard between devices and JSON in the control plane, the backup, and the browser fill; trailing bytes after a postcard message are refused, a JSON field given twice is refused, and a field a build does not know is ignored in the backup's payload, an item, and the control state, and refused in a browser fill message. A next wire format should choose one canonical encoding and refuse unknown fields everywhere. API-facing JSON is distinct from the authenticated byte representation.

Domain separation distinguishes local wrappers, record AAD, revision signatures, revision IDs, invitations, membership commands, HPKE context, and backup authentication. All identities in authenticated headers are covered by the signature or AEAD, never merely copied from an unauthenticated SQL column.

## Initial local prototype

The initial core model uses an `Item` with `id`, `title`, `kind`, `username`, `password`, `url`, `notes`, `totp_secret`, `custom_fields`, `tags`, and `favorite`. `kind` serializes as `login`, `secure_note`, `identity`, or `card`; custom fields use an ordered string map. `VaultItem` pairs the decrypted item with its revision ID. List summaries expose title, username, URL, and favorite status only through the unlocked core API.

`RevisionInfo` contains `item_id`, `revision`, and the sorted `parents` it supersedes. Revisions form a per-item DAG: a revision names zero parents (new item), one (edit or delete), or up to 16 (conflict resolution). Parents must be stored before a child is accepted and must belong to the same item; a missing parent returns `MissingParent` with nothing written so the caller can retry, and a cross-item parent returns `InvalidParent`.

An item's heads are its revisions that no stored revision names as a parent. A new revision removes only the parents it names from the head set, so revisions exchanged in either order converge on the same heads, and a concurrent edit or delete becomes an additional head. More than one head is a conflict: `get` returns the live head with the greatest revision ID (deterministic across devices; a deletion never hides a live edit) with `conflict` set, `versions` returns every head, and `update`/`delete` fail with `Unresolved`. `resolve` writes one revision whose parents are exactly the heads the owner reviewed; a head that arrived after review stays visible. Local writes check their head-set precondition inside the same IMMEDIATE transaction that updates the heads.

A received revision whose author is not in the authorized-device table is quarantined, not merged: `apply_encrypted_revision` returns `Quarantined` and stores the exact signed revision in a separate table that never affects heads. Only a well-formed revision that decrypts with the vault key is held, since the author ID is bound into the AEAD and relabeling it fails decryption; at most 10,000 entries are held (`QuarantineFull`). The owner reviews held revisions with `quarantined`, then either discards one (`discard_quarantined`) or accepts it (`accept_quarantined`). What those do depends on whether the author is a device the vault knows (see removed devices below). For an author it does not know, discarding drops the held entry on this device only, and if the revision is received again it is held again; accepting never trusts the unauthorized signature: the content is re-authored and signed by this device against the same parents, so it may become a concurrent head for the owner to resolve, and the held entry is released in the same transaction. If the author is later authorized and the same signed revision arrives, it applies as-is and its held copy is released. Backups carry held revisions.

The signed revision envelope is version 2; the SQLite layout is version 7. Format 2 vaults (one head per item) are migrated by SQL on first unlock without touching signed bytes, format 3 vaults gain the quarantine table, format 4 vaults gain the ingress queue when opened, without the key, so a locked vault can receive immediately, format 5 vaults are re-rooted at their next password unlock (below), and format 6 vaults gain the membership fields (below) when opened, without the key.

**Keys (format 6).** Each device has its own random 32-byte root key, which never leaves it. The password wrapper (Argon2id-derived key, AAD `osm-key-wrap-v1` plus NUL, vault ID, `password`) and the optional recovery wrapper (the recovery key, `recovery`) wrap the root key. The root key wraps the device signing seed, keys the authorized-device MACs, and wraps each epoch key in the `epoch_keys` table under AAD `osm-epoch-key-v1` plus NUL, vault ID, and the 64-bit epoch. Records are encrypted with the key of the epoch named in their header; new revisions use the vault's current epoch (`current_epoch` in `vault_meta`), older epochs stay readable, and a revision under an epoch this device has no key for is held in the ingress queue (`MissingEpochKey`) until the key is installed. `install_epoch_key` stores a key received from another member (a different key for a known epoch is refused) and `activate_epoch` moves new writes to a later epoch; under a control plane both happen only through reconciliation with committed state (below). `generate_epoch_key` stores a next-epoch key locally and is only for vaults without a control plane. Because the root key never leaves the device and enrollment sends only epoch keys, a removed device cannot unwrap epoch keys created after its removal even from another device's vault file or a newer backup. `epoch_key_check` is HMAC-SHA256 keyed by an epoch key over `osm-epoch-key-check-v1` plus NUL, the vault ID, and the 64-bit epoch; committed membership records it for every epoch so members can confirm they hold the same key.

**Membership fields (format 7).** Each device keeps a random 32-byte HPKE recipient secret, wrapped by its root key under AAD `osm-recipient-key-v1` plus NUL, vault ID, and device ID (`recipient_nonce`, `recipient_wrapped_secret` in `vault_meta`); its X25519 key pair is derived from it with the KEM's `DeriveKeyPair`, and epoch keys for this device are sealed to that public key. A joining device brings the secret it generated for pairing (`PendingDevice::recipient_secret`); a format 6 vault generates one at its next unlock. `write_fence` (default 1) is the earliest epoch new revisions may use: raised, never lowered, when committed membership activates a later epoch, and writable while locked; while `current_epoch` is below it every write fails with `EpochPending`. `revoked_devices` lists authorized authors removed by committed membership, each row carrying HMAC-SHA256 over `osm-device-revocation-v1` plus NUL, vault ID, and device ID, keyed by a subkey of the root key; unlock fails closed if one does not verify, and rows are never changed or deleted. Control requests are signed by the device key with `sign_control`, which prepends `osm-control-signature-v1` plus NUL.

Recovery is optional per device. `recovery_check` is HMAC-SHA256 keyed by the recovery key over `osm-recovery-check-v1` plus NUL and the vault ID; it is public, is sent during pairing, and lets a device verify a typed recovery key before `enable_recovery` wraps its root with it. A created or restored vault has recovery on; a joined vault starts with it off. Format 5 vaults used one shared key for everything. Re-rooting needs the password: in one transaction the shared key becomes epoch 1, a new root key rewraps the device seed, MACs, and epoch key, the password wrapper is rewritten, and every revision row is copied unchanged into tables that accept any epoch. The old recovery wrapper is kept only to verify the recovery key when it is entered to re-enable recovery; recovery unlock of a format 5 vault returns `UpgradeRequiresPassword`.

A recovery key exists only on the screen that shows it when a vault is made, so a vault can keep it until the owner confirms having stored it. `keep_recovery_key_until_confirmed` checks the key against `recovery_check` and writes it, encrypted with the root key under AAD `osm-key-wrap-v1` plus NUL, the vault ID, and `unconfirmed-recovery`, as the one row of an `unconfirmed_recovery` table (`singleton`, 24-byte `nonce`, `wrapped_key`). The table is made when a key is first kept and is absent from every other vault; it needs no format change, and a build that does not know it ignores it. `unconfirmed_recovery_key` reads it while unlocked, and `confirm_recovery_key_stored` deletes the row. Backups do not carry it. The desktop app keeps the key of a vault it creates and of a vault made by a recovery, shows it after each unlock, and stops keeping it when the owner confirms.

The ingress queue stores received revisions with their exact signed bytes before any verification. `stage_revision` works while locked and checks only the envelope's shape (version, vault ID, lengths, parent syntax); a revision already accepted, staged, or quarantined is a duplicate. It holds at most 100,000 revisions or 512 MiB of ciphertext (`IngressFull`). `process_staged` requires the key: it verifies and applies staged revisions in arrival order, repeating while any progress is made, and each revision leaves the queue in the same SQLite transaction that accepts or quarantines it. A revision that fails verification is discarded and reported; one whose parent is still missing stays staged; a storage failure stops processing without discarding anything. Revision IDs and ciphertext can be read while locked (`revision_ids`, `revisions_by_id`, `staged_revision_ids`, `staged_missing_parents`), since they are public metadata or already encrypted; decrypting anything still requires unlock. A backup without held revisions restores with none. Each vault holds one device signing identity: a random 16-byte device ID and an Ed25519 key pair. The 32-byte seed is encrypted with the master key under AAD `osm-device-signing-key-v1` plus NUL, the vault ID, device ID, and public key; it is only in memory while unlocked. A restored vault always generates a new device identity and never reuses the source device's key.

Record AAD is the ASCII domain `osm-item-revision-v2` plus a NUL byte, the 32-byte vault ID, length-prefixed UTF-8 item ID, one length-prefixed field holding the sorted parent revision IDs concatenated (each exactly 64 characters, so the field is unambiguous and zero or one parent encodes exactly as the earlier single-parent layout), an unsigned 64-bit key epoch (1 to 2^32), the 16-byte author device ID, and one tombstone byte. Length prefixes are unsigned 64-bit big-endian byte counts. The author signs `osm-revision-signature-v2` plus NUL, followed by length-prefixed AAD, nonce, and ciphertext. The revision ID is lowercase hex SHA-256 over `osm-revision-id-v2` plus NUL, followed by length-prefixed AAD, nonce, ciphertext, and signature, so it identifies the signed envelope.

A revision is accepted, and read, only after `verify_strict` succeeds against a public key in the local authorized-device table; a key carried by a revision is never trusted. Each authorized-device row carries HMAC-SHA256 over `osm-device-authorization-v1` plus NUL, vault ID, device ID, and public key, keyed by a subkey of the device's root key (HMAC-SHA256 of `osm-device-authorization-key-v1`, without a NUL, under the root key; the revocation mark's subkey is made the same way from `osm-device-revocation-key-v1`); unlock fails closed if any row does not verify. A created vault's table holds only this device, plus the source authors when restored from a backup; under a control plane, reconciliation adds every committed author. A revoked author's revisions that this device has already accepted stay readable. A revision of its that arrives later is held in the quarantine (`Quarantined`), unless an authorized, non-revoked author's revision names it as a parent, directly or through other held revisions by known authors: then the held revisions are verified and accepted as-is, parents first, in the same transaction as that child. `endorse_heads_of` writes, as this device, a revision with the same content on top of each head a given author wrote, so its last accepted state survives revocation on devices that never accepted it; `retry_quarantined` applies held revisions whose authors have since been authorized.

The owner's decision on a held revision by a known author, whose signature and content verify (`QuarantinedRevision::known_author`), uses that same rule, so that it holds on every device and not only on the one where it was made. A member that had not yet learned of the removal may have accepted the revision and keeps offering it; a decision that only dropped or re-authored the held copy would be undone at the next sync. `accept_quarantined` writes, as this device, a revision with the same content whose only parent is the held revision. `discard_quarantined` writes, as this device, a revision that keeps the item as it is on this device (a deletion if the item is not there) and whose parents are the held revision and the item's current head, unless the held revision already names that head; it returns `Unresolved`, changing nothing, while the item has more than one head, because there is then no single version to keep. Either revision vouches for the held one, which joins the history as it was signed, already superseded, on this device and on every device the new revision reaches. Neither overrides an edit made since: an accepted revision that is concurrent with the current head becomes a second head. A revision by a removed author that is already in the history is a replay when received again, not a new hold.

Format 1 vaults (unsigned revisions, no author) are migrated in one transaction on first unlock: every revision is authenticated with the version 1 AAD (`osm-item-revision-v1` plus NUL, vault ID, length-prefixed item ID, the one parent or nothing as a length-prefixed field, the 64-bit epoch, and the tombstone byte) and ID (SHA-256 over `osm-revision-id-v1` plus NUL and the length-prefixed AAD, nonce, and ciphertext), then re-sealed and signed by the new local device identity, with parent links remapped. Format 1 backups are rejected with `UnsupportedVersion(1)`; unlock the source vault with a current build and export again.

The local wrapper AAD is `osm-key-wrap-v1` plus NUL, the 32-byte vault ID, and the wrapping-method bytes. The initial non-test Argon2id configuration is 65,536 KiB, three iterations, and one lane. Unit-test builds use a cheaper profile; they are not evidence for production unlock performance. The recovery string is `OSM-RK1-` followed by unpadded base64url encoding of 32 random bytes.

The backup (version 4) requires recovery to be enabled on the exporting device. It is encrypted with that device's root key, carries the recovery wrapper of that root key, and its payload holds every epoch key, the current epoch, the authorized authors, the revoked ones (absent in older backups, meaning none), revisions, and held revisions. The file is one JSON object: `magic` (`OSM-BACKUP`), `format_version`, and five values as unpadded base64url text: `vault_id`, `recovery_nonce` and `recovery_wrapped_key` (the recovery wrapper), `nonce`, and `ciphertext`. The ciphertext is the payload as JSON (`current_epoch`, `epoch_keys` as `{epoch, key}`, `devices` as `{device_id, public_key}`, `revisions`, `quarantine`, `revoked`, with byte strings as arrays of numbers), sealed under the root key with AAD `osm-portable-backup-v1` plus NUL, the vault ID, and the two recovery texts as they stand in the file, each behind its length as 8 big-endian bytes. Restoring applies the accepted revisions, then the revocations, then the held revisions: a removed device's revisions that were accepted are restored as accepted, and one that was held stays held. (Until Phase 6 the held revisions were applied before the revocations, so a removed device's held revision was taken in by a restore; the frozen backup caught this.) Restoration preserves the source vault identity while creating a new root key, password, recovery wrapper, and device identity. Earlier backup versions are rejected. This supports an offline local copy; it is not live device enrollment, and a vault restored this way shares its identity with the original, so it must not found or join a control plane as if it were a new vault. Recovery from lost devices is a fork into a new trust domain instead (see Backups and recovery). Sections below describing membership-authorized signers, epochs, author counters, or HPKE integration are target contracts beyond this local format.

## Local storage

SQLite is a transactional container for encrypted values, not an assertion of whole-file database encryption. Titles, usernames, passwords, notes, origins, and TOTP secrets belong inside record ciphertext. Public indexes may contain random identifiers, encrypted revision bytes, ancestry, epochs, and local sync progress. WAL, journal, temporary tables, error logs, and SQLite tracing must not contain plaintext secrets.

A vault header contains its format version, random vault identity, Argon2id salt/parameters, and an authenticated local key wrapper. The wrapper binds the vault identity, format, and KDF parameters. Use 16 or more random bytes for the salt, a 32-byte derived wrapping key, and a fresh 24-byte XChaCha20-Poly1305 nonce. Validate KDF resource bounds before deriving a key. Password changes create and authenticate a new wrapper in one transaction.

The unlocked key bundle contains the current epoch key and any retained historical keys needed to read existing revisions. Signing keys, recipient keys, and transport keys have separate roles. New devices receive their own independent local password wrapper. Copying another device's wrapper is backup replication, not a finished enrollment workflow.

Recommended logical tables are vault metadata, encrypted revisions, parent edges, materialized heads, pending ingress, committed public membership, recipient key envelopes, rotation progress, and sync cursors. Persistent Raft storage additionally needs votes, logs, applied state, and snapshots. These are logical requirements; exact SQL names remain implementation details.

## Immutable record revisions

The target authenticated revision header contains:

| Field | Rule |
| --- | --- |
| `format_version` | Explicit supported integer version |
| `vault_id` | Random stable vault identity; cross-vault copies rejected |
| `record_id` | Random stable record identity |
| `parents` | Sorted, unique revision IDs from the same record |
| `author_device_id` | Identifier resolved through authenticated membership |
| `membership_epoch` | Authorizing committed configuration |
| `key_epoch` | Encryption key selection, authenticated rather than guessed |
| `author_counter` | Durable per-author sequence; useful for replay/rollback diagnostics |
| `nonce` | 24 fresh random bytes for XChaCha20-Poly1305 |

Encrypt the serialized record or tombstone with the header as AAD. Sign a domain-separated encoding of the header and ciphertext with Ed25519. Define the revision ID as a domain-separated SHA-256 digest of the immutable signed envelope. If the prototype uses a random revision ID instead, signature coverage of that ID remains mandatory; a migration is required before substituting content addressing.

Signature validation uses a public key already authorized by membership. An attacker-supplied public key inside the revision is not sufficient. Parent existence and same-record ancestry are checked before acceptance. A missing parent delays materialization; it does not erase existing heads. Wall-clock timestamps are display metadata, not a total-order or revocation authority.

The materialized head set is derived, repairable state. A new revision supersedes only its named ancestors. An explicit conflict resolution names every head the owner resolved. A new concurrent head arriving later remains visible. Deletion is an encrypted tombstone with the same validation rules as an edit.

## HPKE key envelopes

Use an RFC 9180 implementation rather than a custom X25519 construction. The sync primitive currently uses DHKEM(X25519, HKDF-SHA256), HKDF-SHA256, and AES-256-GCM; record XChaCha20-Poly1305 and HPKE AES-256-GCM are different uses and have different nonce handling. The suite and the envelope's layout are frozen in a fixture. HPKE's suite identifiers and context handling follow [RFC 9180](https://www.rfc-editor.org/rfc/rfc9180.html).

The implemented envelope is 188 bytes: the magic `OSK1`, the 32-byte vault ID, the epoch as 8 big-endian bytes, the recipient device's 32-byte signing key, the recipient's 32-byte HPKE public key, the 32-byte encapsulated key, and 48 bytes of ciphertext (the 32-byte epoch key and its tag). It is HPKE base mode with `info` `osm-epoch-key-hpke-v1` and, as AAD, the vault ID, epoch, recipient device, and recipient key in that order (104 bytes). A recipient's key pair is the KEM's `DeriveKeyPair` of its 32-byte recipient secret. An envelope binds the protocol version, vault, key epoch, recipient device/key identity, and authorizing membership transition. Its encrypted payload contains the epoch key and matching identifiers. Preserve the HPKE encapsulated key and ciphertext. Use a fixed domain label plus these identifiers as `info`/AAD. An authorized sender signs the envelope or includes it in authenticated committed control state. HPKE base mode alone does not authenticate that sender.

Unwrapping checks the recipient, vault, supported suite, epoch, and committed authorization before activation. Duplicate delivery is idempotent. Transport receipt while locked may store the envelope, but activation requires a later unlocked authorized step.

## Membership and rotation control plane

Record anti-entropy and membership consensus are separate protocols. The record plane exchanges immutable revisions and missing-parent requests. The control plane carries OpenRaft append/vote/snapshot messages plus application commands for enrollment and rotation. Pin authenticated device identity to the Raft node ID; an untrusted RPC field cannot choose another identity.

Application commands have a stable request ID for deduplication and a signed authorization context. Enrollment introduces a learner, verifies catch-up, transitions membership through OpenRaft, and only then makes the corresponding key grant active. Removal stages retained-recipient envelopes and has durable prepared, membership-committed, and epoch-active states. A retry after restart resumes the same request and cannot issue a conflicting epoch.

Do not expose a “force majority” input. Return quorum unavailable when the configured quorum cannot commit. A recovery fork has a new vault/control-plane identity and requires explicit re-enrollment.

### Implemented control plane (Phase 4, milestones 2 to 4)

`osm-vault-membership` runs OpenRaft 0.9 with storage v2. A Raft node ID is the device's 16-byte ID read as a big-endian `u128`, so Raft identities are device identities; each node's record in the membership carries the device's Ed25519 public key, TLS certificate pin, and HPKE recipient key. Every RPC names its sender in `vote` (the leader or candidate); the receiving node checks that against the identity its transport authenticated (`verify_rpc_sender`, inside `ControlNode::handle`) and answers `Refused` on a mismatch without passing the RPC to Raft, so a peer cannot speak for another device.

Each node keeps one SQLite database with `synchronous = FULL`: the vote, the log (one JSON entry per index), the committed and purged log IDs, the control state, and the latest snapshot. Its layout version, 1, is in SQLite's `user_version` (see Frozen formats). The JSON is serde's of the Rust types, OpenRaft's among them; a device ID is a JSON integer of up to 39 digits, and a decimal string where it is a map's key, which a reader that keeps numbers as 64-bit floats cannot hold. A database belongs to one vault: the state records the vault ID, and opening it, or installing a snapshot, for another vault fails. Appends commit before OpenRaft's flush callback runs; truncation and purge never leave a hole (the purge point is recorded before entries are deleted). The state machine persists its state in the transaction that records each applied batch.

Application entries are either signed control requests or completions. A signed request has a stable 16-byte request ID, the requester's device ID, the request, and an Ed25519 signature over `osm-control-signature-v1` plus NUL followed by `osm-control-request-v2` plus NUL, the vault ID, the request ID, the requester, and a tagged encoding of the request in which every variable-length list and envelope is length-prefixed. The state machine verifies the requester is an enrolled voter in the committed membership at that log position and checks the signature with that membership's key, so every node reaches the same verdict. Enrolled means a voter that is also an author under the key membership records for it: genesis makes the founding voters authors, and after that only a completed, signed enrollment does. Authority and epoch keys follow enrollment, never voting rights alone, because a Raft membership entry carries no signature: a voter that appeared in the membership without a signed enrollment can make no request and is given no key. Accepted request IDs are remembered (the last 4,096) and a repeat returns `AlreadyApplied`; a rejected request had no effect, is not remembered, and is evaluated again if resubmitted. The requests are:

- `Genesis` (once, before anything else is accepted): the current epoch, the key check of every epoch from 1, and the vault's authors. The requester holds every key so far; every voter is an author.
- `ProposeChange(Enroll)`: a device with its signing key, TLS pin, and recipient key, which must not be a voter or a removed device, and whose TLS pin no other device in the membership has (a certificate identifies one device).
- `ProposeChange(Remove)`: a voter other than the requester, with a rotation: the next epoch, its key check, and exactly one epoch-key envelope per remaining enrolled voter, each sealed to that voter's recorded signing and recipient keys for this vault and epoch.
- `CancelEnrollment`: abandons the pending enrollment it names; the change then targets the voters without that device.
- `GrantKeys`: envelopes for epochs an enrolled voter has not been given, only once its enrollment is complete and no change concerns it.

A proposal is accepted only when no change is pending and records the target voter set. A completion names the pending request and is accepted only once the committed membership is uniform and equals that target. It is unsigned and carries no authority of its own, since any node can check that condition; this lets a leader whose vault is locked finish a change. Completing an enrollment makes the device an author; completing a removal makes the rotation's epoch current, records its check and envelopes, drops the removed device's envelopes, and records the removed device with the device that removed it and with the TLS pin it had when the removal was proposed (`removed_pins`), so that it can be recognized and told. Removed devices never rejoin under the same ID. A removed device is not enrolled again by anything: if a membership entry, which carries no signature, makes it a voter again, it can make no request and is given no key, and the members can remove it again, with the record of its first removal kept. (Until Phase 6a stop 2 such a device counted as enrolled, so every member would have sealed the newest epoch keys to it; a property test of the state machine found this.)

The leader drives a pending change: for an enrollment it adds the device as a learner and waits until replication shows the learner has the leader's last log entry (checked explicitly each attempt, since a configuration including an unreachable learner could otherwise reach a majority without it), then calls `change_membership`, which commits the joint and then the uniform configuration, then appends the completion. For a cancelled enrollment or a removal it skips catch-up; a device dropped from the target is removed from membership outright, and learners no pending enrollment needs are removed once the configuration is committed and uniform. Every step is idempotent and the intent is in the log, so after a crash at any step the next leader resumes the same request; at most one change is pending, which serializes enrollment and removal. A follower passes a submitted request to the leader as a `Submit` RPC and retries while no leader is known or reachable; the leader accepts a passed-on request only from the device that signed it. A write that no quorum commits in time returns `QuorumUnavailable`; its outcome is unknown until a quorum returns, and resubmitting the same request is safe.

The node reaches other devices through a `Dialer`, which a transport implements along with `Link` (one RPC and its reply at a time, bounded by a deadline). The RPCs are `AppendEntries`, `Vote`, `InstallSnapshot`, and `Submit`. Two transports exist: the in-process `Router` used by tests, which models partitions, and the TLS transport below. A snapshot is the whole control state as JSON and is sent in OpenRaft's chunks; installing one for another vault fails.

### Members without a vote (Phase 6b, stop 1)

A member is a voter or a device enrolled without a vote. `ProposeChange(Enroll)` carries `votes`: absent or true, the device becomes a voter as described above; false, it stays a Raft learner. Such a member is sent the log, given every epoch key, synced with, and may sign requests like a voter; it counts toward no majority, so a phone that is off or out of reach never holds up a change. An enrollment without a vote is signed under tag 6 instead of 2, with the same fields after it, so neither kind passes for the other. It is stored with `"votes":false`; a voting enrollment is stored without the field, exactly as before, so every earlier log entry and every frozen vector reads and is written back unchanged. The control state lists the members without a vote under `without_vote`, which is absent while there are none, so a state from before writes back as it was.

The rules change in four places. A device is enrolled if it is a voter, or a member without a vote that is in the membership as a learner, and in both cases an author under the key the membership records for it and not removed; Raft membership entries, which carry no signature, still give no authority or key by themselves. After genesis a request is accepted from any enrolled member, voting or not (before it, as before, only from a voter). A removal's rotation must have exactly one envelope per remaining enrolled member, voting or not. A change is in effect, so that its completion is accepted, when the committed membership is uniform with the target voters and, for a member without a vote, when that device is in the membership on joining and gone from it on removal. The leader adds a member without a vote as a learner, waits until it has caught up, and completes the enrollment without `change_membership`; it removes one with `ChangeMembers::RemoveNodes`, and never removes the learners that are members without a vote when it clears stale ones. `crates/vault-membership/fixtures/without-vote.json` freezes the new enrollment's signed bytes and stored text and a state holding such a member.

### Rotation and enrollment coupling (Phase 4, milestone 3)

`osm_vault_peer::control` couples a vault to committed state. Request IDs are SHA-256 of `osm-control-request-id-v1` plus NUL, the vault ID, the length-prefixed kind, and its subject (the joiner's device ID; the removed device and new epoch; the granted device and epochs), truncated to 16 bytes, so a retry after an unknown outcome is recognized instead of producing a second rotation or grant. `found` initializes a one-voter cluster and commits genesis from the vault's epoch keys and authors. `removal_request` generates the next epoch key, seals it to every other voter, records its check, and discards it: every remaining device, including the requester, installs it from its own envelope only after the removal completes, so no device holds a key for an epoch that was never committed. `grant_requests` seals the epochs a settled voter lacks; any unlocked member may submit them.

`reconcile(vault, state)` is idempotent and is run whenever applied state changes and right after unlock, before staged revisions are processed or anything is written. If committed membership removed this device it reports that and changes nothing. Otherwise it raises the write fence to the committed epoch, which works while locked and is all it does then. Unlocked, it authorizes every committed author (a known device with a different key is a protocol violation), revokes every removed device, checks every epoch key it holds against the committed check (`EpochKeyMismatch` on a difference), opens each envelope sealed to it, checks and installs the key, activates the committed epoch once it holds it, applies held revisions whose authors are now authorized, and, on the device that removed another, endorses that device's remaining heads. A member that has applied a removal's completion is fenced until it holds the new key; one that has not yet learned of it can still write under the old epoch.

Enrollment through pairing: after the owner confirms the short code, `approve_enrollment` consumes the invitation token and returns the signed `Enroll` proposal and an `EnrollmentGrant` (version 1, vault ID, the proposal's request ID, the recovery check, the vault's members from the inviter's committed state, each with device ID, TLS pin, and optional address, the port the inviter accepts member connections on, and the inviter's pairing signature over `enrollment-grant` plus NUL, the transcript, and those fields, with the member list and each address length-prefixed). The inviter submits the proposal and sends the grant only if it is accepted; otherwise it tells the joiner the enrollment was refused. The joiner runs its control-plane node from the start, under the device ID from `Joiner::control_device`. It has no log to tell it whose connections to accept, and the leader need not be the inviter, so `Joiner::members` verifies the grant, requires the inviter's entry to carry the pin from the invitation, and returns the members for the joiner to accept and to announce itself to (below). The leader brings it up to date as a learner and makes it a voter, and a member then grants it every epoch key. `Joiner::finish_enrollment` verifies the grant against the invitation's key, requires that committed state records this device as a settled voter and author with the keys and pin it sent, opens every envelope sealed to it with the recipient key derived from its pending secret, checks each against the committed check, and creates its vault with the committed epoch, authors, and removed devices; it fails with `EnrollmentPending` until then. A joiner that never catches up can be dropped with `CancelEnrollment`; it never received a key.

A device that already holds a copy of the vault, paired before vaults had a control plane, joins under the identity it has (`Joiner::start_with_vault`). The invitation must be for its vault. Its join request carries its existing device ID, signing key, and recipient key, signed by the vault; genesis listed it as an author, and an enrollment of an author is accepted only under the same key. It then becomes a voter like any joiner, and `Joiner::finish_in_place` verifies the grant, requires that committed state records it as an enrolled voter with those keys and its pin, and reconciles its vault: the keys it holds are checked against the committed checks and nothing is created or replaced. One of the two devices founds the control plane and the other joins it; both keep their vaults.

### Member transport (Phase 4, milestone 4, stages 1 and 2)

`osm_vault_peer::MemberEndpoint` is one device's end of the connections between a vault's devices, over the same TLS 1.3 settings as pairing: mandatory client certificates, pins in both directions, no resumption. One listener serves two channels, the control plane's RPCs and revision sync, chosen by the first frame.

**Whose certificate is accepted.** The server decides at every handshake, from the node's `Directory`: the devices its own log names (the nodes of the committed membership, of the latest membership in the log, and of a pending, uncancelled enrollment), plus devices a member introduced, minus every removed device. The pin is mapped back to a device ID, and a pin that two accepted devices share maps to neither. A client dials only the pin that membership records for its target. A removed device's certificate also completes the handshake, but only so that its `Open` can be answered with `Removed`; nothing it sends is taken in.

**Introductions.** A device's own log does not always name the current members: a device still being enrolled has no log, and one that was away while another joined does not know the newcomer, which may now lead. Such a device accepts pins on a member's word until its log names them: from the signed enrollment grant, and from the roster on a connection to or from a device that its own committed state lists as a member. A roster holds only what its sender's committed state lists as enrolled voters, never what the sender was itself told. What the log records wins: an introduction neither replaces a recorded device's pin nor claims a recorded pin for another device, and it never admits a removed device. At most 256 are kept, in memory.

**Member.** For rosters and for sync, a member is a device that the receiver's committed state lists as an enrolled voter, not removed, and not the subject of a pending removal. This holds while another device's change is under way.

**Opening exchange.** After the handshake the client sends `Open` (postcard, in a frame as for sync): protocol version 2, vault ID, channel (`Control` or `Sync`), the port it accepts member connections on, if any, and its roster of at most 64 members (device ID, TLS pin, optional address of at most 128 bytes). The server answers `Welcome` with its own roster, or closes after `UnsupportedVersion`, `VaultMismatch`, `NotAMember` (the sync channel, from a device that is not a member), or `Removed`. The opening exchange has a 10-second timeout. `MemberEndpoint::announce` opens a control connection only for this exchange.

**Addresses.** Each device keeps one address per device in the `member_addresses` table of its peer store file (`AddressBook::open`): the source address of an authenticated incoming connection with the port from its `Open`, an address it connected to successfully, or one from a believed roster. A roster address fills in only when none is known or the known one last failed. Addresses are advisory; the pin authenticates whatever answers.

**Control channel.** Each frame is then one RPC and its reply, in turn: the 4-byte length and a JSON body, the encoding the log is stored in, at most 24 MiB. The receiver looks the pin up again before every RPC, so a device removed while its connection is open loses it, and passes the RPC to the node under that device ID. A reply is `Refused` when the RPC claims a sender other than the connection's device, or passes on a request another device signed. A connection without an RPC for 120 seconds is closed. The client makes its connection when first needed, in a task of its own so that a deadline on one RPC does not abandon a handshake, and drops it after any failed or abandoned exchange.

**Sync channel.** Both ends require the other to be a member by their own committed state: the client before dialing, with the pin from that state, and the server before answering `Welcome`. The connection then carries a sync session as described under the implemented protocol below, `Hello` included. Before the session starts, each end reconciles its vault with its committed control state (`MemberSync::run_shared`), so received revisions are judged against the current authors and removals; a device whose state says it was removed exchanges nothing. A session takes the vault for one message at a time (`SharedVault`), never while it waits for the peer, so two devices that dial each other at the same moment both finish, and the application keeps using the vault in between.

**Removal notice.** The entry that completes a removal is appended after the membership no longer includes the removed device, so that device may never receive it. It learns of its removal when it next connects to a member: the `Removed` answer, which `MemberEndpoint::told_removed` then reports. A device believes this from any member it dialed by pin.

**Serving.** An accept loop (`serve_members`) completes handshakes concurrently, serves control connections itself, and hands sync connections to the application, which runs them against the vault. It serves at most 64 connections at once, handshakes included, and closes them when it stops.

**Development CLI.** `osm-peer device` runs one device: its node, listener, a loop that reconciles the vault, then processes staged revisions, and submits key grants whenever applied state changes, and commands on stdin to found, invite, add, list, sync, remove, and report status. `osm-peer device-locked` runs the same device without its password, as an app that is open but locked. `osm-peer join-device` pairs through the enrollment path and then runs as `device` does.

**Desktop app.** The app keeps `control.sqlite3` (the node's database) beside the vault and the peer store. It runs the node and listener whenever it is open and the vault has a control plane, locked or not. Creating a vault founds the control plane; a vault from before, never paired, is founded at its next unlock; a vault paired by an older build waits for the owner to choose which device founds it. On every change of applied state, and at unlock before anything staged is processed, it reconciles the vault, then processes staged revisions and submits key grants if unlocked. A joining device runs its node from the moment it shows the short code, keeps its pending identity in memory until it is enrolled, and discards its control database if the join is abandoned. A device that learns it was removed, from its own committed state or from a member's `Removed` answer, writes an empty `removed` file beside the vault, since its own log may never record the removal, and is then reset at once: the app stops its node and moves the vault file first, then the control database, peer store, invitation store, and the marker, into an `archive-<time>` folder. That leaves a device without a vault, which joins again as a new device with a new transport certificate. A `reset-after-removal` file names the archive folder until the device has a vault again, so the app can say what happened. The owner can have a device's copy put away in the same way without a removal (`leave_vault`, which takes the device's password), for a device whose vault was replaced by a recovery on another device; a `left-vault` file then names the archive folder. Before any file is moved, a `putting-away` file records the reason (`removed` or `left`) and the archive folder on two lines, and it is deleted once the note is written; at launch, before the vault or its stores are opened, a `putting-away` file that names a folder beside the vault has its move finished, and any other is deleted. If the app stops between the marker and the reset, the next launch finishes the reset; while the marker exists the app runs no node, founds nothing, and refuses to sync.

An `archive-<time>` folder holds a complete copy as it was: the vault file, its control-plane database, its peer and invitation stores. The desktop app lists these folders (the name is `archive-` and the time in seconds, with `-<n>` after it when two were made in one second; nothing else is listed, opened, or deleted, and a link in that place is not followed). The owner opens one with the password the copy had; the app then reads its items, and says for each whether the vault on this device holds it, holds it with other content, or does not hold it. Copying an item writes a new item with a new ID into the current vault, with ` (archived copy)` after the title when the vault already has an item of that ID; nothing is written to the archived copy's revisions, though opening its file can create SQLite's sidecar files and would apply a format upgrade as opening any vault does. Deleting removes the folder and everything in it, and a note that names it.

## Pairing and sync messages

An invitation needs a version, invitation ID, random single-use secret, expiry, inviter identity/pin, vault identity, and candidate connection addresses. Address discovery is advisory. Invitation redemption persists the one-use decision before reporting success and binds both endpoint keys to the confirmed transcript.

Frame messages with an explicit bounded length and request ID. Negotiate only supported protocol versions without silently falling back to weaker authentication. Inventory, revision batches, missing-parent requests, and acknowledgments expose ciphertext metadata only. Acknowledgments distinguish durable receipt from validated acceptance. Limit message size, revisions per batch, total pending bytes, concurrent peers, and processing time.

The receiver deduplicates before enqueueing where safe, authenticates metadata before accepting it, and stores unknown ancestry or unavailable epochs as pending. Synchronization resumes from persisted state after a crash. Arrival order and duplicate batches must yield the same accepted heads.

### Implemented protocol (Phase 3, with Phase 4 enrollment)

`osm-vault-peer` implements pairing and sync as sans-IO steps and carries them over TLS 1.3 on TCP. There is no discovery or NAT traversal: the invitation names the inviter's address, and members reach each other at the addresses in their address books (above).

Pairing is owner-confirmed, and the owner's confirmation becomes an enrollment proposal to the vault's control plane (above), so any number of devices can join. Until Phase 4 milestone 4 the confirmation itself was the enrollment authority, for at most one paired peer; that path is removed. A peer store written then may still name that one device (`PeerStore::legacy_peers`), which is read only to offer the move onto the control plane. The invitation text is `OSM-PAIR1-` plus base64url of a postcard body: version 1, vault ID, inviter device ID and Ed25519 public key, the inviter's TLS certificate pin, up to four advisory addresses, a 32-byte one-use token, and an expiry of at most 15 minutes. The token is stored only as a hash, SHA-256 of `osm-invitation-token-v1` (without a NUL) and the token (`InvitationStore::issue_pairing`), binds to the first device that redeems it, and is consumed before the joiner is authorized.

The joiner creates its own device identity (`PendingDevice`), including the recipient secret its HPKE key pair is derived from and which its vault keeps, and sends a request that also names its TLS certificate pin, signed with the new device key over `join-request` plus NUL and the transcript. Both sides hash a transcript: `osm-pairing-transcript-v1` plus NUL, vault ID, inviter device ID, key, and TLS pin, SHA-256 of `osm-pairing-token-v1` plus NUL and the token, joiner device ID, key, HPKE key, and TLS pin, so the short code also confirms both transport identities. The short code both screens show is the first four bytes of SHA-256 of `osm-pairing-sas-v1` plus NUL and the transcript, read as a big-endian number and reduced modulo 1,000,000, shown as six digits in two groups of three. The inviter checks the token without consuming it (`InvitationStore::check`) and the request signature before the owner is asked. After the owner confirms, the inviter proposes the enrollment and answers with the enrollment grant, `Declined` if the owner declined, or `Refused` if the vault's devices did not accept the proposal. The inviter's root key and recovery wrapper are never sent, and epoch keys reach the joiner only as envelopes in committed control state once it is a voter; the joiner wraps them under a new root key of its own and starts with recovery off. Pairing signatures prefix `osm-pairing-signature-v1` plus NUL so they cannot be confused with revision signatures. The joiner verifies the grant against the key from the invitation, requires the owner's confirmation, and calls `Vault::join`, which creates its vault with its own password and identity; no other device's password wrapper ever leaves it.

Transport identity is separate from the revision signing key: each device has a self-signed Ed25519 certificate generated with rcgen and stored in its peer store, which is created with owner-only permissions. The TLS private key is not encrypted, because a locked device must still be able to receive ciphertext; revision authenticity never depends on it. Peers pin the SHA-256 of each other's certificate and ignore names, validity periods, and system roots; the handshake signature still proves possession of the pinned certificate's key. Only TLS 1.3 is offered, client certificates are mandatory, and session resumption is disabled so every connection checks both certificates. During pairing the inviter accepts any client certificate and then requires that the signed join request names exactly the certificate on the connection; the joiner pins the inviter from the invitation. Connections that fail before the owner is asked are dropped and the inviter keeps listening until the invitation window closes. Sync runs only between members, over the member transport (above). Reads and writes run concurrently, each frame has a 60-second timeout, and connects and handshakes have 10-second timeouts.

Frames are a 4-byte big-endian length and a postcard body, at most 24 MiB; the declared length is checked before the body is buffered, the body is kept as it arrives rather than allocated at its declared length, and trailing bytes are rejected. Before a peer is known to be a member, the bound is 64 KiB: the join request, the answer to it, and the opening exchange between members are each a few kilobytes. The pairing listener takes one connection at a time and gives a join request 10 seconds after the handshake. A sync session opens with `Hello` (protocol version 1, vault ID, and the port this device accepts sync connections on, if any; the receiver records the peer's address as the connection's source IP with that port) and an `Inventory` of every accepted and staged revision ID, so nothing already staged is sent again. Each side answers the other's inventory with the revisions it lacks, parents first, in `Revisions` batches of at most 64 revisions or 8 MiB, then `Done`. Revisions are the core's signed `EncryptedRevision`s. Every received revision is staged first (durable receipt); if the vault is unlocked the session then processes the queue (validated acceptance): unknown authors are quarantined, and any other invalid revision is discarded and ends the session. A locked device receives and stages only, and can still send its stored revisions. After `Done` the receiver sends `Need` for parents of staged revisions that it has neither accepted nor staged, for at most 8 rounds. A side takes the peer's `Inventory` once, its `Need` in at most 8 rounds, and its `Done` at most once more than it has itself sent `Need`; anything beyond is a protocol violation that ends the session, so a peer cannot have the vault sent again and again. `Finished` means a side needs nothing more. A session started while unlocked processes anything staged earlier. An interrupted session is resumed by starting another: inventories recompute what is missing, and staged revisions survive restarts.

## Backups and recovery

The public backup contract must freeze a magic value, format version, vault identity, cryptographic suite, KDF or recovery-wrapper descriptor, nonce, authenticated manifest, and encrypted payload. Authenticate the manifest and key wrappers. The payload contains a consistent database snapshot or equivalent complete encrypted records and required key material. Copying only the SQLite main file while a WAL transaction is outstanding is not a valid snapshot procedure.

**Files appear whole.** The core writes a new vault (made, restored, joined, or forked) and a backup under the name with `.partial` added, beside its place, and moves it there only once it is complete; a file already at that place is never replaced, and a `.partial` file a crash left is replaced by the next attempt. Until Phase 6a stop 2 a vault was written in place, so a process killed while making one left a file that could neither be opened nor made again. Recovery uses a high-entropy secret independent of the local unlock password. A restore API authenticates before writing and takes a new destination and new local password. It must not overwrite an existing vault by default. Live rejoin creates a fresh device identity; restoring an old signing identity into two writers risks cloned identity and counter reuse.

### Implemented recovery fork (Phase 4, milestone 4)

When too many of a vault's devices are lost for the rest to remove them, no membership change can commit, by design. `Vault::fork` starts a new trust domain from one surviving device instead. The new vault has a new random vault ID, device identity, root key, epoch 1 key, recipient secret, and recovery key, and its only authorized author is the new identity. Every live version of every item is sealed again under the new vault ID and epoch key and signed by the new identity, with no parents: an item with several live versions stays a conflict. Earlier history, deletions, held revisions, and unverified received revisions are not carried; an unresolved choice between an edit and a deletion keeps the edit. The source vault is not modified. Because the vault ID is inside every revision's authenticated header and every control request's signature, nothing signed or sealed in one domain verifies in the other.

The desktop app does this as one confirmed action that asks for the vault password again, which also becomes the new vault's password. It first takes in the committed state and received revisions it already has, stops its control-plane node, and writes the new vault to `recovered.sqlite3.partial`, renamed to `recovered.sqlite3` once complete. It then moves the old vault file, control database, peer store, and invitation store into a new `archive-<time>` folder beside them, the vault file last, and renames the new vault into place; at launch a leftover partial file is deleted and a leftover complete one finishes the swap. The new vault gets a new transport certificate and an empty address book, and the app founds its control plane with this device as the only member. The other devices are not members of the new vault: on each, the owner has its copy put away (see the removed-device reset under the member transport) and it joins by pairing, and a device of the old domain that reappears can neither connect nor be believed. The old vault's membership is not changed by any of this.

The implemented import (Bitwarden JSON, Chrome CSV, Firefox CSV) takes at most 128 MiB and 100,000 entries. A refusal says where the file stopped being an export (a line and column, or a record and field) and never quotes it, since what it would quote can be a password. A row whose name is blank is given a title from its address, its user name, or its row number. Plaintext export is a separate deliberate format and action. Import accepts bounded input with a schema/version, produces row-level preview errors, and commits atomically or clearly reports partial behavior. Vendor adapters must map origin, username, password, note, and TOTP fields without silently discarding unknown material.

### Backups, restores, and password resets in the desktop app (Phase 6a, stop 5)

The app writes the backup above (version 4) to a file the owner names in the system's save dialog, by default `Open Secret Manager backup <date>.osmbackup` in the Documents folder; the extension is only a name, and the file is the JSON envelope. Right after writing it, the device reads it back with its own root key (`Vault::check_backup`): the envelope must be of this vault, carry this device's recovery wrapper exactly, and authenticate and parse; it reports how many items, revisions, and held revisions it holds. A file already at the chosen place is never replaced. The window never names a path: the commands open the dialogs themselves, and the file chosen for a restore stays in the app.

Restoring is offered only on a device without a vault, and is refused while a vault file that cannot be opened lies at the vault's place; the owner has that put away first, into an `archive-<time>` folder with the files that belong to it. The backup is restored, under the owner's new password, into a new `archive-<time>/vault.sqlite3`: a copy with the backup's identity and its whole history, which the Archive dialog opens with the new password and which the old recovery key also opens. From that copy the app makes the new vault with `Vault::fork`, as the recovery fork does: a new vault ID, new keys, and a new recovery key, the live versions of every item, conflicts kept as conflicts, and held revisions left in the copy. It goes through `recovered.sqlite3.partial` and `recovered.sqlite3` like the recovery fork, so an interruption after the new vault is complete is finished at the next launch, and one before it leaves only the archive folder. This device then founds the new vault's control plane alone, and other devices join by pairing. The restored copy never founds or joins a control plane, so restoring does not give a live control plane a second vault with its identity, as the rule above requires.

For a forgotten password, `Vault::reset_password` unlocks with the recovery key and wraps the root key under the new password with a new salt, in one step; the old password no longer opens that device, and the other devices keep theirs. It needs recovery turned on on that device and changes nothing if the key is wrong.

## TOTP and browser integration

TOTP stores the decoded secret, supported hash algorithm, digit count, and positive time step inside record ciphertext. Validate standard test vectors, explicit time input, and time-step boundaries according to [RFC 6238](https://datatracker.ietf.org/doc/html/rfc6238). An `otpauth` import must reject malformed Base32 and unsupported parameters rather than guessing.

Native messaging uses browser-defined 32-bit native-endian length-prefixed UTF-8 JSON. The implementation may impose a smaller documented limit than the browser. Reserve stdout for framed protocol responses; diagnostics go to stderr without secrets. Extension identity is explicitly allowlisted during installation, as described by [Chrome's native messaging documentation](https://developer.chrome.com/docs/extensions/develop/concepts/native-messaging).

A fill is asked for by the extension and decided in the desktop app. The request is `{version, request_id, tab_id, frame_id, document_id, origin}`; it names no record, because the owner chooses the login in the app and the extension never receives a list of vault items. The desktop session releases a login only after that choice, in the unlock it was made under. The response is bound to the same request and HTTPS origin. No protocol message accepts a master password. A missing desktop session returns unavailable.

### Implemented fill protocol (Phase 5, stop 1)

Implemented: the origin rule, the messages, the native host, the desktop session's end, the desktop app that serves it, and the extension (both below).

**Origin.** `osm-origin` is the one implementation, used by the core, the host, and the session. `Origin::of_url` gives the origin of an address stored with a login: the scheme must be `https`, there must be no user name or password, the path, query, and fragment are ignored, the host is taken as the URL standard serializes it (lower case, an international name in its ASCII form), and a missing port is 443. `Origin::parse` reads an origin from a message and accepts it only if it is already exactly that serialization, such as `https://example.com` or `https://example.com:8443`: a trailing slash, upper case, a written default port, or anything else that merely resembles an origin is refused. Two origins match only if host and port are equal. `https://example.com.` (trailing dot) is a different origin from `https://example.com`, as it is to a browser. An address without a scheme, such as `example.com`, has no origin, and its login is never offered. Redirects are not a concern of this rule: the extension reports the origin of the document it will fill.

**Messages.** Every message is a JSON object of at most 64 KiB with a `type`, and field names in camelCase. A message with an unknown field is refused. The extension sends:

| `type` | Fields | Rules |
| --- | --- | --- |
| `fill_request` | `version`, `requestId`, `tabId`, `frameId`, `documentId`, `origin` | `version` is 1. `requestId` and `documentId` are 1 to 64 ASCII letters, digits, or hyphens. `tabId` is not negative. `frameId` is 0: only the page itself is filled. `origin` must pass `Origin::parse`. |
| `cancel` | `version`, `requestId` | Withdraws a request that is waiting. Nothing is answered if none is. |

The extension receives:

| `type` | Fields | Meaning |
| --- | --- | --- |
| `waiting` | `requestId` | The desktop session has the request and the owner has not decided. Sent at once and then every 20 seconds. |
| `fill_reply` | `requestId`, `tabId`, `frameId`, `documentId`, `origin`, `username`, `password` | The owner's choice. The first five repeat the request. |
| `error` | `requestId` (or `null`), `code` | The request ended without a login. |

`code` is one of `invalid_message`, `unsupported_message`, `unsupported_version`, `extension_not_allowed`, `origin_rejected`, `frame_rejected`, `desktop_session_unavailable`, `busy` (another request is waiting), `replayed` (the request ID was used before), `denied`, `cancelled`, and `expired`. A request ID that is not of the allowed form is not repeated in the answer.

**Native host.** Frames on standard input and output carry the browser's native-endian length. A length of zero or above the limit, or input that ends inside a frame, ends the host with a failure status and no answer. The browser names the calling extension on the host's command line: a Chromium browser passes the extension's origin, `chrome-extension://<id>/`, and Firefox passes the path of the host's manifest and then the add-on ID. The host passes a request on only if that names the allowed extension: ID `hjgekjgkjnakgmiopldddikdkcjhnmge` in Chromium, which follows from the `key` in `manifest.chromium.json`, or `extension@opensecretmanager.org` in Firefox. Otherwise the answer is `extension_not_allowed` and no connection is made. The private half of that key was not kept; an extension published through a store has another ID, and the constant changes with it. The host holds at most four requests open and refuses a request ID that is already open.

**Socket.** The desktop session listens on the Unix socket `browser.sock` in the app's data folder (`OpenSecretManager` in the account's data folder), with mode 0600. The host connects only if that path is a socket owned by the account it runs as; the session answers only a connection from the account it runs as. Frames carry a big-endian 32-bit length and the same 64 KiB limit. Each connection carries one request: the host sends `{caller: {browser, extension}, request}`, where `browser` is `chromium` or `firefox` and `request` is the `fill_request` without its `type`. The session answers with the `waiting`, `fill_reply`, and `error` messages above and closes after the first that is not `waiting`. Closing the connection withdraws the request, and so does sending anything more on it. The host hands a response to the extension only if it parses and answers the request it forwarded: the same request ID, and for a `fill_reply` the same tab, frame, document, and origin. Anything else, a closed connection, or 60 seconds of silence becomes `desktop_session_unavailable`. A socket path longer than the operating system allows (about 104 bytes) cannot be bound.

**Desktop session.** `osm-vault-browser` checks the caller and the request again, since any program of the account can reach the socket. One request waits at a time; it ends after 120 seconds without a decision. The IDs of the last 1024 requests taken in are refused. `Desk::choices` gives what the owner is asked: the origin, the kind of browser, and, if the vault is unlocked, the logins from `Vault::logins_for_origin` together with `Vault::unlock_session`, 16 random bytes that name the current unlock and exist only in memory. `Desk::approve` takes the request, the chosen item, and that session. It releases the item's user name and password only if the vault is still in that unlock, the request is still the one waiting, and `Vault::credentials_for_origin` accepts the item for the request's origin, which it does only for a login whose address has exactly that origin. A locked vault, or one that was locked and unlocked again, refuses the choice and leaves the request waiting. A request can arrive while the vault is locked and waits for the unlock.

`osm-fill` is a development stand-in for the app: it opens a vault, serves the socket, and plays the owner from command-line options or commands on standard input.

### Desktop app and host manifests (Phase 5, stop 2)

The app binds the socket when it starts and serves it until it exits. If the socket is already served, by another copy of the app on the same data folder, this copy does not listen and says so in its Browser panel. A socket left behind by a copy that is gone is replaced.

The window learns of a request through the event `fill-request`, sent whenever a request arrives, ends, or is decided, and reads it with the command `fill_request`. That returns nothing, or `{requestId, origin, browser, secondsLeft, session, logins, notOffered}`. `session` is `Vault::unlock_session` as 32 hexadecimal digits, or null while the vault is locked or missing, in which case `logins` is empty. Each of `logins` is `{id, title, username, url, conflict}`; no password crosses to the window. `notOffered` names logins that cannot be chosen but whose address would have the page's origin if `https://` were put in front of it (`no_scheme`) or in place of `http://` (`not_https`), so that the app can say what to change; it is computed outside the origin rule and decides nothing. `approve_fill(requestId, itemId, session)` hands the owner's choice to `Desk::approve` and fails with `locked`, `fill_ended`, or `not_for_this_page`. `deny_fill(requestId)` turns the request down.

When a request arrives the app unhides, shows, and focuses its window. Whether an app in the background may take the front is the operating system's decision; if the window was behind, the app also asks for attention, which on macOS makes its icon signal until the owner comes or the request ends. After the owner fills or denies a request that the window came forward for, the app hides (on macOS) or minimizes, so that the browser is in front again. The rule that a covered window locks the vault is unchanged, so the vault locks at that point.

`browser_status` reports whether the app is listening, where the host program is, whether that place lasts (`temporaryPlace`, below), and each known browser whose own folder exists under the home folder. `connect_browser(id)` writes the host's manifest, `org.opensecretmanager.native.json`, into that browser's folder, replacing a file of that name; `disconnect_browser(id)` removes it. The manifest is `{name, description, path, type: "stdio"}` with `allowed_origins: ["chrome-extension://<id>/"]` for a Chromium browser or `allowed_extensions: ["extension@opensecretmanager.org"]` for Firefox, and `path` is the absolute path of the host program. A browser is `connected` only if the file is exactly that; any other content is reported as `other`. The folders, relative to the home folder:

| Browser | macOS | Linux |
| --- | --- | --- |
| Google Chrome | `Library/Application Support/Google/Chrome/NativeMessagingHosts` | `.config/google-chrome/NativeMessagingHosts` |
| Chromium | `Library/Application Support/Chromium/NativeMessagingHosts` | `.config/chromium/NativeMessagingHosts` |
| Brave | `Library/Application Support/BraveSoftware/Brave-Browser/NativeMessagingHosts` | `.config/BraveSoftware/Brave-Browser/NativeMessagingHosts` |
| Microsoft Edge | `Library/Application Support/Microsoft Edge/NativeMessagingHosts` | `.config/microsoft-edge/NativeMessagingHosts` |
| Firefox | `Library/Application Support/Mozilla/NativeMessagingHosts` | `.mozilla/native-messaging-hosts` |

The host program is `osm-native-host` beside the app's own program. A development build also looks where the repository's workspace builds it. On a system without Unix sockets the commands exist and report that filling into a browser is unavailable.

**Packaging (Phase 5 close-out).** `npm run tauri:build` in `apps/desktop` packages the app with the host inside it. It adds `src-tauri/tauri.bundle.conf.json` to the app's configuration, which does two things: before the app is compiled, `scripts/host.mjs` builds `osm-native-host` in release mode from the repository's workspace and copies it to `src-tauri/binaries/osm-native-host-<target>`; and the packaging tool takes that file as an external program, which puts it beside the app's own program: `Contents/MacOS/osm-native-host` in a macOS app. The copy in `binaries/` is not kept in the repository. The app's main configuration does not name the host, because it would then have to be built before every check and test of the app; so a plain `tauri build` packages no host, and such an app says in its Browser panel that it found none.

The app does not point a browser at a host whose path has a folder named `AppTranslocation` or one whose name begins with `.mount_`. macOS runs an app that was downloaded and not moved since from a copy in a folder of the first kind, and an AppImage runs from a folder of the second kind; both are gone when the app quits, and a manifest naming them would name nothing afterwards. `browser_status` then has `temporaryPlace: true`, `connect_browser` fails with `temporary_place`, and the panel says to install the app first. This is a rule on the path only.

### Extension (Phase 5, stop 3)

One source builds an extension for Chromium and one for Firefox (`dist/chromium`, `dist/firefox`), each with its manifest. Both ask for `activeTab`, `scripting`, and `nativeMessaging`, and for nothing else: no host permissions, no content script declared for any page, no storage. The Chromium manifest's `key` gives the extension the ID the host allows.

The extension acts on a press of its toolbar button (or the keyboard shortcut the owner may assign to it), which is what gives it access to that one tab:

1. The tab's address, from the browser, must be an `https` address without a user name or password; its origin is what is asked for. Otherwise the press ends with an explanation.
2. A script is put into the tab's top document (frame 0) and connected to. It answers with a name for the document, 1 to 64 letters, digits, or hyphens, made at random when the script first ran there; the document's origin, which must equal the tab's; and which of a user name field and a password field it found. With no field found, nothing is asked.
3. The `fill_request` goes to the host with a request ID made at random, the tab ID, frame 0, that document name, and the origin.
4. A `waiting` response updates the button. An `error` ends the request. A `fill_reply` is taken once: the request stops waiting before anything else happens, so a repeated reply meets no request. It is filled only if it names the same request, tab, frame, document, and origin, and only if the browser, asked again, says the tab still shows a page of that origin and still shows that document. For the second, the script leaves its document's name in the extension's own scope of that document, and the extension reads it back through the browser from whatever document the tab shows now; a document loaded since has none.
5. The script fills the fields it found when asked, if they are still in the document, by setting each value and sending `input` and `change` events. It sends no key events and does not submit. It fills once per request and only if the document name and origin it is handed are its own.

The connection to the script closes when its document goes away, and the script closes it itself when its page is left (`pagehide`), because Firefox can keep a document it has left, connection included, for the Back button; it usually does and sometimes does not. That ends the request: the extension sends `cancel` to the host and drops any reply that comes later. A document that was left is not filled even if the browser shows it again. The extension itself gives up after 150 seconds. When no request waits, it closes its connection to the host, which ends the host's process.

The script looks for the login form in the form of the field that has the focus, and otherwise in the whole document: the first visible password field, and the last visible text, email, or telephone field before it; or, with no password field, the focused field of those kinds or one whose `autocomplete`, `name`, or `id` names a user name or email. It does not look inside shadow roots or frames.

What the button says: `…` while the request waits, `✓` after a fill, `!` when nothing was filled, with the reason in its title. The button's icon and the extension's are the desktop app's icon at 16, 32, 48, and 128 pixels (`icons/`), drawn from it by `node icons.mjs` and kept in the repository.

The Firefox manifest differs from the Chromium one in three places: the background is a script rather than a service worker, `browser_specific_settings.gecko.id` gives the ID the host allows, and `action.default_area` puts the button in the toolbar. Firefox reports why a native connection closed on the connection itself (`port.error`), Chromium beside it (`runtime.lastError`); the extension reads both.

## Frozen formats (Phase 6, stop 1)

The formats below are frozen as the code writes them today. Frozen means: files written by this code are committed under each crate's `fixtures/` folder, tests read them with every build, and a change that makes a test fail is a format change, to be made under a new version number and never by rewriting a frozen file.

**What the tests hold to.** A vault file written by each of formats 1 to 7, made by that format's own code at the last commit that wrote it (`crates/vault-core/examples/make_fixture.rs`; the commits are in each `expected.json`), opens with its password, shows the content it was written with, is upgraded to format 7, keeps every signed revision as it was (format 1, which had no signatures, is signed anew), still belongs to its recovery key, and can then be edited, backed up, and restored. The format 7 file, which also holds a conflict between two authors, a removed device, held and staged revisions, two key epochs, and a recovery key not yet confirmed, is read without being written to. A second test reads that file's rows with the encodings in `vectors.json` alone and no vault code above them, so the vectors describe the file. A flipped bit in any authenticated value of the vault file, and a changed byte anywhere in a backup, is refused as not authentic; a file, backup, revision, invitation, or message of a later version is refused by its version and the file left untouched. Checksums of the binary fixtures are checked, because opening an older vault where it lies would upgrade it; tests work on copies. The bounds are tried on both sides: an item of exactly 16 MiB and one byte more, 16 parents and 17, an item ID of 128 bytes and 129, epoch 2^32 and one past it, 1,024 epoch keys and one more, and the stored password hashing cost at and outside 8 to 256 MiB, 1 to 10 iterations, and 1 to 16 lanes. Not tried at their edge, because of what filling them costs: 10,000 held revisions, 100,000 staged revisions or 512 MiB of them, and a 512 MiB backup.

**Device-local stores.** The control-plane database, the peer store, and the invitation store carry their layout version in SQLite's `user_version`. A store that says 0 is a new one or one written before the mark existed, and is layout 1; it is marked when opened. A store marked with a later version is refused before anything is written to it. The desktop app does not handle that refusal: it stops at launch, which happens only when an older build is run on a newer build's files.

**What the vault file proves and what it does not.** Every value that decides what is shown or who may write is under a key: the wrappers, the device's own identity, each author's and each removed device's mark, each epoch key, and every revision's header, content, and signature. The set of rows is not: whoever can write the file can remove a revision or a head row, or mark an edit as a deletion, and the item or the edit is then missing without an error, though nothing else can be shown in its place. `current_epoch` and `write_fence` are plain numbers; under a control plane both are set again from committed state at every unlock. The triggers that keep rows from being changed stop a mistake, not someone who can write the file.

**The fields of an item** are part of signed revision 2: `id`, `title`, `kind`, `username`, `password`, `url`, `notes`, `totp_secret`, `custom_fields`, `tags`, `favorite`, in that order, as JSON. All must be present. A build reads an item that has a field it does not know without that field, and would drop it at the next edit, so a build that adds a field must write a later revision version.

**Domain labels.** Each is followed by a NUL byte unless noted: `osm-key-wrap-v1` (wrapping a key; then the vault ID and `password`, `recovery`, or `unconfirmed-recovery`), `osm-device-signing-key-v1`, `osm-recipient-key-v1`, `osm-epoch-key-v1`, `osm-epoch-key-check-v1`, `osm-recovery-check-v1`, `osm-device-authorization-v1` and `osm-device-revocation-v1` (with their subkey labels `osm-device-authorization-key-v1` and `osm-device-revocation-key-v1`, no NUL), `osm-item-revision-v2`, `osm-revision-signature-v2`, `osm-revision-id-v2` (and `osm-item-revision-v1`, `osm-revision-id-v1`, read only when upgrading format 1), `osm-portable-backup-v1`, `osm-pairing-signature-v1` (then `join-request` or `enrollment-grant`, each with a NUL), `osm-pairing-transcript-v1`, `osm-pairing-token-v1`, `osm-pairing-sas-v1`, `osm-control-signature-v1`, `osm-control-request-v2`, `osm-control-request-id-v1`, `osm-epoch-key-hpke-v1` (HPKE `info`, no NUL), and `osm-invitation-token-v1` (no NUL). Text forms: `OSM-RK1-` (recovery key), `OSM-PAIR1-` (invitation), `OSM-BACKUP` (backup magic), `OSK1` (envelope magic).

**Changing a format.** Give it the next version number where it is marked. Keep reading the previous version, or refuse it by its number; never try an older reading after authentication fails. Add a fixture written by the new code, in a new folder or file, and a test that takes the previous version's fixture through the upgrade. Leave every existing fixture as it is: `make_fixture` and the tests that write vectors refuse to replace a file. Update this document in the same change.

**Not frozen.** The commands between the desktop window and its Rust shell, which ship together. The marker files the desktop app keeps beside the vault (`removed`, `putting-away`, `left-vault`, `reset-after-removal`), described above but without fixtures. Import formats, which are other products' files. The frames and locked inbox of `osm-vault-sync` that the revision protocol replaced, which nothing uses.
