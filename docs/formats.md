# Storage and protocol contracts

This document is for engineers implementing compatible vault, sync, and client adapters. The project is an early implementation. A design described here is not a stable public file format until there are frozen fixtures, a migration policy, and interoperability tests. [Implementation status](implementation-status.md) separates code from planned contracts.

## Ownership and interfaces

| Component | Owns | Must not own |
| --- | --- | --- |
| Vault core | Lock state; encryption; records; revision validation; backup/recovery; TOTP; generators; import parsing | Webviews, browser permissions, network listeners |
| Sync service | Peer transport; pairing; ciphertext queues; anti-entropy; durable consensus adapters | Record plaintext or password-derived keys |
| Desktop adapter | Core session lifecycle; narrow commands; explicit confirmation; clipboard and operating-system events | Independent cryptographic or origin-policy implementations |
| Browser extension | Browser-derived tab/frame identity; explicit record selection and fill | Persistent vault keys, automatic fill, arbitrary vault enumeration |
| Native host | Bounded framing; extension allowlist; authenticated desktop IPC; origin/request binding | A second unlocked vault process or a plaintext credential cache |

The core exposes create/open/unlock/lock, record list/read/write/delete, conflict inspection/resolution, encrypted backup/restore, password change, generator, TOTP, and import preview/commit operations. Locked access returns an explicit locked error. A ciphertext ingress API has a separate result type: `stored_pending`, `accepted`, `duplicate`, or `rejected`; successful storage is not equivalent to successful validation.

Adapters translate errors to stable categories: locked, authentication failed, invalid input, unsupported format, conflict, not authorized, missing dependency, quorum unavailable, storage failure, and unavailable. Errors and logs must not embed submitted passwords, decrypted records, invitations, or private key bytes.

## Serialization rules

Every persisted envelope and network message has an explicit format version. Unknown versions fail closed. Cryptographic encodings must be deterministic and domain-separated; ordinary JSON object iteration order is not a canonical signature format. Do not sign a map in one language and reconstruct it with a different key order in another.

For the initial Rust implementation, freeze the exact serde struct serialization, field order, integer representation, optional-field behavior, and byte encoding in fixtures before promising portability. The next public wire format must choose one canonical encoding and reject duplicate fields, trailing data, invalid byte lengths, and out-of-range integers. API-facing JSON is distinct from the authenticated byte representation.

Domain separation distinguishes local wrappers, record AAD, revision signatures, revision IDs, invitations, membership commands, HPKE context, and backup authentication. All identities in authenticated headers are covered by the signature or AEAD, never merely copied from an unauthenticated SQL column.

## Initial local prototype

The initial core model uses an `Item` with `id`, `title`, `kind`, `username`, `password`, `url`, `notes`, `totp_secret`, `custom_fields`, `tags`, and `favorite`. `kind` serializes as `login`, `secure_note`, `identity`, or `card`; custom fields use an ordered string map. `VaultItem` pairs the decrypted item with its revision ID. List summaries expose title, username, URL, and favorite status only through the unlocked core API.

`RevisionInfo` contains `item_id`, `revision`, and the sorted `parents` it supersedes. Revisions form a per-item DAG: a revision names zero parents (new item), one (edit or delete), or up to 16 (conflict resolution). Parents must be stored before a child is accepted and must belong to the same item; a missing parent returns `MissingParent` with nothing written so the caller can retry, and a cross-item parent returns `InvalidParent`.

An item's heads are its revisions that no stored revision names as a parent. A new revision removes only the parents it names from the head set, so revisions exchanged in either order converge on the same heads, and a concurrent edit or delete becomes an additional head. More than one head is a conflict: `get` returns the live head with the greatest revision ID (deterministic across devices; a deletion never hides a live edit) with `conflict` set, `versions` returns every head, and `update`/`delete` fail with `Unresolved`. `resolve` writes one revision whose parents are exactly the heads the owner reviewed; a head that arrived after review stays visible. Local writes check their head-set precondition inside the same IMMEDIATE transaction that updates the heads.

A received revision whose author is not in the authorized-device table is quarantined, not merged: `apply_encrypted_revision` returns `Quarantined` and stores the exact signed revision in a separate table that never affects heads. Only a well-formed revision that decrypts with the vault key is held, since the author ID is bound into the AEAD and relabeling it fails decryption; at most 10,000 entries are held (`QuarantineFull`). The owner reviews held revisions with `quarantined`, then either discards one (`discard_quarantined`) or accepts it (`accept_quarantined`). What those do depends on whether the author is a device the vault knows (see removed devices below). For an author it does not know, discarding drops the held entry on this device only, and if the revision is received again it is held again; accepting never trusts the unauthorized signature: the content is re-authored and signed by this device against the same parents, so it may become a concurrent head for the owner to resolve, and the held entry is released in the same transaction. If the author is later authorized and the same signed revision arrives, it applies as-is and its held copy is released. Backups carry held revisions.

The signed revision envelope is version 2; the SQLite layout is version 7. Format 2 vaults (one head per item) are migrated by SQL on first unlock without touching signed bytes, format 3 vaults gain the quarantine table, format 4 vaults gain the ingress queue when opened, without the key, so a locked vault can receive immediately, format 5 vaults are re-rooted at their next password unlock (below), and format 6 vaults gain the membership fields (below) when opened, without the key.

**Keys (format 6).** Each device has its own random 32-byte root key, which never leaves it. The password wrapper (Argon2id-derived key, AAD `osm-key-wrap-v1` plus NUL, vault ID, `password`) and the optional recovery wrapper (the recovery key, `recovery`) wrap the root key. The root key wraps the device signing seed, keys the authorized-device MACs, and wraps each epoch key in the `epoch_keys` table under AAD `osm-epoch-key-v1` plus NUL, vault ID, and the 64-bit epoch. Records are encrypted with the key of the epoch named in their header; new revisions use the vault's current epoch (`current_epoch` in `vault_meta`), older epochs stay readable, and a revision under an epoch this device has no key for is held in the ingress queue (`MissingEpochKey`) until the key is installed. `install_epoch_key` stores a key received from another member (a different key for a known epoch is refused) and `activate_epoch` moves new writes to a later epoch; under a control plane both happen only through reconciliation with committed state (below). `generate_epoch_key` stores a next-epoch key locally and is only for vaults without a control plane. Because the root key never leaves the device and enrollment sends only epoch keys, a removed device cannot unwrap epoch keys created after its removal even from another device's vault file or a newer backup. `epoch_key_check` is HMAC-SHA256 keyed by an epoch key over `osm-epoch-key-check-v1` plus NUL, the vault ID, and the 64-bit epoch; committed membership records it for every epoch so members can confirm they hold the same key.

**Membership fields (format 7).** Each device keeps a random 32-byte HPKE recipient secret, wrapped by its root key under AAD `osm-recipient-key-v1` plus NUL, vault ID, and device ID (`recipient_nonce`, `recipient_wrapped_secret` in `vault_meta`); its X25519 key pair is derived from it with the KEM's `DeriveKeyPair`, and epoch keys for this device are sealed to that public key. A joining device brings the secret it generated for pairing (`PendingDevice::recipient_secret`); a format 6 vault generates one at its next unlock. `write_fence` (default 1) is the earliest epoch new revisions may use: raised, never lowered, when committed membership activates a later epoch, and writable while locked; while `current_epoch` is below it every write fails with `EpochPending`. `revoked_devices` lists authorized authors removed by committed membership, each row carrying HMAC-SHA256 over `osm-device-revocation-v1` plus NUL, vault ID, and device ID, keyed by a subkey of the root key; unlock fails closed if one does not verify, and rows are never changed or deleted. Control requests are signed by the device key with `sign_control`, which prepends `osm-control-signature-v1` plus NUL.

Recovery is optional per device. `recovery_check` is HMAC-SHA256 keyed by the recovery key over `osm-recovery-check-v1` plus NUL and the vault ID; it is public, is sent during pairing, and lets a device verify a typed recovery key before `enable_recovery` wraps its root with it. A created or restored vault has recovery on; a joined vault starts with it off. Format 5 vaults used one shared key for everything. Re-rooting needs the password: in one transaction the shared key becomes epoch 1, a new root key rewraps the device seed, MACs, and epoch key, the password wrapper is rewritten, and every revision row is copied unchanged into tables that accept any epoch. The old recovery wrapper is kept only to verify the recovery key when it is entered to re-enable recovery; recovery unlock of a format 5 vault returns `UpgradeRequiresPassword`.

A recovery key exists only on the screen that shows it when a vault is made, so a vault can keep it until the owner confirms having stored it. `keep_recovery_key_until_confirmed` checks the key against `recovery_check` and writes it, encrypted with the root key under AAD `osm-key-wrap-v1` plus NUL, the vault ID, and `unconfirmed-recovery`, as the one row of an `unconfirmed_recovery` table (`singleton`, 24-byte `nonce`, `wrapped_key`). The table is made when a key is first kept and is absent from every other vault; it needs no format change, and a build that does not know it ignores it. `unconfirmed_recovery_key` reads it while unlocked, and `confirm_recovery_key_stored` deletes the row. Backups do not carry it. The desktop app keeps the key of a vault it creates and of a vault made by a recovery, shows it after each unlock, and stops keeping it when the owner confirms.

The ingress queue stores received revisions with their exact signed bytes before any verification. `stage_revision` works while locked and checks only the envelope's shape (version, vault ID, lengths, parent syntax); a revision already accepted, staged, or quarantined is a duplicate. It holds at most 100,000 revisions or 512 MiB of ciphertext (`IngressFull`). `process_staged` requires the key: it verifies and applies staged revisions in arrival order, repeating while any progress is made, and each revision leaves the queue in the same SQLite transaction that accepts or quarantines it. A revision that fails verification is discarded and reported; one whose parent is still missing stays staged; a storage failure stops processing without discarding anything. Revision IDs and ciphertext can be read while locked (`revision_ids`, `revisions_by_id`, `staged_revision_ids`, `staged_missing_parents`), since they are public metadata or already encrypted; decrypting anything still requires unlock. Backups are version 3; a backup without held revisions restores with none. Each vault holds one device signing identity: a random 16-byte device ID and an Ed25519 key pair. The 32-byte seed is encrypted with the master key under AAD `osm-device-signing-key-v1` plus NUL, the vault ID, device ID, and public key; it is only in memory while unlocked. A restored vault always generates a new device identity and never reuses the source device's key.

Record AAD is the ASCII domain `osm-item-revision-v2` plus a NUL byte, the 32-byte vault ID, length-prefixed UTF-8 item ID, one length-prefixed field holding the sorted parent revision IDs concatenated (each exactly 64 characters, so the field is unambiguous and zero or one parent encodes exactly as the earlier single-parent layout), an unsigned 64-bit key epoch (1 to 2^32), the 16-byte author device ID, and one tombstone byte. Length prefixes are unsigned 64-bit big-endian byte counts. The author signs `osm-revision-signature-v2` plus NUL, followed by length-prefixed AAD, nonce, and ciphertext. The revision ID is lowercase hex SHA-256 over `osm-revision-id-v2` plus NUL, followed by length-prefixed AAD, nonce, ciphertext, and signature, so it identifies the signed envelope.

A revision is accepted, and read, only after `verify_strict` succeeds against a public key in the local authorized-device table; a key carried by a revision is never trusted. Each authorized-device row carries HMAC-SHA256 over `osm-device-authorization-v1` plus NUL, vault ID, device ID, and public key, keyed by a subkey derived from the device's root key; unlock fails closed if any row does not verify. A created vault's table holds only this device, plus the source authors when restored from a backup; under a control plane, reconciliation adds every committed author. A revoked author's revisions that this device has already accepted stay readable. A revision of its that arrives later is held in the quarantine (`Quarantined`), unless an authorized, non-revoked author's revision names it as a parent, directly or through other held revisions by known authors: then the held revisions are verified and accepted as-is, parents first, in the same transaction as that child. `endorse_heads_of` writes, as this device, a revision with the same content on top of each head a given author wrote, so its last accepted state survives revocation on devices that never accepted it; `retry_quarantined` applies held revisions whose authors have since been authorized.

The owner's decision on a held revision by a known author, whose signature and content verify (`QuarantinedRevision::known_author`), uses that same rule, so that it holds on every device and not only on the one where it was made. A member that had not yet learned of the removal may have accepted the revision and keeps offering it; a decision that only dropped or re-authored the held copy would be undone at the next sync. `accept_quarantined` writes, as this device, a revision with the same content whose only parent is the held revision. `discard_quarantined` writes, as this device, a revision that keeps the item as it is on this device (a deletion if the item is not there) and whose parents are the held revision and the item's current head, unless the held revision already names that head; it returns `Unresolved`, changing nothing, while the item has more than one head, because there is then no single version to keep. Either revision vouches for the held one, which joins the history as it was signed, already superseded, on this device and on every device the new revision reaches. Neither overrides an edit made since: an accepted revision that is concurrent with the current head becomes a second head. A revision by a removed author that is already in the history is a replay when received again, not a new hold.

Format 1 vaults (unsigned revisions, no author) are migrated in one transaction on first unlock: every revision is authenticated with the version 1 AAD and ID, then re-sealed and signed by the new local device identity, with parent links remapped. Format 1 backups are rejected with `UnsupportedVersion(1)`; unlock the source vault with a current build and export again.

The local wrapper AAD is `osm-key-wrap-v1` plus NUL, the 32-byte vault ID, and the wrapping-method bytes. The initial non-test Argon2id configuration is 65,536 KiB, three iterations, and one lane. Unit-test builds use a cheaper profile; they are not evidence for production unlock performance. The recovery string is `OSM-RK1-` followed by unpadded base64url encoding of 32 random bytes.

The backup (version 4) requires recovery to be enabled on the exporting device. It is encrypted with that device's root key, carries the recovery wrapper of that root key, and its payload holds every epoch key, the current epoch, the authorized authors, the revoked ones (absent in older backups, meaning none), revisions, and held revisions. Revocations are restored after the revisions, so revisions accepted before a removal are restored as accepted. Restoration preserves the source vault identity while creating a new root key, password, recovery wrapper, and device identity. Earlier backup versions are rejected. This supports an offline local copy; it is not live device enrollment, and a vault restored this way shares its identity with the original, so it must not found or join a control plane as if it were a new vault. Recovery from lost devices is a fork into a new trust domain instead (see Backups and recovery). Sections below describing membership-authorized signers, epochs, author counters, or HPKE integration are target contracts beyond this local format.

## Local storage

SQLite is a transactional container for encrypted values, not an assertion of whole-file database encryption. Titles, usernames, passwords, notes, origins, and TOTP secrets belong inside record ciphertext. Public indexes may contain random identifiers, encrypted revision bytes, ancestry, epochs, and local sync progress. WAL, journal, temporary tables, error logs, and SQLite tracing must not contain plaintext secrets.

A vault header contains its format version, random vault identity, Argon2id salt/parameters, and an authenticated local key wrapper. The wrapper binds the vault identity, format, and KDF parameters. Use 16 or more random bytes for the salt, a 32-byte derived wrapping key, and a fresh 24-byte XChaCha20-Poly1305 nonce. Validate KDF resource bounds before deriving a key. Password changes create and authenticate a new wrapper in one transaction.

The unlocked key bundle contains the current epoch key and any retained historical keys needed to read existing revisions. Signing keys, recipient keys, and transport keys have separate roles. New devices receive their own independent local password wrapper. Copying another device's wrapper is backup replication, not a finished enrollment workflow.

Recommended logical tables are vault metadata, encrypted revisions, parent edges, materialized heads, pending ingress, committed public membership, recipient key envelopes, rotation progress, and sync cursors. Persistent Raft storage additionally needs votes, logs, applied state, and snapshots. These are logical requirements; exact SQL names remain implementation details.

## Immutable record revisions

The target authenticated revision header contains:

| Field | Rule |
| --- | --- |
| `format_version` | Explicit supported integer version |
| `vault_id` | Random stable vault identity; cross-vault copies rejected |
| `record_id` | Random stable record identity |
| `parents` | Sorted, unique revision IDs from the same record |
| `author_device_id` | Identifier resolved through authenticated membership |
| `membership_epoch` | Authorizing committed configuration |
| `key_epoch` | Encryption key selection, authenticated rather than guessed |
| `author_counter` | Durable per-author sequence; useful for replay/rollback diagnostics |
| `nonce` | 24 fresh random bytes for XChaCha20-Poly1305 |

Encrypt the serialized record or tombstone with the header as AAD. Sign a domain-separated encoding of the header and ciphertext with Ed25519. Define the revision ID as a domain-separated SHA-256 digest of the immutable signed envelope. If the prototype uses a random revision ID instead, signature coverage of that ID remains mandatory; a migration is required before substituting content addressing.

Signature validation uses a public key already authorized by membership. An attacker-supplied public key inside the revision is not sufficient. Parent existence and same-record ancestry are checked before acceptance. A missing parent delays materialization; it does not erase existing heads. Wall-clock timestamps are display metadata, not a total-order or revocation authority.

The materialized head set is derived, repairable state. A new revision supersedes only its named ancestors. An explicit conflict resolution names every head the owner resolved. A new concurrent head arriving later remains visible. Deletion is an encrypted tombstone with the same validation rules as an edit.

## HPKE key envelopes

Use an RFC 9180 implementation rather than a custom X25519 construction. The sync primitive currently uses DHKEM(X25519, HKDF-SHA256), HKDF-SHA256, and AES-256-GCM; record XChaCha20-Poly1305 and HPKE AES-256-GCM are different uses and have different nonce handling. Freeze this suite in fixtures before calling it a stable wire format. HPKE's suite identifiers and context handling follow [RFC 9180](https://www.rfc-editor.org/rfc/rfc9180.html).

An envelope binds the protocol version, vault, key epoch, recipient device/key identity, and authorizing membership transition. Its encrypted payload contains the epoch key and matching identifiers. Preserve the HPKE encapsulated key and ciphertext. Use a fixed domain label plus these identifiers as `info`/AAD. An authorized sender signs the envelope or includes it in authenticated committed control state. HPKE base mode alone does not authenticate that sender.

Unwrapping checks the recipient, vault, supported suite, epoch, and committed authorization before activation. Duplicate delivery is idempotent. Transport receipt while locked may store the envelope, but activation requires a later unlocked authorized step.

## Membership and rotation control plane

Record anti-entropy and membership consensus are separate protocols. The record plane exchanges immutable revisions and missing-parent requests. The control plane carries OpenRaft append/vote/snapshot messages plus application commands for enrollment and rotation. Pin authenticated device identity to the Raft node ID; an untrusted RPC field cannot choose another identity.

Application commands have a stable request ID for deduplication and a signed authorization context. Enrollment introduces a learner, verifies catch-up, transitions membership through OpenRaft, and only then makes the corresponding key grant active. Removal stages retained-recipient envelopes and has durable prepared, membership-committed, and epoch-active states. A retry after restart resumes the same request and cannot issue a conflicting epoch.

Do not expose a “force majority” input. Return quorum unavailable when the configured quorum cannot commit. A recovery fork has a new vault/control-plane identity and requires explicit re-enrollment.

### Implemented control plane (Phase 4, milestones 2 to 4)

`osm-vault-membership` runs OpenRaft 0.9 with storage v2. A Raft node ID is the device's 16-byte ID read as a big-endian `u128`, so Raft identities are device identities; each node's record in the membership carries the device's Ed25519 public key, TLS certificate pin, and HPKE recipient key. Every RPC names its sender in `vote` (the leader or candidate); the receiving node checks that against the identity its transport authenticated (`verify_rpc_sender`, inside `ControlNode::handle`) and answers `Refused` on a mismatch without passing the RPC to Raft, so a peer cannot speak for another device.

Each node keeps one SQLite database with `synchronous = FULL`: the vote, the log (one JSON entry per index), the committed and purged log IDs, the control state, and the latest snapshot. A database belongs to one vault: the state records the vault ID, and opening it, or installing a snapshot, for another vault fails. Appends commit before OpenRaft's flush callback runs; truncation and purge never leave a hole (the purge point is recorded before entries are deleted). The state machine persists its state in the transaction that records each applied batch.

Application entries are either signed control requests or completions. A signed request has a stable 16-byte request ID, the requester's device ID, the request, and an Ed25519 signature over `osm-control-signature-v1` plus NUL followed by `osm-control-request-v2` plus NUL, the vault ID, the request ID, the requester, and a tagged encoding of the request in which every variable-length list and envelope is length-prefixed. The state machine verifies the requester is an enrolled voter in the committed membership at that log position and checks the signature with that membership's key, so every node reaches the same verdict. Enrolled means a voter that is also an author under the key membership records for it: genesis makes the founding voters authors, and after that only a completed, signed enrollment does. Authority and epoch keys follow enrollment, never voting rights alone, because a Raft membership entry carries no signature: a voter that appeared in the membership without a signed enrollment can make no request and is given no key. Accepted request IDs are remembered (the last 4,096) and a repeat returns `AlreadyApplied`; a rejected request had no effect, is not remembered, and is evaluated again if resubmitted. The requests are:

- `Genesis` (once, before anything else is accepted): the current epoch, the key check of every epoch from 1, and the vault's authors. The requester holds every key so far; every voter is an author.
- `ProposeChange(Enroll)`: a device with its signing key, TLS pin, and recipient key, which must not be a voter or a removed device, and whose TLS pin no other device in the membership has (a certificate identifies one device).
- `ProposeChange(Remove)`: a voter other than the requester, with a rotation: the next epoch, its key check, and exactly one epoch-key envelope per remaining enrolled voter, each sealed to that voter's recorded signing and recipient keys for this vault and epoch.
- `CancelEnrollment`: abandons the pending enrollment it names; the change then targets the voters without that device.
- `GrantKeys`: envelopes for epochs an enrolled voter has not been given, only once its enrollment is complete and no change concerns it.

A proposal is accepted only when no change is pending and records the target voter set. A completion names the pending request and is accepted only once the committed membership is uniform and equals that target. It is unsigned and carries no authority of its own, since any node can check that condition; this lets a leader whose vault is locked finish a change. Completing an enrollment makes the device an author; completing a removal makes the rotation's epoch current, records its check and envelopes, drops the removed device's envelopes, and records the removed device with the device that removed it and with the TLS pin it had when the removal was proposed (`removed_pins`), so that it can be recognized and told. Removed devices never rejoin under the same ID.

The leader drives a pending change: for an enrollment it adds the device as a learner and waits until replication shows the learner has the leader's last log entry (checked explicitly each attempt, since a configuration including an unreachable learner could otherwise reach a majority without it), then calls `change_membership`, which commits the joint and then the uniform configuration, then appends the completion. For a cancelled enrollment or a removal it skips catch-up; a device dropped from the target is removed from membership outright, and learners no pending enrollment needs are removed once the configuration is committed and uniform. Every step is idempotent and the intent is in the log, so after a crash at any step the next leader resumes the same request; at most one change is pending, which serializes enrollment and removal. A follower passes a submitted request to the leader as a `Submit` RPC and retries while no leader is known or reachable; the leader accepts a passed-on request only from the device that signed it. A write that no quorum commits in time returns `QuorumUnavailable`; its outcome is unknown until a quorum returns, and resubmitting the same request is safe.

The node reaches other devices through a `Dialer`, which a transport implements along with `Link` (one RPC and its reply at a time, bounded by a deadline). The RPCs are `AppendEntries`, `Vote`, `InstallSnapshot`, and `Submit`. Two transports exist: the in-process `Router` used by tests, which models partitions, and the TLS transport below. A snapshot is the whole control state as JSON and is sent in OpenRaft's chunks; installing one for another vault fails.

### Rotation and enrollment coupling (Phase 4, milestone 3)

`osm_vault_peer::control` couples a vault to committed state. Request IDs are SHA-256 of `osm-control-request-id-v1` plus NUL, the vault ID, the length-prefixed kind, and its subject (the joiner's device ID; the removed device and new epoch; the granted device and epochs), truncated to 16 bytes, so a retry after an unknown outcome is recognized instead of producing a second rotation or grant. `found` initializes a one-voter cluster and commits genesis from the vault's epoch keys and authors. `removal_request` generates the next epoch key, seals it to every other voter, records its check, and discards it: every remaining device, including the requester, installs it from its own envelope only after the removal completes, so no device holds a key for an epoch that was never committed. `grant_requests` seals the epochs a settled voter lacks; any unlocked member may submit them.

`reconcile(vault, state)` is idempotent and is run whenever applied state changes and right after unlock, before staged revisions are processed or anything is written. If committed membership removed this device it reports that and changes nothing. Otherwise it raises the write fence to the committed epoch, which works while locked and is all it does then. Unlocked, it authorizes every committed author (a known device with a different key is a protocol violation), revokes every removed device, checks every epoch key it holds against the committed check (`EpochKeyMismatch` on a difference), opens each envelope sealed to it, checks and installs the key, activates the committed epoch once it holds it, applies held revisions whose authors are now authorized, and, on the device that removed another, endorses that device's remaining heads. A member that has applied a removal's completion is fenced until it holds the new key; one that has not yet learned of it can still write under the old epoch.

Enrollment through pairing: after the owner confirms the short code, `approve_enrollment` consumes the invitation token and returns the signed `Enroll` proposal and an `EnrollmentGrant` (version 1, vault ID, the proposal's request ID, the recovery check, the vault's members from the inviter's committed state, each with device ID, TLS pin, and optional address, the port the inviter accepts member connections on, and the inviter's pairing signature over `enrollment-grant` plus NUL, the transcript, and those fields, with the member list and each address length-prefixed). The inviter submits the proposal and sends the grant only if it is accepted; otherwise it tells the joiner the enrollment was refused. The joiner runs its control-plane node from the start, under the device ID from `Joiner::control_device`. It has no log to tell it whose connections to accept, and the leader need not be the inviter, so `Joiner::members` verifies the grant, requires the inviter's entry to carry the pin from the invitation, and returns the members for the joiner to accept and to announce itself to (below). The leader brings it up to date as a learner and makes it a voter, and a member then grants it every epoch key. `Joiner::finish_enrollment` verifies the grant against the invitation's key, requires that committed state records this device as a settled voter and author with the keys and pin it sent, opens every envelope sealed to it with the recipient key derived from its pending secret, checks each against the committed check, and creates its vault with the committed epoch, authors, and removed devices; it fails with `EnrollmentPending` until then. A joiner that never catches up can be dropped with `CancelEnrollment`; it never received a key.

A device that already holds a copy of the vault, paired before vaults had a control plane, joins under the identity it has (`Joiner::start_with_vault`). The invitation must be for its vault. Its join request carries its existing device ID, signing key, and recipient key, signed by the vault; genesis listed it as an author, and an enrollment of an author is accepted only under the same key. It then becomes a voter like any joiner, and `Joiner::finish_in_place` verifies the grant, requires that committed state records it as an enrolled voter with those keys and its pin, and reconciles its vault: the keys it holds are checked against the committed checks and nothing is created or replaced. One of the two devices founds the control plane and the other joins it; both keep their vaults.

### Member transport (Phase 4, milestone 4, stages 1 and 2)

`osm_vault_peer::MemberEndpoint` is one device's end of the connections between a vault's devices, over the same TLS 1.3 settings as pairing: mandatory client certificates, pins in both directions, no resumption. One listener serves two channels, the control plane's RPCs and revision sync, chosen by the first frame.

**Whose certificate is accepted.** The server decides at every handshake, from the node's `Directory`: the devices its own log names (the nodes of the committed membership, of the latest membership in the log, and of a pending, uncancelled enrollment), plus devices a member introduced, minus every removed device. The pin is mapped back to a device ID, and a pin that two accepted devices share maps to neither. A client dials only the pin that membership records for its target. A removed device's certificate also completes the handshake, but only so that its `Open` can be answered with `Removed`; nothing it sends is taken in.

**Introductions.** A device's own log does not always name the current members: a device still being enrolled has no log, and one that was away while another joined does not know the newcomer, which may now lead. Such a device accepts pins on a member's word until its log names them: from the signed enrollment grant, and from the roster on a connection to or from a device that its own committed state lists as a member. A roster holds only what its sender's committed state lists as enrolled voters, never what the sender was itself told. What the log records wins: an introduction neither replaces a recorded device's pin nor claims a recorded pin for another device, and it never admits a removed device. At most 256 are kept, in memory.

**Member.** For rosters and for sync, a member is a device that the receiver's committed state lists as an enrolled voter, not removed, and not the subject of a pending removal. This holds while another device's change is under way.

**Opening exchange.** After the handshake the client sends `Open` (postcard, in a frame as for sync): protocol version 2, vault ID, channel (`Control` or `Sync`), the port it accepts member connections on, if any, and its roster of at most 64 members (device ID, TLS pin, optional address of at most 128 bytes). The server answers `Welcome` with its own roster, or closes after `UnsupportedVersion`, `VaultMismatch`, `NotAMember` (the sync channel, from a device that is not a member), or `Removed`. The opening exchange has a 10-second timeout. `MemberEndpoint::announce` opens a control connection only for this exchange.

**Addresses.** Each device keeps one address per device in the `member_addresses` table of its peer store file (`AddressBook::open`): the source address of an authenticated incoming connection with the port from its `Open`, an address it connected to successfully, or one from a believed roster. A roster address fills in only when none is known or the known one last failed. Addresses are advisory; the pin authenticates whatever answers.

**Control channel.** Each frame is then one RPC and its reply, in turn: the 4-byte length and a JSON body, the encoding the log is stored in, at most 24 MiB. The receiver looks the pin up again before every RPC, so a device removed while its connection is open loses it, and passes the RPC to the node under that device ID. A reply is `Refused` when the RPC claims a sender other than the connection's device, or passes on a request another device signed. A connection without an RPC for 120 seconds is closed. The client makes its connection when first needed, in a task of its own so that a deadline on one RPC does not abandon a handshake, and drops it after any failed or abandoned exchange.

**Sync channel.** Both ends require the other to be a member by their own committed state: the client before dialing, with the pin from that state, and the server before answering `Welcome`. The connection then carries a sync session as described under the implemented protocol below, `Hello` included. Before the session starts, each end reconciles its vault with its committed control state (`MemberSync::run_shared`), so received revisions are judged against the current authors and removals; a device whose state says it was removed exchanges nothing. A session takes the vault for one message at a time (`SharedVault`), never while it waits for the peer, so two devices that dial each other at the same moment both finish, and the application keeps using the vault in between.

**Removal notice.** The entry that completes a removal is appended after the membership no longer includes the removed device, so that device may never receive it. It learns of its removal when it next connects to a member: the `Removed` answer, which `MemberEndpoint::told_removed` then reports. A device believes this from any member it dialed by pin.

**Serving.** An accept loop (`serve_members`) completes handshakes concurrently, serves control connections itself, and hands sync connections to the application, which runs them against the vault. It serves at most 64 connections at once, handshakes included, and closes them when it stops.

**Development CLI.** `osm-peer device` runs one device: its node, listener, a loop that reconciles the vault, then processes staged revisions, and submits key grants whenever applied state changes, and commands on stdin to found, invite, add, list, sync, remove, and report status. `osm-peer device-locked` runs the same device without its password, as an app that is open but locked. `osm-peer join-device` pairs through the enrollment path and then runs as `device` does.

**Desktop app.** The app keeps `control.sqlite3` (the node's database) beside the vault and the peer store. It runs the node and listener whenever it is open and the vault has a control plane, locked or not. Creating a vault founds the control plane; a vault from before, never paired, is founded at its next unlock; a vault paired by an older build waits for the owner to choose which device founds it. On every change of applied state, and at unlock before anything staged is processed, it reconciles the vault, then processes staged revisions and submits key grants if unlocked. A joining device runs its node from the moment it shows the short code, keeps its pending identity in memory until it is enrolled, and discards its control database if the join is abandoned. A device that learns it was removed, from its own committed state or from a member's `Removed` answer, writes an empty `removed` file beside the vault, since its own log may never record the removal, and is then reset at once: the app stops its node and moves the vault file first, then the control database, peer store, invitation store, and the marker, into an `archive-<time>` folder. That leaves a device without a vault, which joins again as a new device with a new transport certificate. A `reset-after-removal` file names the archive folder until the device has a vault again, so the app can say what happened. The owner can have a device's copy put away in the same way without a removal (`leave_vault`, which takes the device's password), for a device whose vault was replaced by a recovery on another device; a `left-vault` file then names the archive folder. Before any file is moved, a `putting-away` file records the reason (`removed` or `left`) and the archive folder on two lines, and it is deleted once the note is written; at launch, before the vault or its stores are opened, a `putting-away` file that names a folder beside the vault has its move finished, and any other is deleted. If the app stops between the marker and the reset, the next launch finishes the reset; while the marker exists the app runs no node, founds nothing, and refuses to sync.

## Pairing and sync messages

An invitation needs a version, invitation ID, random single-use secret, expiry, inviter identity/pin, vault identity, and candidate connection addresses. Address discovery is advisory. Invitation redemption persists the one-use decision before reporting success and binds both endpoint keys to the confirmed transcript.

Frame messages with an explicit bounded length and request ID. Negotiate only supported protocol versions without silently falling back to weaker authentication. Inventory, revision batches, missing-parent requests, and acknowledgments expose ciphertext metadata only. Acknowledgments distinguish durable receipt from validated acceptance. Limit message size, revisions per batch, total pending bytes, concurrent peers, and processing time.

The receiver deduplicates before enqueueing where safe, authenticates metadata before accepting it, and stores unknown ancestry or unavailable epochs as pending. Synchronization resumes from persisted state after a crash. Arrival order and duplicate batches must yield the same accepted heads.

### Implemented protocol (Phase 3, with Phase 4 enrollment)

`osm-vault-peer` implements pairing and sync as sans-IO steps and carries them over TLS 1.3 on TCP. There is no discovery or NAT traversal: the invitation names the inviter's address, and members reach each other at the addresses in their address books (above).

Pairing is owner-confirmed, and the owner's confirmation becomes an enrollment proposal to the vault's control plane (above), so any number of devices can join. Until Phase 4 milestone 4 the confirmation itself was the enrollment authority, for at most one paired peer; that path is removed. A peer store written then may still name that one device (`PeerStore::legacy_peers`), which is read only to offer the move onto the control plane. The invitation text is `OSM-PAIR1-` plus base64url of a postcard body: version 1, vault ID, inviter device ID and Ed25519 public key, the inviter's TLS certificate pin, up to four advisory addresses, a 32-byte one-use token, and an expiry of at most 15 minutes. The token is stored only as a hash (`InvitationStore::issue_pairing`), binds to the first device that redeems it, and is consumed before the joiner is authorized.

The joiner creates its own device identity (`PendingDevice`), including the recipient secret its HPKE key pair is derived from and which its vault keeps, and sends a request signed with the new device key that also names its TLS certificate pin. Both sides hash a transcript: `osm-pairing-transcript-v1` plus NUL, vault ID, inviter device ID, key, and TLS pin, SHA-256 of `osm-pairing-token-v1` plus NUL and the token, joiner device ID, key, HPKE key, and TLS pin, so the short code also confirms both transport identities. The short code both screens show is the first four bytes of SHA-256 of `osm-pairing-sas-v1` plus NUL and the transcript, reduced modulo 1,000,000. The inviter checks the token without consuming it (`InvitationStore::check`) and the request signature before the owner is asked. After the owner confirms, the inviter proposes the enrollment and answers with the enrollment grant, `Declined` if the owner declined, or `Refused` if the vault's devices did not accept the proposal. The inviter's root key and recovery wrapper are never sent, and epoch keys reach the joiner only as envelopes in committed control state once it is a voter; the joiner wraps them under a new root key of its own and starts with recovery off. Pairing signatures prefix `osm-pairing-signature-v1` plus NUL so they cannot be confused with revision signatures. The joiner verifies the grant against the key from the invitation, requires the owner's confirmation, and calls `Vault::join`, which creates its vault with its own password and identity; no other device's password wrapper ever leaves it.

Transport identity is separate from the revision signing key: each device has a self-signed Ed25519 certificate generated with rcgen and stored in its peer store, which is created with owner-only permissions. The TLS private key is not encrypted, because a locked device must still be able to receive ciphertext; revision authenticity never depends on it. Peers pin the SHA-256 of each other's certificate and ignore names, validity periods, and system roots; the handshake signature still proves possession of the pinned certificate's key. Only TLS 1.3 is offered, client certificates are mandatory, and session resumption is disabled so every connection checks both certificates. During pairing the inviter accepts any client certificate and then requires that the signed join request names exactly the certificate on the connection; the joiner pins the inviter from the invitation. Connections that fail before the owner is asked are dropped and the inviter keeps listening until the invitation window closes. Sync runs only between members, over the member transport (above). Reads and writes run concurrently, each frame has a 60-second timeout, and connects and handshakes have 10-second timeouts.

Frames are a 4-byte big-endian length and a postcard body, at most 24 MiB; the declared length is checked before the body is buffered, and trailing bytes are rejected. A sync session opens with `Hello` (protocol version 1, vault ID, and the port this device accepts sync connections on, if any; the receiver records the peer's address as the connection's source IP with that port) and an `Inventory` of every accepted and staged revision ID, so nothing already staged is sent again. Each side answers the other's inventory with the revisions it lacks, parents first, in `Revisions` batches of at most 64 revisions or 8 MiB, then `Done`. Revisions are the core's signed `EncryptedRevision`s. Every received revision is staged first (durable receipt); if the vault is unlocked the session then processes the queue (validated acceptance): unknown authors are quarantined, and any other invalid revision is discarded and ends the session. A locked device receives and stages only, and can still send its stored revisions. After `Done` the receiver sends `Need` for parents of staged revisions that it has neither accepted nor staged, for at most 8 rounds. `Finished` means a side needs nothing more. A session started while unlocked processes anything staged earlier. An interrupted session is resumed by starting another: inventories recompute what is missing, and staged revisions survive restarts.

## Backups and recovery

The public backup contract must freeze a magic value, format version, vault identity, cryptographic suite, KDF or recovery-wrapper descriptor, nonce, authenticated manifest, and encrypted payload. Authenticate the manifest and key wrappers. The payload contains a consistent database snapshot or equivalent complete encrypted records and required key material. Copying only the SQLite main file while a WAL transaction is outstanding is not a valid snapshot procedure.

Recovery uses a high-entropy secret independent of the local unlock password. A restore API authenticates before writing and takes a new destination and new local password. It must not overwrite an existing vault by default. Live rejoin creates a fresh device identity; restoring an old signing identity into two writers risks cloned identity and counter reuse.

### Implemented recovery fork (Phase 4, milestone 4)

When too many of a vault's devices are lost for the rest to remove them, no membership change can commit, by design. `Vault::fork` starts a new trust domain from one surviving device instead. The new vault has a new random vault ID, device identity, root key, epoch 1 key, recipient secret, and recovery key, and its only authorized author is the new identity. Every live version of every item is sealed again under the new vault ID and epoch key and signed by the new identity, with no parents: an item with several live versions stays a conflict. Earlier history, deletions, held revisions, and unverified received revisions are not carried; an unresolved choice between an edit and a deletion keeps the edit. The source vault is not modified. Because the vault ID is inside every revision's authenticated header and every control request's signature, nothing signed or sealed in one domain verifies in the other.

The desktop app does this as one confirmed action that asks for the vault password again, which also becomes the new vault's password. It first takes in the committed state and received revisions it already has, stops its control-plane node, and writes the new vault to `recovered.sqlite3.partial`, renamed to `recovered.sqlite3` once complete. It then moves the old vault file, control database, peer store, and invitation store into a new `archive-<time>` folder beside them, the vault file last, and renames the new vault into place; at launch a leftover partial file is deleted and a leftover complete one finishes the swap. The new vault gets a new transport certificate and an empty address book, and the app founds its control plane with this device as the only member. The other devices are not members of the new vault: on each, the owner has its copy put away (see the removed-device reset under the member transport) and it joins by pairing, and a device of the old domain that reappears can neither connect nor be believed. The old vault's membership is not changed by any of this.

Plaintext export is a separate deliberate format and action. Import accepts bounded input with a schema/version, produces row-level preview errors, and commits atomically or clearly reports partial behavior. Vendor adapters must map origin, username, password, note, and TOTP fields without silently discarding unknown material.

## TOTP and browser integration

TOTP stores the decoded secret, supported hash algorithm, digit count, and positive time step inside record ciphertext. Validate standard test vectors, explicit time input, and time-step boundaries according to [RFC 6238](https://datatracker.ietf.org/doc/html/rfc6238). An `otpauth` import must reject malformed Base32 and unsupported parameters rather than guessing.

Native messaging uses browser-defined 32-bit native-endian length-prefixed UTF-8 JSON. The implementation may impose a smaller documented limit than the browser. Reserve stdout for framed protocol responses; diagnostics go to stderr without secrets. Extension identity is explicitly allowlisted during installation, as described by [Chrome's native messaging documentation](https://developer.chrome.com/docs/extensions/develop/concepts/native-messaging).

The target fill request is `{version, request_id, tab_id, frame_id, document_id, origin, record_id}`. The desktop produces a one-use grant only after explicit selection/confirmation in an unlocked session. The response is bound to the same request and normalized HTTPS origin. No protocol message accepts a master password from page content. A missing desktop session returns unavailable. Exact origin normalization is shared with core policy and tested for default ports, IDNs, trailing dots, userinfo, opaque origins, redirects, and subdomain mismatch.
