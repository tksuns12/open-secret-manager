# Storage and protocol contracts

This document is for engineers implementing compatible vault, sync, and client adapters. The formats the code reads and writes today are frozen: [Frozen formats](#frozen-formats-phase-6-stop-1) lists them, the files that pin them, and the rule for changing one. Sections that describe a target rather than the implementation say so. [Implementation status](implementation-status.md) separates code from planned contracts.

## Ownership and interfaces

| Component | Owns | Must not own |
| --- | --- | --- |
| Vault core | Lock state; encryption; records; revision validation; backup/recovery; TOTP; generators; import parsing | Webviews, browser permissions, network listeners |
| Sync service | Peer transport; pairing; ciphertext queues; anti-entropy; durable consensus adapters | Record plaintext or password-derived keys |
| Desktop adapter | Core session lifecycle; narrow commands; explicit confirmation; the owner's choice of a login for a browser fill; clipboard and operating-system events | Independent cryptographic or origin-policy implementations |
| Browser extension | Browser-derived tab/frame identity; the owner's explicit request; fill | Persistent vault keys, automatic fill, any list of vault items |
| Native host | Bounded framing; extension allowlist; the connection to the desktop session; origin/request binding | A vault, a key, or a plaintext credential cache |

The core exposes create/open/unlock/lock, record list/read/write/delete, conflict inspection/resolution, encrypted backup/restore, password change, generator, TOTP, and import preview/commit operations. Locked access returns an explicit locked error. A ciphertext ingress API has a separate result type: `stored_pending`, `accepted`, `duplicate`, or `rejected`; successful storage is not equivalent to successful validation.

Adapters translate errors to stable categories: locked, authentication failed, invalid input, unsupported format, conflict, not authorized, missing dependency, quorum unavailable, storage failure, and unavailable. Errors and logs must not embed submitted passwords, decrypted records, invitations, or private key bytes.

## Serialization rules

Every persisted envelope and network message has an explicit format version. Unknown versions fail closed. Cryptographic encodings must be deterministic and domain-separated; ordinary JSON object iteration order is not a canonical signature format. Do not sign a map in one language and reconstruct it with a different key order in another.

The Rust implementation's serde struct serialization, field order, integer representation, optional-field behavior, and byte encoding are frozen in fixtures (see Frozen formats). What is signed or used as AAD is always a hand-written byte encoding, never serde output. The messages around it are postcard between devices and JSON in the control plane, the backup, and the browser fill; trailing bytes after a postcard message are refused, a JSON field given twice is refused, and a field a build does not know is ignored in the backup's payload and the control state, kept in an item (since Phase 8; see the fields of an item below), and refused in a browser fill message. A next wire format should choose one canonical encoding and refuse unknown fields everywhere. API-facing JSON is distinct from the authenticated byte representation.

Domain separation distinguishes local wrappers, record AAD, revision signatures, revision IDs, invitations, membership commands, HPKE context, and backup authentication. All identities in authenticated headers are covered by the signature or AEAD, never merely copied from an unauthenticated SQL column.

## Initial local prototype

The initial core model uses an `Item` with `id`, `title`, `kind`, `username`, `password`, `url`, `notes`, `totp_secret`, `custom_fields`, `tags`, and `favorite`. `kind` serializes as `login`, `secure_note`, `identity`, or `card`; custom fields use an ordered string map. `VaultItem` pairs the decrypted item with its revision ID. List summaries expose title, username, URL, and favorite status only through the unlocked core API; since Phase 17 a card's summary also has the last four digits of its number and its brand, and since Phase 18 a summary says how many passkeys a login holds.

**A card's fields (since Phase 17).** A card keeps its fields among its other fields (`custom_fields`), under the names the owner reads there, which are also those a Bitwarden import gives them (`crates/vault-core/src/card.rs`): `Cardholder name`, `Number`, `Expiry month`, `Expiry year`, `Security code`, and `Brand`. Every device reads and writes a card by these names, so they are part of this format: a build that named them otherwise would see another device's card as one with other fields. As this build writes them, `Number` is the number without the spaces and dashes it was typed with, `Expiry month` is two digits (a month typed as one digit, 1 to 9, gets a leading zero), `Expiry year` is four (a year typed as two digits is put in this century), and `Brand` is the one the owner chose or, when a number is saved without one, the one its first digits name, as Bitwarden names them (`Visa`, `Mastercard`, `Amex`, `Discover`, `JCB`, `Diners Club`, `UnionPay`); a field set empty is removed. Values read that are not written so, such as an imported month of one digit, are taken as they are. A change to a card's fields leaves its other fields as they are. What may be shown of a number is its last four digits, and only for a number of 12 to 19 digits; the number and the security code are otherwise copied, never shown, as a password is. A number that fails the check its last digit is for (Luhn) is kept as typed, with a warning in the editors.

**A login's passkeys (since Phase 18).** A login keeps its passkeys in the field `passkeys` (`crates/vault-core/src/passkey.rs`), a list written after `favorite` and only when there is one, so that an item without stays as earlier builds wrote it; absent, it reads as none. A passkey is an object of nine fields, all present, in this order: `credential_id` (the credential's ID, 1 to 1023 bytes, in base64url without padding), `rp_id` (the site it is for), `user_handle` (the site's ID for the account, 1 to 64 bytes, base64url), `user_name` and `user_display_name` (the site's names for the account as it gave them, cut to 256 characters), `algorithm` (COSE's number for the key's algorithm: -7, ES256, for every passkey made here), `key` (the private key, PKCS #8 in base64url without padding), `created_at` (seconds since 1970 by the clock of the device that made it; 0 when not known), and `sign_count` (the counter it was imported with; 0 for one made here). It keeps fields it does not know, as an item does, after its own, and a field given twice is refused. Its values are not checked when read: a later build's passkey, of another algorithm perhaps, is kept as it is through an edit here, and is neither listed nor used. A passkey a device writes and did not read is checked: only a login holds passkeys, so a login with one stays a login; at most 32 on a login; each once, by RP ID and credential ID; IDs of those lengths in that form; an RP ID by the rule below; algorithm -7; and a key that parses as P-256. Settling a conflict or restoring a version keeps the passkeys of every version it follows besides its own, so that keeping one version whole loses none; a version that is not a login cannot then be kept over one with passkeys. Removing one is an edit: its key stays in the earlier versions and in backups. Builds from Phase 8 to 17 keep the field as one they do not know; builds before Phase 8 drop it at their next edit.

**What a passkey sends (since Phase 18).** As WebAuthn Level 3 has an authenticator send it, made by the core alone. The authenticator data is the SHA-256 of the RP ID; the flags: user present, backup eligible, and backed up (the passkey syncs), user verified only when the owner was verified in that same request, and attested data when the passkey is made; the counter, big-endian, which is 0 for a passkey made here, since devices that share it cannot agree on one, and for a passkey imported with a counter above 0 the time in seconds, which only grows, or that counter if it is larger; and, when made, an AAGUID of zeros, the credential ID's length in two bytes, the ID, and the public key as a COSE key (`{1: 2, 3: -7, -1: 1, -2: x, -3: y}`). The attestation object is `{"fmt": "none", "attStmt": {}, "authData": ...}`, in CTAP2's canonical CBOR. A signature is ECDSA over P-256 with SHA-256, of the authenticator data followed by the hash of the client data, DER encoded, its nonce by RFC 6979, so that one key and message give one signature. The client data a device makes is `{"type":"webauthn.create","challenge":<base64url>,"origin":<origin>,"crossOrigin":false}` in that order, or `webauthn.get` for a sign-in. A site is sent WebAuthn's JSON: `RegistrationResponseJSON`, with `transports` `["hybrid","internal"]`, the public key in SPKI DER, and `credProps.rk` true; or `AuthenticationResponseJSON`, with the user handle. `crates/vault-core/fixtures/vectors-passkeys.json` holds all of them for fixed inputs, and a test checks them with a verifier written apart from this code (`@simplewebauthn/server`).

**Which sites a passkey is for (since Phase 18).** An RP ID is a domain in lower-case ASCII as the URL standard writes one (an international name in its `xn--` form), at most 253 characters, its labels of letters, digits, and hyphens, with no dot at the end. It is not an address (one whose last label is a number), and not a public suffix by the public suffix list, its private section included (the `psl` crate): `com`, `co.uk`, `github.io`, and `localhost` are refused, though WebAuthn lets a page whose own host is a public suffix use it. A page may use the passkeys of its own host or of a domain it is under: a page of `www.example.com` those of `example.com`, not those of `other.example.com`, whatever its port. An app names its RP ID, which is checked only to be one a passkey may be for (Phase 18, stop 5, says what else an app is asked). A request read, `PublicKeyCredentialCreationOptionsJSON` or `PublicKeyCredentialRequestOptionsJSON`, is at most 64 KiB; its binary values are base64url, padded or not; a null stands for a value left out; it names at most 256 credentials, a challenge of 1 to 1024 bytes, a user handle of 1 to 64, and to make a passkey ES256 among the algorithms it takes, or none, which stands for the defaults; a `userVerification` this build does not know is `preferred`. Anything else is refused, and the browser's own passkeys may still answer it.

`RevisionInfo` contains `item_id`, `revision`, and the sorted `parents` it supersedes. Revisions form a per-item DAG: a revision names zero parents (new item), one (edit or delete), or up to 16 (conflict resolution). Parents must be stored before a child is accepted and must belong to the same item; a missing parent returns `MissingParent` with nothing written so the caller can retry, and a cross-item parent returns `InvalidParent`.

An item's heads are its revisions that no stored revision names as a parent. A new revision removes only the parents it names from the head set, so revisions exchanged in either order converge on the same heads, and a concurrent edit or delete becomes an additional head. More than one head is a conflict: `get` returns the live head with the greatest revision ID (deterministic across devices; a deletion never hides a live edit) with `conflict` set, `versions` returns every head, and `update`/`delete` fail with `Unresolved`. `resolve` writes one revision whose parents are exactly the heads the owner reviewed; a head that arrived after review stays visible. Local writes check their head-set precondition inside the same IMMEDIATE transaction that updates the heads.

A received revision whose author is not in the authorized-device table is quarantined, not merged: `apply_encrypted_revision` returns `Quarantined` and stores the exact signed revision in a separate table that never affects heads. Only a well-formed revision that decrypts with the vault key is held, since the author ID is bound into the AEAD and relabeling it fails decryption; at most 10,000 entries are held (`QuarantineFull`). The owner reviews held revisions with `quarantined`, then either discards one (`discard_quarantined`) or accepts it (`accept_quarantined`). What those do depends on whether the author is a device the vault knows (see removed devices below). For an author it does not know, discarding drops the held entry on this device only, and if the revision is received again it is held again; accepting never trusts the unauthorized signature: the content is re-authored and signed by this device against the same parents, so it may become a concurrent head for the owner to resolve, and the held entry is released in the same transaction. If the author is later authorized and the same signed revision arrives, it applies as-is and its held copy is released. Backups carry held revisions.

The signed revision envelope is version 2; the SQLite layout is version 8. Format 2 vaults (one head per item) are migrated by SQL on first unlock without touching signed bytes, format 3 vaults gain the quarantine table, format 4 vaults gain the ingress queue when opened, without the key, so a locked vault can receive immediately, format 5 vaults are re-rooted at their next password unlock (below), format 6 vaults gain the membership fields (below) when opened, without the key, and format 7 vaults are sealed (below) at their next unlock.

**Keys (format 6).** Each device has its own random 32-byte root key, which never leaves it. The password wrapper (Argon2id-derived key, AAD `osm-key-wrap-v1` plus NUL, vault ID, `password`) and the optional recovery wrapper (the recovery key, `recovery`) wrap the root key. The root key wraps the device signing seed, keys the authorized-device MACs, and wraps each epoch key in the `epoch_keys` table under AAD `osm-epoch-key-v1` plus NUL, vault ID, and the 64-bit epoch. Records are encrypted with the key of the epoch named in their header; new revisions use the vault's current epoch (`current_epoch` in `vault_meta`), older epochs stay readable, and a revision under an epoch this device has no key for is held in the ingress queue (`MissingEpochKey`) until the key is installed. `install_epoch_key` stores a key received from another member (a different key for a known epoch is refused) and `activate_epoch` moves new writes to a later epoch; under a control plane both happen only through reconciliation with committed state (below). `generate_epoch_key` stores a next-epoch key locally and is only for vaults without a control plane. Because the root key never leaves the device and enrollment sends only epoch keys, a removed device cannot unwrap epoch keys created after its removal even from another device's vault file or a newer backup. `epoch_key_check` is HMAC-SHA256 keyed by an epoch key over `osm-epoch-key-check-v1` plus NUL, the vault ID, and the 64-bit epoch; committed membership records it for every epoch so members can confirm they hold the same key.

**Membership fields (format 7).** Each device keeps a random 32-byte HPKE recipient secret, wrapped by its root key under AAD `osm-recipient-key-v1` plus NUL, vault ID, and device ID (`recipient_nonce`, `recipient_wrapped_secret` in `vault_meta`); its X25519 key pair is derived from it with the KEM's `DeriveKeyPair`, and epoch keys for this device are sealed to that public key. A joining device brings the secret it generated for pairing (`PendingDevice::recipient_secret`); a format 6 vault generates one at its next unlock. `write_fence` (default 1) is the earliest epoch new revisions may use: raised, never lowered, when committed membership activates a later epoch, and writable while locked; while `current_epoch` is below it every write fails with `EpochPending`. `revoked_devices` lists authorized authors removed by committed membership, each row carrying HMAC-SHA256 over `osm-device-revocation-v1` plus NUL, vault ID, and device ID, keyed by a subkey of the root key; unlock fails closed if one does not verify, and rows are never changed or deleted. Control requests are signed by the device key with `sign_control`, which prepends `osm-control-signature-v1` plus NUL.

**Row seal (format 8, Phase 10).** The rows of four tables are never changed or removed: `revisions`, `devices`, `revoked_devices`, and `epoch_keys`. Since format 8 the vault keeps a seal over which of them exist, in `vault_meta.row_seal`: a 24-byte nonce followed by 32 bytes encrypted by the root key under AAD `osm-row-seal-v1` plus NUL and the vault ID, 72 bytes in all. The 32 bytes are the XOR of one mark per row. A mark is HMAC-SHA256 over `osm-row-mark-v1`, NUL, the table's name, NUL, and the row's key (a revision ID as its 64 characters, a device ID as its 16 bytes, an epoch as 64 bits), under a seal key that is HMAC-SHA256 of `osm-row-seal-key-v1` under the root key. Each transaction that adds such rows opens the seal, adds their marks, and writes it again under a new nonce, so a write costs the same however many rows there are. The connection learns which rows it added from temporary triggers that live in its memory, never in the file, and are rolled back with the transaction. Because the marks are encrypted, someone who can write the file but holds no root key can neither take a row's mark out of the seal nor learn a mark by comparing the seal before and after a write. Two processes may write one file, as the iOS app and its AutoFill extension do: each write opens the seal the other left.

At each unlock the vault checks, in one transaction, that the seal opens and holds the marks of the rows there are; that each revision's columns give its ID, which covers its header, nonce, ciphertext, and signature; and that `heads` holds exactly the revisions that no other revision names as a parent, each with its deletion flag. The check reads every revision, so it grows with the vault: at 20,000 revisions an unlock took about 0.2 seconds longer than at 100 on the development machine, in a release build (medians of 10 unlocks, 366 and 172 ms, at a load average of about 25; `crates/vault-core/examples/unlock_cost.rs`). If anything fails, `rows_changed` in `vault_meta` becomes 1, the heads are set again from the revisions, and the rows there are are sealed again, so later writes keep the seal. A seal that no longer opens at a write, broken since the unlock, is handled the same way at that write. `rows_changed` stays 1 at every unlock until the owner confirms (`Vault::rows_changed`, `Vault::confirm_rows_changed`). A revision that is missing comes back from another device at the next sync, as anything a device lacks does. Until a version between two others comes back, nothing left says that the one before it was superseded, so the item shows both as a conflict; the version fetched again is not made a head, since a stored one names it, and the conflict goes. A revision whose row was changed cannot be put right, since rows are never changed, and its item shows an error or stays missing. A row added to the file is found the same way and reported, not removed. Held and staged revisions (`quarantine`, `ingress`) are not sealed: one taken out is as if it had not arrived, and it comes again.

Format 8 also wraps the device signing seed under a label of its own, so that a format 8 file whose header is set back to 7, which would skip the check, no longer unlocks. A format 7 vault becomes format 8 at its next unlock, which needs the root key: in one transaction it gains `row_seal` and `rows_changed` (if a file of this build's schema does not have them already), its signing seed is wrapped again under the new label, and its rows are sealed.

Recovery is optional per device. `recovery_check` is HMAC-SHA256 keyed by the recovery key over `osm-recovery-check-v1` plus NUL and the vault ID; it is public, is sent during pairing, and lets a device verify a typed recovery key before `enable_recovery` wraps its root with it. A created or restored vault has recovery on; a joined vault starts with it off. Format 5 vaults used one shared key for everything. Re-rooting needs the password: in one transaction the shared key becomes epoch 1, a new root key rewraps the device seed, MACs, and epoch key, the password wrapper is rewritten, and every revision row is copied unchanged into tables that accept any epoch. The old recovery wrapper is kept only to verify the recovery key when it is entered to re-enable recovery; recovery unlock of a format 5 vault returns `UpgradeRequiresPassword`.

A recovery key exists only on the screen that shows it when a vault is made, so a vault can keep it until the owner confirms having stored it. `keep_recovery_key_until_confirmed` checks the key against `recovery_check` and writes it, encrypted with the root key under AAD `osm-key-wrap-v1` plus NUL, the vault ID, and `unconfirmed-recovery`, as the one row of an `unconfirmed_recovery` table (`singleton`, 24-byte `nonce`, `wrapped_key`). The table is made when a key is first kept and is absent from every other vault; it needs no format change, and a build that does not know it ignores it. `unconfirmed_recovery_key` reads it while unlocked, and `confirm_recovery_key_stored` deletes the row. Backups do not carry it. The desktop app keeps the key of a vault it creates and of a vault made by a recovery, shows it after each unlock, and stops keeping it when the owner confirms.

The ingress queue stores received revisions with their exact signed bytes before any verification. `stage_revision` works while locked and checks only the envelope's shape (version, vault ID, lengths, parent syntax); a revision already accepted, staged, or quarantined is a duplicate. It holds at most 100,000 revisions or 512 MiB of ciphertext (`IngressFull`). `process_staged` requires the key: it verifies and applies staged revisions in arrival order, repeating while any progress is made, and each revision leaves the queue in the same SQLite transaction that accepts or quarantines it. A revision that fails verification is discarded and reported; one whose parent is still missing stays staged; a storage failure stops processing without discarding anything. Revision IDs and ciphertext can be read while locked (`revision_ids`, `revisions_by_id`, `staged_revision_ids`, `staged_missing_parents`), since they are public metadata or already encrypted; decrypting anything still requires unlock. A backup without held revisions restores with none. Each vault holds one device signing identity: a random 16-byte device ID and an Ed25519 key pair. The 32-byte seed is encrypted with the master key under AAD `osm-device-signing-key-v1` plus NUL, the vault ID, device ID, and public key (`osm-device-signing-key-v2` since format 8); it is only in memory while unlocked. A restored vault always generates a new device identity and never reuses the source device's key.

Record AAD is the ASCII domain `osm-item-revision-v2` plus a NUL byte, the 32-byte vault ID, length-prefixed UTF-8 item ID, one length-prefixed field holding the sorted parent revision IDs concatenated (each exactly 64 characters, so the field is unambiguous and zero or one parent encodes exactly as the earlier single-parent layout), an unsigned 64-bit key epoch (1 to 2^32), the 16-byte author device ID, and one tombstone byte. Length prefixes are unsigned 64-bit big-endian byte counts. The author signs `osm-revision-signature-v2` plus NUL, followed by length-prefixed AAD, nonce, and ciphertext. The revision ID is lowercase hex SHA-256 over `osm-revision-id-v2` plus NUL, followed by length-prefixed AAD, nonce, ciphertext, and signature, so it identifies the signed envelope.

A revision is accepted, and read, only after `verify_strict` succeeds against a public key in the local authorized-device table; a key carried by a revision is never trusted. Each authorized-device row carries HMAC-SHA256 over `osm-device-authorization-v1` plus NUL, vault ID, device ID, and public key, keyed by a subkey of the device's root key (HMAC-SHA256 of `osm-device-authorization-key-v1`, without a NUL, under the root key; the revocation mark's subkey is made the same way from `osm-device-revocation-key-v1`); unlock fails closed if any row does not verify. A created vault's table holds only this device, plus the source authors when restored from a backup; under a control plane, reconciliation adds every committed author. A revoked author's revisions that this device has already accepted stay readable. A revision of its that arrives later is held in the quarantine (`Quarantined`), unless an authorized, non-revoked author's revision names it as a parent, directly or through other held revisions by known authors: then the held revisions are verified and accepted as-is, parents first, in the same transaction as that child. `endorse_heads_of` writes, as this device, a revision with the same content on top of each head a given author wrote, so its last accepted state survives revocation on devices that never accepted it; `retry_quarantined` applies held revisions whose authors have since been authorized.

The owner's decision on a held revision by a known author, whose signature and content verify (`QuarantinedRevision::known_author`), uses that same rule, so that it holds on every device and not only on the one where it was made. A member that had not yet learned of the removal may have accepted the revision and keeps offering it; a decision that only dropped or re-authored the held copy would be undone at the next sync. `accept_quarantined` writes, as this device, a revision with the same content whose only parent is the held revision. `discard_quarantined` writes, as this device, a revision that keeps the item as it is on this device (a deletion if the item is not there) and whose parents are the held revision and the item's current head, unless the held revision already names that head; it returns `Unresolved`, changing nothing, while the item has more than one head, because there is then no single version to keep. Either revision vouches for the held one, which joins the history as it was signed, already superseded, on this device and on every device the new revision reaches. Neither overrides an edit made since: an accepted revision that is concurrent with the current head becomes a second head. A revision by a removed author that is already in the history is a replay when received again, not a new hold.

Format 1 vaults (unsigned revisions, no author) are migrated in one transaction on first unlock: every revision is authenticated with the version 1 AAD (`osm-item-revision-v1` plus NUL, vault ID, length-prefixed item ID, the one parent or nothing as a length-prefixed field, the 64-bit epoch, and the tombstone byte) and ID (SHA-256 over `osm-revision-id-v1` plus NUL and the length-prefixed AAD, nonce, and ciphertext), then re-sealed and signed by the new local device identity, with parent links remapped. Format 1 backups are rejected with `UnsupportedVersion(1)`; unlock the source vault with a current build and export again.

The local wrapper AAD is `osm-key-wrap-v1` plus NUL, the 32-byte vault ID, and the wrapping-method bytes. The initial non-test Argon2id configuration is 65,536 KiB, three iterations, and one lane. Unit-test builds use a cheaper profile; they are not evidence for production unlock performance. The recovery string is `OSM-RK1-` followed by unpadded base64url encoding of 32 random bytes.

The backup (version 4) requires recovery to be enabled on the exporting device. It is encrypted with that device's root key, carries the recovery wrapper of that root key, and its payload holds every epoch key, the current epoch, the authorized authors, the revoked ones (absent in older backups, meaning none), revisions, and held revisions. The file is one JSON object: `magic` (`OSM-BACKUP`), `format_version`, and five values as unpadded base64url text: `vault_id`, `recovery_nonce` and `recovery_wrapped_key` (the recovery wrapper), `nonce`, and `ciphertext`. The ciphertext is the payload as JSON (`current_epoch`, `epoch_keys` as `{epoch, key}`, `devices` as `{device_id, public_key}`, `revisions`, `quarantine`, `revoked`, with byte strings as arrays of numbers), sealed under the root key with AAD `osm-portable-backup-v1` plus NUL, the vault ID, and the two recovery texts as they stand in the file, each behind its length as 8 big-endian bytes. Restoring applies the accepted revisions, then the revocations, then the held revisions: a removed device's revisions that were accepted are restored as accepted, and one that was held stays held. (Until Phase 6 the held revisions were applied before the revocations, so a removed device's held revision was taken in by a restore; the frozen backup caught this.) Restoration preserves the source vault identity while creating a new root key, password, recovery wrapper, and device identity. Earlier backup versions are rejected. This supports an offline local copy; it is not live device enrollment, and a vault restored this way shares its identity with the original, so it must not found or join a control plane as if it were a new vault. Recovery from lost devices is a fork into a new trust domain instead (see Backups and recovery). Sections below describing membership-authorized signers, epochs, author counters, or HPKE integration are target contracts beyond this local format.

## Local storage

SQLite is a transactional container for encrypted values, not an assertion of whole-file database encryption. Titles, usernames, passwords, notes, origins, and TOTP secrets belong inside record ciphertext. Public indexes may contain random identifiers, encrypted revision bytes, ancestry, epochs, and local sync progress. WAL, journal, temporary tables, error logs, and SQLite tracing must not contain plaintext secrets.

A vault header contains its format version, random vault identity, Argon2id salt/parameters, and an authenticated local key wrapper. The wrapper binds the vault identity, format, and KDF parameters. Use 16 or more random bytes for the salt, a 32-byte derived wrapping key, and a fresh 24-byte XChaCha20-Poly1305 nonce. Validate KDF resource bounds before deriving a key. Password changes create and authenticate a new wrapper in one transaction.

The unlocked key bundle contains the current epoch key and any retained historical keys needed to read existing revisions. Signing keys, recipient keys, and transport keys have separate roles. New devices receive their own independent local password wrapper. Copying another device's wrapper is backup replication, not a finished enrollment workflow.

Recommended logical tables are vault metadata, encrypted revisions, parent edges, materialized heads, pending ingress, committed public membership, recipient key envelopes, rotation progress, and sync cursors. Persistent Raft storage additionally needs votes, logs, applied state, and snapshots. These are logical requirements; exact SQL names remain implementation details.

The desktop app keeps the owner's settings in `settings.json` beside the vault in its data folder (since Phase 8): a JSON object with `autoLockMinutes`, the minutes without activity that lock the vault, one of 1, 5, 15, and 60. A missing file, or one with anything else, means 5. Since Phase 19 it may also hold `generator`, the password generator's choice, once the owner changed it from the default: an object of `length` (8 to 64), `lowercase`, `uppercase`, `digits`, `symbols`, and `avoidLookAlike`, all booleans but the length, at least one kind true. A choice missing, or not all of that, is the default (20 characters of every kind, without look-alikes); each of the two is read on its own, so that one not as written leaves the other, and an earlier build reads the file as before, leaving the choice out when it writes the file again. It is written whole (to `settings.json.partial`, then renamed), is not synced, and stays when the device is reset.

The shared generator (`generate_password`) makes a password of the length asked, at least one character of each kind chosen and the rest of any of them, from the system's random source, shuffled: lowercase `a`–`z`, uppercase `A`–`Z`, digits `0`–`9`, and the symbols ``!@#$%^&*()-_=+[]{}:,.?``. Until Phase 19 it always left out `l`, `I`, `O`, `0`, and `1`, which are taken for one another; since then that is the choice `avoid_look_alike`, on by default, and it leaves `0` and `1` in when digits are the only kind chosen, as for a PIN. A length below the number of kinds chosen, or above 1024, or no kind, is refused. The desktop window's preview makes passwords the same way, of the same characters, which a test checks.

Beside it, `backups.json` (since Phase 12) notes when this device last saved a backup, for the window's reminder: a JSON object with `vault`, the vault's ID in hex; `since`, when the device began counting (the first time it looked, for a vault it has not backed up), in seconds since 1970; and `lastBackup`, when it last saved a backup, in seconds since 1970, or `null`. It holds no secret and is not synced. A file for another vault ID, or with anything else, is taken for none and replaced with a new count; it is written whole like the settings. Since Phase 15 a backup is also noted in the vault, so that its other devices learn of it: a revision of the item ID `osm-backups`, a deletion whose content is `{"saved_at":<seconds>}` (see the fields of an item), following that ID's current versions, at most 16. The latest time among them, and its author, is the vault's last backup; the reminder counts from it or from `lastBackup`, whichever is later. No item may take that ID: a version of it that is not a deletion is refused when made or received, and the ID is left out of the list, of Recently deleted, and of a backup's count of items. Builds before Phase 15 list only items with a current version that is not a deletion, and in Recently deleted only items with one before the deletion, so they show none of it. Since Phase 16 the vault keeps the code of its relay the same way, under the item ID `osm-relay`: each time the owner sets the relay or takes it away, a deletion whose content is `{"saved_at":<seconds>,"relay":<code or null>}`, following that ID's current versions; the latest by its time, and of two in one second the one stored last, is the vault's relay. A note in another form is passed over. Neither ID is listed, and no item may take either.

**Rows seen (desktop, since 2026-10-14).** So that an earlier copy of the vault's file put in its place is found, the desktop keeps outside its data folder how many rows that are never changed or removed it last saw the file hold: the rows of the four sealed tables, `revisions`, `devices`, `revoked_devices`, and `epoch_keys` (`Vault::sealed_rows`). It is a generic password in the system's keystore, the login Keychain on macOS or the Secret Service on Linux: service `org.opensecretmanager.rows-seen`, account the device's ID in hex, and the count in decimal as its secret. A new vault, joined, restored, or started over has a device ID of its own and so an entry of its own. The count is written after the writes that add such rows, when the owner's writes and the received revisions taken in have raised it, and at every lock; it only rises, but for the owner confirming the card, which sets it to what the file holds then. At each unlock, before anything received is taken in, a file that holds fewer sets `rows_changed` (`Vault::note_set_back`), as rows taken out do. An entry that is not a number is taken for none and written over. Without a keystore nothing is kept and nothing is checked. The phones keep no count.

## Immutable record revisions

The target authenticated revision header contains:

| Field | Rule |
| --- | --- |
| `format_version` | Explicit supported integer version |
| `vault_id` | Random stable vault identity; cross-vault copies rejected |
| `record_id` | Random stable record identity |
| `parents` | Sorted, unique revision IDs from the same record |
| `author_device_id` | Identifier resolved through authenticated membership |
| `membership_epoch` | Authorizing committed configuration |
| `key_epoch` | Encryption key selection, authenticated rather than guessed |
| `author_counter` | Durable per-author sequence; useful for replay/rollback diagnostics |
| `nonce` | 24 fresh random bytes for XChaCha20-Poly1305 |

Encrypt the serialized record or tombstone with the header as AAD. Sign a domain-separated encoding of the header and ciphertext with Ed25519. Define the revision ID as a domain-separated SHA-256 digest of the immutable signed envelope. If the prototype uses a random revision ID instead, signature coverage of that ID remains mandatory; a migration is required before substituting content addressing.

Signature validation uses a public key already authorized by membership. An attacker-supplied public key inside the revision is not sufficient. Parent existence and same-record ancestry are checked before acceptance. A missing parent delays materialization; it does not erase existing heads. Wall-clock timestamps are display metadata, not a total-order or revocation authority.

The materialized head set is derived, repairable state. A new revision supersedes only its named ancestors. An explicit conflict resolution names every head the owner resolved. A new concurrent head arriving later remains visible. Deletion is an encrypted tombstone with the same validation rules as an edit.

An item's history (since Phase 8) is every stored revision of it, read newest first in the order the device stored them, in which a revision always follows its parents. Since Phase 15 a revision says when it was saved, by the clock of the device that saved it (see the fields of an item); the history shows it and nothing orders or checks by it, since a device's clock is whatever it says. A revision from before has no time, nor has a revision whose time is that of a parent saved by another device: a build from before Phase 15 that edits an item keeps `saved_at` as a field it does not know and writes it back, so its edit would otherwise show its parent's time. (One device saving twice in a second gives both the same time, and both keep it.) An item is deleted when every one of its heads is a tombstone; the version before is the nearest of the tombstones' ancestors that is not one. A restore writes no new kind of revision: it is a resolution, with the content of the chosen earlier revision of the same item (never a tombstone), whose parents are the heads the owner was shown; a head that arrived since stays, as in any resolution.

## HPKE key envelopes

Use an RFC 9180 implementation rather than a custom X25519 construction. The sync primitive currently uses DHKEM(X25519, HKDF-SHA256), HKDF-SHA256, and AES-256-GCM; record XChaCha20-Poly1305 and HPKE AES-256-GCM are different uses and have different nonce handling. The suite and the envelope's layout are frozen in a fixture. HPKE's suite identifiers and context handling follow [RFC 9180](https://www.rfc-editor.org/rfc/rfc9180.html).

The implemented envelope is 188 bytes: the magic `OSK1`, the 32-byte vault ID, the epoch as 8 big-endian bytes, the recipient device's 32-byte signing key, the recipient's 32-byte HPKE public key, the 32-byte encapsulated key, and 48 bytes of ciphertext (the 32-byte epoch key and its tag). It is HPKE base mode with `info` `osm-epoch-key-hpke-v1` and, as AAD, the vault ID, epoch, recipient device, and recipient key in that order (104 bytes). A recipient's key pair is the KEM's `DeriveKeyPair` of its 32-byte recipient secret. An envelope binds the protocol version, vault, key epoch, recipient device/key identity, and authorizing membership transition. Its encrypted payload contains the epoch key and matching identifiers. Preserve the HPKE encapsulated key and ciphertext. Use a fixed domain label plus these identifiers as `info`/AAD. An authorized sender signs the envelope or includes it in authenticated committed control state. HPKE base mode alone does not authenticate that sender.

Unwrapping checks the recipient, vault, supported suite, epoch, and committed authorization before activation. Duplicate delivery is idempotent. Transport receipt while locked may store the envelope, but activation requires a later unlocked authorized step.

## Membership and rotation control plane

Record anti-entropy and membership consensus are separate protocols. The record plane exchanges immutable revisions and missing-parent requests. The control plane carries OpenRaft append/vote/snapshot messages plus application commands for enrollment and rotation. Pin authenticated device identity to the Raft node ID; an untrusted RPC field cannot choose another identity.

Application commands have a stable request ID for deduplication and a signed authorization context. Enrollment introduces a learner, verifies catch-up, transitions membership through OpenRaft, and only then makes the corresponding key grant active. Removal stages retained-recipient envelopes and has durable prepared, membership-committed, and epoch-active states. A retry after restart resumes the same request and cannot issue a conflicting epoch.

Do not expose a “force majority” input. Return quorum unavailable when the configured quorum cannot commit. A recovery fork has a new vault/control-plane identity and requires explicit re-enrollment.

### Implemented control plane (Phase 4, milestones 2 to 4)

`osm-vault-membership` runs OpenRaft 0.9 with storage v2. A Raft node ID is the device's 16-byte ID read as a big-endian `u128`, so Raft identities are device identities; each node's record in the membership carries the device's Ed25519 public key, TLS certificate pin, and HPKE recipient key. Every RPC names its sender in `vote` (the leader or candidate); the receiving node checks that against the identity its transport authenticated (`verify_rpc_sender`, inside `ControlNode::handle`) and answers `Refused` on a mismatch without passing the RPC to Raft, so a peer cannot speak for another device.

Each node keeps one SQLite database with `synchronous = FULL`: the vote, the log (one JSON entry per index), the committed and purged log IDs, the control state, and the latest snapshot. Its layout version, 1, is in SQLite's `user_version` (see Frozen formats). The JSON is serde's of the Rust types, OpenRaft's among them; a device ID is a JSON integer of up to 39 digits, and a decimal string where it is a map's key, which a reader that keeps numbers as 64-bit floats cannot hold. A database belongs to one vault: the state records the vault ID, and opening it, or installing a snapshot, for another vault fails. Appends commit before OpenRaft's flush callback runs; truncation and purge never leave a hole (the purge point is recorded before entries are deleted). The state machine persists its state in the transaction that records each applied batch.

Application entries are either signed control requests or completions. A signed request has a stable 16-byte request ID, the requester's device ID, the request, and an Ed25519 signature over `osm-control-signature-v1` plus NUL followed by `osm-control-request-v2` plus NUL, the vault ID, the request ID, the requester, and a tagged encoding of the request in which every variable-length list and envelope is length-prefixed. The state machine verifies the requester is an enrolled voter in the committed membership at that log position and checks the signature with that membership's key, so every node reaches the same verdict. Enrolled means a voter that is also an author under the key membership records for it: genesis makes the founding voters authors, and after that only a completed, signed enrollment does. Authority and epoch keys follow enrollment, never voting rights alone, because a Raft membership entry carries no signature: a voter that appeared in the membership without a signed enrollment can make no request and is given no key. Accepted request IDs are remembered (the last 4,096) and a repeat returns `AlreadyApplied`; a rejected request had no effect, is not remembered, and is evaluated again if resubmitted. The requests are:

- `Genesis` (once, before anything else is accepted): the current epoch, the key check of every epoch from 1, and the vault's authors. The requester holds every key so far; every voter is an author.
- `ProposeChange(Enroll)`: a device with its signing key, TLS pin, and recipient key, which must not be a voter or a removed device, and whose TLS pin no other device in the membership has (a certificate identifies one device).
- `ProposeChange(Remove)`: a voter other than the requester, with a rotation: the next epoch, its key check, and exactly one epoch-key envelope per remaining enrolled voter, each sealed to that voter's recorded signing and recipient keys for this vault and epoch.
- `CancelEnrollment`: abandons the pending enrollment it names; the change then targets the voters without that device.
- `GrantKeys`: envelopes for epochs an enrolled voter has not been given, only once its enrollment is complete and no change concerns it.

A proposal is accepted only when no change is pending and records the target voter set. A completion names the pending request and is accepted only once the committed membership is uniform and equals that target. It is unsigned and carries no authority of its own, since any node can check that condition; this lets a leader whose vault is locked finish a change. Completing an enrollment makes the device an author; completing a removal makes the rotation's epoch current, records its check and envelopes, drops the removed device's envelopes, and records the removed device with the device that removed it and with the TLS pin it had when the removal was proposed (`removed_pins`), so that it can be recognized and told. Removed devices never rejoin under the same ID. A removed device is not enrolled again by anything: if a membership entry, which carries no signature, makes it a voter again, it can make no request and is given no key, and the members can remove it again, with the record of its first removal kept. (Until Phase 6a stop 2 such a device counted as enrolled, so every member would have sealed the newest epoch keys to it; a property test of the state machine found this.)

The leader drives a pending change: for an enrollment it adds the device as a learner and waits until replication shows the learner has the leader's last log entry (checked explicitly each attempt, since a configuration including an unreachable learner could otherwise reach a majority without it), then calls `change_membership`, which commits the joint and then the uniform configuration, then appends the completion. For a cancelled enrollment or a removal it skips catch-up; a device dropped from the target is removed from membership outright, and learners no pending enrollment needs are removed once the configuration is committed and uniform. Every step is idempotent and the intent is in the log, so after a crash at any step the next leader resumes the same request; at most one change is pending, which serializes enrollment and removal. A follower passes a submitted request to the leader as a `Submit` RPC and retries while no leader is known or reachable; the leader accepts a passed-on request only from the device that signed it. A write that no quorum commits in time returns `QuorumUnavailable`; its outcome is unknown until a quorum returns, and resubmitting the same request is safe.

The node reaches other devices through a `Dialer`, which a transport implements along with `Link` (one RPC and its reply at a time, bounded by a deadline). The RPCs are `AppendEntries`, `Vote`, `InstallSnapshot`, and `Submit`. Two transports exist: the in-process `Router` used by tests, which models partitions, and the TLS transport below. A snapshot is the whole control state as JSON and is sent in OpenRaft's chunks; installing one for another vault fails.

### Members without a vote (Phase 6b, stop 1)

A member is a voter or a device enrolled without a vote. `ProposeChange(Enroll)` carries `votes`: absent or true, the device becomes a voter as described above; false, it stays a Raft learner. Such a member is sent the log, given every epoch key, synced with, and may sign requests like a voter; it counts toward no majority, so a phone that is off or out of reach never holds up a change. An enrollment without a vote is signed under tag 6 instead of 2, with the same fields after it, so neither kind passes for the other. It is stored with `"votes":false`; a voting enrollment is stored without the field, exactly as before, so every earlier log entry and every frozen vector reads and is written back unchanged. The control state lists the members without a vote under `without_vote`, which is absent while there are none, so a state from before writes back as it was.

The rules change in four places. A device is enrolled if it is a voter, or a member without a vote that is in the membership as a learner, and in both cases an author under the key the membership records for it and not removed; Raft membership entries, which carry no signature, still give no authority or key by themselves. After genesis a request is accepted from any enrolled member, voting or not (before it, as before, only from a voter). A removal's rotation must have exactly one envelope per remaining enrolled member, voting or not. A change is in effect, so that its completion is accepted, when the committed membership is uniform with the target voters and, for a member without a vote, when that device is in the membership on joining and gone from it on removal. The leader adds a member without a vote as a learner, waits until it has caught up, and completes the enrollment without `change_membership`; it removes one with `ChangeMembers::RemoveNodes`, and never removes the learners that are members without a vote when it clears stale ones. `crates/vault-membership/fixtures/without-vote.json` freezes the new enrollment's signed bytes and stored text and a state holding such a member.

### Rotation and enrollment coupling (Phase 4, milestone 3)

`osm_vault_peer::control` couples a vault to committed state. Request IDs are SHA-256 of `osm-control-request-id-v1` plus NUL, the vault ID, the length-prefixed kind, and its subject (the joiner's device ID; the removed device and new epoch; the granted device and epochs), truncated to 16 bytes, so a retry after an unknown outcome is recognized instead of producing a second rotation or grant. `found` initializes a one-voter cluster and commits genesis from the vault's epoch keys and authors. `removal_request` generates the next epoch key, seals it to every other voter, records its check, and discards it: every remaining device, including the requester, installs it from its own envelope only after the removal completes, so no device holds a key for an epoch that was never committed. `grant_requests` seals the epochs a settled voter lacks; any unlocked member may submit them.

`reconcile(vault, state)` is idempotent and is run whenever applied state changes and right after unlock, before staged revisions are processed or anything is written. If committed membership removed this device it reports that and changes nothing. Otherwise it raises the write fence to the committed epoch, which works while locked and is all it does then. Unlocked, it authorizes every committed author (a known device with a different key is a protocol violation), revokes every removed device, checks every epoch key it holds against the committed check (`EpochKeyMismatch` on a difference), opens each envelope sealed to it, checks and installs the key, activates the committed epoch once it holds it, applies held revisions whose authors are now authorized, and, on the device that removed another, endorses that device's remaining heads. A member that has applied a removal's completion is fenced until it holds the new key; one that has not yet learned of it can still write under the old epoch.

Enrollment through pairing: after the owner confirms the short code, `approve_enrollment` consumes the invitation token and returns the signed `Enroll` proposal and an `EnrollmentGrant` (version 1, vault ID, the proposal's request ID, the recovery check, the vault's members from the inviter's committed state, each with device ID, TLS pin, and optional address, the port the inviter accepts member connections on, and the inviter's pairing signature over `enrollment-grant` plus NUL, the transcript, and those fields, with the member list and each address length-prefixed). The inviter submits the proposal and sends the grant only if it is accepted; otherwise it tells the joiner the enrollment was refused. The joiner runs its control-plane node from the start, under the device ID from `Joiner::control_device`. It has no log to tell it whose connections to accept, and the leader need not be the inviter, so `Joiner::members` verifies the grant, requires the inviter's entry to carry the pin from the invitation, and returns the members for the joiner to accept and to announce itself to (below). The leader brings it up to date as a learner and makes it a voter, and a member then grants it every epoch key. `Joiner::finish_enrollment` verifies the grant against the invitation's key, requires that committed state records this device as a settled voter and author with the keys and pin it sent, opens every envelope sealed to it with the recipient key derived from its pending secret, checks each against the committed check, and creates its vault with the committed epoch, authors, and removed devices; it fails with `EnrollmentPending` until then. A joiner that never catches up can be dropped with `CancelEnrollment`; it never received a key.

A device that already holds a copy of the vault, paired before vaults had a control plane, joins under the identity it has (`Joiner::start_with_vault`). The invitation must be for its vault. Its join request carries its existing device ID, signing key, and recipient key, signed by the vault; genesis listed it as an author, and an enrollment of an author is accepted only under the same key. It then becomes a voter like any joiner, and `Joiner::finish_in_place` verifies the grant, requires that committed state records it as an enrolled voter with those keys and its pin, and reconciles its vault: the keys it holds are checked against the committed checks and nothing is created or replaced. One of the two devices founds the control plane and the other joins it; both keep their vaults.

### Member transport (Phase 4, milestone 4, stages 1 and 2)

`osm_vault_peer::MemberEndpoint` is one device's end of the connections between a vault's devices, over the same TLS 1.3 settings as pairing: mandatory client certificates, pins in both directions, no resumption. One listener serves two channels, the control plane's RPCs and revision sync, chosen by the first frame.

**Whose certificate is accepted.** The server decides at every handshake, from the node's `Directory`: the devices its own log names (the nodes of the committed membership, of the latest membership in the log, and of a pending, uncancelled enrollment), plus devices a member introduced, minus every removed device. The pin is mapped back to a device ID, and a pin that two accepted devices share maps to neither. A client dials only the pin that membership records for its target. A removed device's certificate also completes the handshake, but only so that its `Open` can be answered with `Removed`; nothing it sends is taken in.

**Introductions.** A device's own log does not always name the current members: a device still being enrolled has no log, and one that was away while another joined does not know the newcomer, which may now lead. Such a device accepts pins on a member's word until its log names them: from the signed enrollment grant, and from the roster on a connection to or from a device that its own committed state lists as a member. A roster holds only what its sender's committed state lists as enrolled voters, never what the sender was itself told. What the log records wins: an introduction neither replaces a recorded device's pin nor claims a recorded pin for another device, and it never admits a removed device. At most 256 are kept, in memory.

**Member.** For rosters and for sync, a member is a device that the receiver's committed state lists as an enrolled voter, not removed, and not the subject of a pending removal. This holds while another device's change is under way.

**Opening exchange.** After the handshake the client sends `Open` (postcard, in a frame as for sync): protocol version 2, vault ID, channel (`Control` or `Sync`), the port it accepts member connections on, if any, and its roster of at most 64 entries (device ID, TLS pin, optional address of at most 128 bytes). Since 2026-10-13 a roster names each other member once, at the address its sender tries first, and the sender itself once for each of up to four of its own addresses, best first (`MemberEndpoint::own_addresses`: those an invitation would name, from its network interfaces with the port it listens on, read again for each connection), as many as fit after the others; a sender that names none, as one that does not listen, is named once without an address. The form, version 2, and `members.json` are unchanged, and a build from before reads such a roster as it reads any, taking in each address as a member's report. The signed enrollment grant still names each member once. The server answers `Welcome` with its own roster, or closes after `UnsupportedVersion`, `VaultMismatch`, `NotAMember` (the sync channel, from a device that is not a member), or `Removed`. The opening exchange has a 10-second timeout. `MemberEndpoint::announce` opens a control connection only for this exchange.

**Addresses.** Each device keeps up to eight addresses for each other device, best first, in the `device_addresses` table of its peer store file (`AddressBook::open`; since Phase 16, layout 3 of the peer store; before, one address per device in `member_addresses`, which is moved over when the store is opened): the source address of an authenticated incoming connection with the port from its `Open` (an IPv4 address that a listener for both families sees in its IPv6 form is recorded as IPv4), an address it connected to successfully, one from a believed roster, or, on a joiner, each address its invitation named for the inviter with the port from the grant. An address reached, or seen as a connection's source, goes first; one reported or named is added after those that work and before those that failed, and never pushes out one that works; one that failed goes last. Since 2026-10-13 the addresses a believed roster's sender names for itself, that is, the entries with the pin the connection authenticated, are taken as its own (`AddressBook::claim`): only an IP address with a port, at most four, they go right after the address the device was just reached or seen at (or first, if that one failed), in their order, and push out older ones when the device has eight, so that a device whose addresses change, as an IPv6 address replaced each day does, is not shut out by the ones it had; nothing is written when they are in place already. An entry naming the receiver itself is not kept: a device knows its own addresses. Since 2026-10-14 nor is one naming a removed device, and whenever a device's committed state changes it forgets every address of the devices that state records as removed, which are never dialled again, and any it kept for itself, as builds before 2026-10-13 did (`MemberEndpoint::forget_departed`, on the desktop and the phones). So a device learns where another can be reached when that one's addresses change, or a VPN gives it one more, at their next connection, with no new invitation. A device dials a member at all of its addresses in that order, each 300 milliseconds after the one before unless that one has failed already, and keeps the first connection that answers. Addresses are advisory; the pin authenticates whatever answers.

**Control channel.** Each frame is then one RPC and its reply, in turn: the 4-byte length and a JSON body, the encoding the log is stored in, at most 24 MiB. The receiver looks the pin up again before every RPC, so a device removed while its connection is open loses it, and passes the RPC to the node under that device ID. A reply is `Refused` when the RPC claims a sender other than the connection's device, or passes on a request another device signed. A connection without an RPC for 120 seconds is closed. The client makes its connection when first needed, in a task of its own so that a deadline on one RPC does not abandon a handshake, and drops it after any failed or abandoned exchange.

**Sync channel.** Both ends require the other to be a member by their own committed state: the client before dialing, with the pin from that state, and the server before answering `Welcome`. The connection then carries a sync session as described under the implemented protocol below, `Hello` included. Before the session starts, each end reconciles its vault with its committed control state (`MemberSync::run_shared`), so received revisions are judged against the current authors and removals; a device whose state says it was removed exchanges nothing. A session takes the vault for one message at a time (`SharedVault`), never while it waits for the peer, so two devices that dial each other at the same moment both finish, and the application keeps using the vault in between.

**Removal notice.** The entry that completes a removal is appended after the membership no longer includes the removed device, so that device may never receive it. It learns of its removal when it next connects to a member: the `Removed` answer, which `MemberEndpoint::told_removed` then reports. A device believes this from any member it dialed by pin.

**Serving.** An accept loop (`serve_members`) completes handshakes concurrently, serves control connections itself, and hands sync connections to the application, which runs them against the vault. It serves at most 64 connections at once, handshakes included, and closes them when it stops.

**Relay (since Phase 16).** A relay the owner runs (`osm-relay <folder> <listen-addr> <public-addr>`) joins two devices that cannot reach each other, and passes their bytes without reading them (`crates/vault-peer/src/relay.rs`). It has a TLS identity of its own, kept in its folder in a peer store file (`relay.sqlite3`, the key unsealed), and a random 32-byte token (`token`, in hex, readable by its owner only), both made on its first run. It prints its code: `OSM-RELAY1-` and the unpadded base64url of a postcard body: version 1, the relay's public address as `host:port` (at most 128 bytes), the SHA-256 pin of its certificate, and the token; a code is read only in that one form. Each connection to the relay opens with one byte: `C` for a device's lasting connection, `J` for a connection to be joined. On a `C` connection the device runs TLS 1.3 with the relay's pin and presents its own member certificate, then sends `Register` (version 1, the token); the relay answers `Registered`, or `Refused` and closes when the token or the version is not its own or 64 devices are registered already. The device is then registered under its certificate's pin, the newest connection of a pin replacing an older one. Over it the device sends `Dial` (a request number, the pin of the device it wants) and `Ping` every 30 seconds; the relay answers `Ticket` (the request number and a random 32-byte ticket), `Absent` when no device is registered under that pin, and `Pong`, and sends the asked-for device `Incoming` with a ticket of its own. Every message is postcard in a frame of at most 256 bytes. A relay ends a device's connection after 90 seconds without a message; a device whose connection ends tries again after 5 seconds. Each end then opens a `J` connection with its 32-byte ticket, in the clear; the relay joins the two connections whose tickets it paired and passes bytes both ways until either closes. A ticket is used once and is void after 10 seconds; at most 256 tickets and waiting connections, and 512 connections in all, are kept. Over the joined connection the two devices run the member TLS and opening exchange as over any other, so the relay sees TLS records only. A device dials a member at its addresses first, and through its relay as well when they have not answered within a second, keeping whichever connects first; a connection that came through the relay is served like one on the listener, except that its source, the relay, is not recorded as the device's address. **In the apps** (stop 4): the owner pastes the relay's code in the desktop's Devices panel (`set_relay`), which keeps it in the vault (below); whenever a device's vault is unlocked, after an unlock, a change of membership, or a sync, the device brings its relay in line with the vault's and keeps a copy of the code in its peer store, in a `relay` table (one row, the code as text, unsealed; added within layout 3, which a build without it leaves alone), and starts, changes, or stops its use of the relay to match. When its control plane starts, locked or not, a device uses the relay its peer store names. The desktop's Devices panel shows the relay's address and whether this device is connected to it now; the phones show nothing of it.

**Development CLI.** `osm-peer device` runs one device: its node, listener, a loop that reconciles the vault, then processes staged revisions, and submits key grants whenever applied state changes, and commands on stdin to found, invite, add, list, sync, remove, and report status. `osm-peer device-locked` runs the same device without its password, as an app that is open but locked. `osm-peer join-device` pairs through the enrollment path and then runs as `device` does. Since Phase 16 a device also takes `unlisten`, which stops its member listener, and `relay <code>`, which keeps the relay's code in the vault and uses the relay; `add` takes a title of several words. `osm-relay` (above) is the relay.

**Desktop app.** The app keeps `control.sqlite3` (the node's database) beside the vault and the peer store. It runs the node and listener whenever it is open and the vault has a control plane, locked or not. Creating a vault founds the control plane; a vault from before, never paired, is founded at its next unlock; a vault paired by an older build waits for the owner to choose which device founds it. On every change of applied state, and at unlock before anything staged is processed, it reconciles the vault, then processes staged revisions and submits key grants if unlocked. A joining device runs its node from the moment it shows the short code, keeps its pending identity in memory until it is enrolled, and discards its control database if the join is abandoned. A device that learns it was removed, from its own committed state or from a member's `Removed` answer, writes an empty `removed` file beside the vault, since its own log may never record the removal, and is then reset at once: the app stops its node and moves the vault file first, then the control database, peer store, invitation store, and the marker, into an `archive-<time>` folder. That leaves a device without a vault, which joins again as a new device with a new transport certificate. A `reset-after-removal` file names the archive folder until the device has a vault again, so the app can say what happened. The owner can have a device's copy put away in the same way without a removal (`leave_vault`, which takes the device's password), for a device whose vault was replaced by a recovery on another device; a `left-vault` file then names the archive folder. Before any file is moved, a `putting-away` file records the reason (`removed` or `left`) and the archive folder on two lines, and it is deleted once the note is written; at launch, before the vault or its stores are opened, a `putting-away` file that names a folder beside the vault with an archive folder's name (`archive-<time>`), a folder and not a link, has its move finished, and any other is deleted (since Phase 13; before, any folder beside the vault, or a link to one elsewhere, was taken). If the app stops between the marker and the reset, the next launch finishes the reset; while the marker exists the app runs no node, founds nothing, and refuses to sync.

An `archive-<time>` folder holds a complete copy as it was: the vault file, its control-plane database, its peer and invitation stores. The desktop app lists these folders (the name is `archive-` and the time in seconds, with `-<n>` after it when two were made in one second; nothing else is listed, opened, or deleted, and a link in that place is not followed). The owner opens one with the password the copy had; the app then reads its items, and says for each whether the vault on this device holds it, holds it with other content, or does not hold it. Copying an item writes a new item with a new ID into the current vault, with ` (archived copy)` after the title when the vault already has an item of that ID; nothing is written to the archived copy's revisions, though opening its file can create SQLite's sidecar files and would apply a format upgrade as opening any vault does. Deleting removes the folder and everything in it, and a note that names it.

## Pairing and sync messages

An invitation needs a version, invitation ID, random single-use secret, expiry, inviter identity/pin, vault identity, and candidate connection addresses. Address discovery is advisory. Invitation redemption persists the one-use decision before reporting success and binds both endpoint keys to the confirmed transcript.

Frame messages with an explicit bounded length and request ID. Negotiate only supported protocol versions without silently falling back to weaker authentication. Summaries, lists of revision IDs, revision batches, missing-parent requests, and acknowledgments expose ciphertext metadata only. Acknowledgments distinguish durable receipt from validated acceptance. Limit message size, revisions per batch, total pending bytes, concurrent peers, and processing time.

The receiver deduplicates before enqueueing where safe, authenticates metadata before accepting it, and stores unknown ancestry or unavailable epochs as pending. Synchronization resumes from persisted state after a crash. Arrival order and duplicate batches must yield the same accepted heads.

### Implemented protocol (Phase 3, with Phase 4 enrollment)

`osm-vault-peer` implements pairing and sync as sans-IO steps and carries them over TLS 1.3 on TCP. There is no discovery or NAT traversal: the invitation names the inviter's addresses, and members reach each other at the addresses in their address books (above). Since Phase 16 the apps listen over IPv6 and IPv4 alike (`osm_vault_peer::listen`), and an invitation names up to four of the inviter's addresses (`local_addresses`): the one its route to the internet leaves from over IPv4, then over IPv6, then those of its other interfaces, IPv4 first, leaving out loopback, link-local, and multicast addresses, those in 192.0.0.0/24 (a phone's IPv4 through 464XLAT, which no other device reaches), and the interfaces that join a computer to its own virtual machines and containers (`docker`, `br-`, `virbr`, `veth`, `bridge`, `vmnet`). So a device on the owner's VPN, or with a global IPv6 address another device can reach, is reached there from anywhere.

Pairing is owner-confirmed, and the owner's confirmation becomes an enrollment proposal to the vault's control plane (above), so any number of devices can join. Until Phase 4 milestone 4 the confirmation itself was the enrollment authority, for at most one paired peer; that path is removed. A peer store written then may still name that one device (`PeerStore::legacy_peers`), which is read only to offer the move onto the control plane. The invitation text is `OSM-PAIR1-` plus base64url of a postcard body: version 1, vault ID, inviter device ID and Ed25519 public key, the inviter's TLS certificate pin, up to four advisory addresses, a 32-byte one-use token, and an expiry of at most 15 minutes. The token is stored only as a hash, SHA-256 of `osm-invitation-token-v1` (without a NUL) and the token (`InvitationStore::issue_pairing`), binds to the first device that redeems it, and is consumed before the joiner is authorized. The desktop shows an invitation for a device without a vote as a QR code too (`apps/desktop/src-tauri/src/qr.rs`): the same text in byte mode at error correction level M, 65 to 85 modules a side for two to four addresses, inside a border of four, drawn as inline SVG (the window's content security policy loads no `data:` image). The phones read it with the camera, through ZXing on Android and AVFoundation on iOS, and take only a text beginning `OSM-PAIR1-`, as if pasted.

The joiner creates its own device identity (`PendingDevice`), including the recipient secret its HPKE key pair is derived from and which its vault keeps, and sends a request that also names its TLS certificate pin, signed with the new device key over `join-request` plus NUL and the transcript. Both sides hash a transcript: `osm-pairing-transcript-v1` plus NUL, vault ID, inviter device ID, key, and TLS pin, SHA-256 of `osm-pairing-token-v1` plus NUL and the token, joiner device ID, key, HPKE key, and TLS pin, so the short code also confirms both transport identities. The short code both screens show is the first four bytes of SHA-256 of `osm-pairing-sas-v1` plus NUL and the transcript, read as a big-endian number and reduced modulo 1,000,000, shown as six digits in two groups of three. The inviter checks the token without consuming it (`InvitationStore::check`) and the request signature before the owner is asked. After the owner confirms, the inviter proposes the enrollment and answers with the enrollment grant, `Declined` if the owner declined, or `Refused` if the vault's devices did not accept the proposal. The inviter's root key and recovery wrapper are never sent, and epoch keys reach the joiner only as envelopes in committed control state once it is a voter; the joiner wraps them under a new root key of its own and starts with recovery off. Pairing signatures prefix `osm-pairing-signature-v1` plus NUL so they cannot be confused with revision signatures. The joiner verifies the grant against the key from the invitation, requires the owner's confirmation, and calls `Vault::join`, which creates its vault with its own password and identity; no other device's password wrapper ever leaves it.

Transport identity is separate from the revision signing key: each device has a self-signed Ed25519 certificate generated with rcgen and stored in its peer store, which is created with owner-only permissions. The TLS private key is not encrypted under the vault's keys, because a locked device must still be able to receive ciphertext; revision authenticity never depends on it. Since Phase 14 it is sealed by the system's keystore instead (layout 2 of the peer store, table `transport_key`), so that the peer store's file alone, in a backup or copied to another computer, does not give it: each sealing makes a 256-bit key of its own in the keystore under a random 16-byte name, and what the file holds is a form byte (1), that name, a nonce, and the key sealed under it, with the text `osm transport key`, the form byte, and the name bound to it. On the desktop the keystore's key is a generic password (service `org.opensecretmanager.transport-key`, account the name in hex) in the login Keychain on macOS or the Secret Service on Linux, and the sealing is XChaCha20-Poly1305 with a 24-byte nonce; on Android it is an AES key in the Android Keystore (alias `org.opensecretmanager.transport-key.` and the name in hex) that never leaves it, usable without the owner's authentication and while the phone is locked, and the sealing is AES-GCM inside the Keystore with its 12-byte nonce; on iOS it is a generic password like the desktop's, in the app group's access group, readable after the first unlock and on this phone only, and the sealing is AES-GCM with a 12-byte nonce. A key is stored sealed only once the keystore has opened it again to the same key. Where no keystore answers, as on a Linux computer without a Secret Service, the key is kept unsealed as before, and sealed the next time the store is opened with a keystore that answers; the desktop's Devices panel says which. A layout 1 store, or a layout 2 store whose key was kept unsealed, is moved over when it is opened (not when the vault is unlocked, which the key does not wait for): the row is copied into `transport_key`, the old table dropped, and the key sealed, with SQLite's `secure_delete` on so that the pages the unsealed key was on are overwritten in the file. A sealed key the keystore no longer holds is reported as lost, and the device makes no new identity in its place: it has to be removed from the vault and joined again. Peers pin the SHA-256 of each other's certificate and ignore names, validity periods, and system roots; the handshake signature still proves possession of the pinned certificate's key. Only TLS 1.3 is offered, client certificates are mandatory, and session resumption is disabled so every connection checks both certificates. During pairing the inviter accepts any client certificate and then requires that the signed join request names exactly the certificate on the connection; the joiner pins the inviter from the invitation. Connections that fail before the owner is asked are dropped and the inviter keeps listening until the invitation window closes. Sync runs only between members, over the member transport (above). Reads and writes run concurrently, each frame has a 60-second timeout, and connects and handshakes have 10-second timeouts.

Frames are a 4-byte big-endian length and a postcard body, at most 24 MiB; the declared length is checked before the body is buffered, the body is kept as it arrives rather than allocated at its declared length, and trailing bytes are rejected. Since Phase 13 a body is read only in its one form: it must be exactly what the message it decodes to is written as, so a number written in more bytes than it needs (which postcard alone accepts) is refused, here and in an invitation's text. Before a peer is known to be a member, the bound is 64 KiB: the join request, the answer to it, and the opening exchange between members are each a few kilobytes. The pairing listener takes one connection at a time and gives a join request 10 seconds after the handshake. **Since 2026-10-13 sync is version 2**, and version 1 is no longer spoken: a device of either version refuses the other's session by the version in its `Hello`, which has the same form in both, and the error says to update both devices. A sync session opens with `Hello` (protocol version 2, vault ID, and the port this device accepts sync connections on, if any, which the receiver does not use: between members, addresses come from the opening exchange) and a `Summary`: for each of 256 buckets, bucket b holding the IDs of the revisions this device holds (accepted, staged, or held for review) whose first byte is b, SHA-256 of the label `osm-sync-bucket-v2` and a zero byte, then the bucket's IDs in ascending order. Revision IDs travel as their 32 bytes. Where the digests of a bucket differ, each side sends its IDs in those buckets, in ascending order, in `Ids` messages of 8,192 IDs, the last holding fewer (an empty one when the count is a whole number of 8,192s); where none differ, each side answers at once with `Done`. Each side compares the peer's IDs with its own as they arrive and, after the last chunk, answers with the stored revisions the peer lacks, parents first (in the order it stored them), in `Revisions` batches of at most 64 revisions or 8 MiB (a larger revision goes alone), then `Done`. Staged and held revisions count as held, so nothing already received is sent again, and they are never sent. Revisions are the core's signed `EncryptedRevision`s. Every received revision is staged first (durable receipt); if the vault is unlocked the session then processes the queue (validated acceptance): unknown authors are quarantined, and any other invalid revision is discarded and ends the session. A locked device receives and stages only, and can still send its stored revisions. After `Done` the receiver sends `Need` for parents of staged revisions that it has neither accepted nor staged, nor asked for before, at most 65,536 in a round, for at most 8 rounds. A side takes the peer's `Summary` once, after its `Hello`, with exactly 256 digests; its `Ids` only after that and only when a bucket differs, ascending across chunks, each in a bucket that differs, at most 2^24 in all, and none after the last chunk; anything else only once all its IDs have come; its `Need` in at most 8 rounds; and its `Done` at most once more than it has itself sent `Need`. Anything beyond is a protocol violation that ends the session, so a peer cannot have the vault sent again and again. `Finished` means a side needs nothing more. A session started while unlocked processes anything staged earlier, once its own `Hello` and `Summary` have gone out. The session reads the peer's frames in a task of its own and sends its next message whenever there is room, reading a batch of revisions from the vault only then: it never waits to send while the peer's frames wait to be read, and it holds at most two frames each way. It ends when no byte has moved either way for 60 seconds, however long one frame takes to arrive. A session that fails still sends what it had queued, and reads what arrives, for up to 2 seconds, so that the peer reads its `Hello`. An interrupted session is resumed by starting another: summaries recompute what is missing, and staged revisions survive restarts. Two devices that hold the same send `Hello`, a summary of about 8 KB, `Done`, and `Finished` each way; when one revision is new, each sends the IDs of one bucket, about N/256 of them for a vault of N revisions. **Version 1** sent every ID, as 64 hex digits, in one `Inventory`. A vault of 387,167 revisions or more could not fit it in a frame and so synced with no device; every session sent it whole both ways; a frame had to arrive within 60 seconds; and the session waited to send while the peer's frames went unread, so two devices that each had more than 16 batches for the other both waited until the session timed out, every time. Each of these was reproduced in a test before the change.

## Backups and recovery

The public backup contract must freeze a magic value, format version, vault identity, cryptographic suite, KDF or recovery-wrapper descriptor, nonce, authenticated manifest, and encrypted payload. Authenticate the manifest and key wrappers. The payload contains a consistent database snapshot or equivalent complete encrypted records and required key material. Copying only the SQLite main file while a WAL transaction is outstanding is not a valid snapshot procedure.

**Files appear whole.** The core writes a new vault (made, restored, joined, or forked) and a backup under the name with `.partial` added, beside its place, and moves it there only once it is complete; a file already at that place is never replaced, and a `.partial` file a crash left is replaced by the next attempt. Until Phase 6a stop 2 a vault was written in place, so a process killed while making one left a file that could neither be opened nor made again. Recovery uses a high-entropy secret independent of the local unlock password. A restore API authenticates before writing and takes a new destination and new local password. It must not overwrite an existing vault by default. Live rejoin creates a fresh device identity; restoring an old signing identity into two writers risks cloned identity and counter reuse.

### Implemented recovery fork (Phase 4, milestone 4)

When too many of a vault's devices are lost for the rest to remove them, no membership change can commit, by design. `Vault::fork` starts a new trust domain from one surviving device instead. The new vault has a new random vault ID, device identity, root key, epoch 1 key, recipient secret, and recovery key, and its only authorized author is the new identity. Every live version of every item is sealed again under the new vault ID and epoch key and signed by the new identity, with no parents: an item with several live versions stays a conflict. Each version keeps the time it was saved, if it has one. Earlier history, deletions, held revisions, and unverified received revisions are not carried; an unresolved choice between an edit and a deletion keeps the edit. The source vault is not modified. Because the vault ID is inside every revision's authenticated header and every control request's signature, nothing signed or sealed in one domain verifies in the other.

The desktop app does this as one confirmed action that asks for the vault password again, which also becomes the new vault's password. It first takes in the committed state and received revisions it already has, stops its control-plane node, and writes the new vault to `recovered.sqlite3.partial`, renamed to `recovered.sqlite3` once complete. It then moves the old vault file, control database, peer store, and invitation store into a new `archive-<time>` folder beside them, the vault file last, and renames the new vault into place; at launch a leftover partial file is deleted and a leftover complete one finishes the swap. The new vault gets a new transport certificate and an empty address book, and the app founds its control plane with this device as the only member. The other devices are not members of the new vault: on each, the owner has its copy put away (see the removed-device reset under the member transport) and it joins by pairing, and a device of the old domain that reappears can neither connect nor be believed. The old vault's membership is not changed by any of this.

The implemented import (Bitwarden JSON, Chrome CSV, Firefox CSV) takes at most 128 MiB and 100,000 entries. A refusal says where the file stopped being an export (a line and column, or a record and field) and never quotes it, since what it would quote can be a password. A row whose name is blank is given a title from its address, its user name, or its row number. A Bitwarden card's or identity's fields become the item's other fields, named for people since Phase 9 (`cardholderName` as Cardholder name, `expMonth` as Expiry month, `code` as Security code, `firstName` as First name, and so on); a field it does not know keeps the export's name. Since Phase 18 a Bitwarden login's passkeys (`fido2Credentials`) come in with it: a P-256 key (`keyAlgorithm` ECDSA, `keyCurve` P-256, `keyValue` PKCS #8 in base64url), its credential ID a GUID, taken as its 16 bytes in the order written, or `b64.` and the bytes in base64url, its counter and creation date as text; one of another kind of key, or for a site no passkey may be for, and any beyond 32 on a login, is counted in a warning on its row, never left out without a word. Plaintext export is a separate deliberate format and action. Import accepts bounded input with a schema/version, produces row-level preview errors, and commits atomically or clearly reports partial behavior. Vendor adapters must map origin, username, password, note, and TOTP fields without silently discarding unknown material.

### Backups, restores, and password resets in the desktop app (Phase 6a, stop 5)

The app writes the backup above (version 4) to a file the owner names in the system's save dialog, by default `Open Secret Manager backup <date>.osmbackup` in the Documents folder; the extension is only a name, and the file is the JSON envelope. Right after writing it, the device reads it back with its own root key (`Vault::check_backup`): the envelope must be of this vault, carry this device's recovery wrapper exactly, and authenticate and parse; it reports how many items, revisions, and held revisions it holds. A file already at the chosen place is never replaced. The window never names a path: the commands open the dialogs themselves, and the file chosen for a restore stays in the app.

Restoring is offered only on a device without a vault, and is refused while a vault file that cannot be opened lies at the vault's place; the owner has that put away first, into an `archive-<time>` folder with the files that belong to it. The backup is restored, under the owner's new password, into a new `archive-<time>/vault.sqlite3`: a copy with the backup's identity and its whole history, which the Archive dialog opens with the new password and which the old recovery key also opens. From that copy the app makes the new vault with `Vault::fork`, as the recovery fork does: a new vault ID, new keys, and a new recovery key, the live versions of every item, conflicts kept as conflicts, and held revisions left in the copy. It goes through `recovered.sqlite3.partial` and `recovered.sqlite3` like the recovery fork, so an interruption after the new vault is complete is finished at the next launch, and one before it leaves only the archive folder. This device then founds the new vault's control plane alone, and other devices join by pairing. The restored copy never founds or joins a control plane, so restoring does not give a live control plane a second vault with its identity, as the rule above requires.

For a forgotten password, `Vault::reset_password` unlocks with the recovery key and wraps the root key under the new password with a new salt, in one step; the old password no longer opens that device, and the other devices keep theirs. It needs recovery turned on on that device and changes nothing if the key is wrong.

## TOTP and browser integration

TOTP stores the decoded secret, supported hash algorithm, digit count, and positive time step inside record ciphertext. Validate standard test vectors, explicit time input, and time-step boundaries according to [RFC 6238](https://datatracker.ietf.org/doc/html/rfc6238). An `otpauth` import must reject malformed Base32 and unsupported parameters rather than guessing.

Native messaging uses browser-defined 32-bit native-endian length-prefixed UTF-8 JSON. The implementation may impose a smaller documented limit than the browser. Reserve stdout for framed protocol responses; diagnostics go to stderr without secrets. Extension identity is explicitly allowlisted during installation, as described by [Chrome's native messaging documentation](https://developer.chrome.com/docs/extensions/develop/concepts/native-messaging).

A fill is asked for by the extension and decided in the desktop app. The request is `{version, request_id, tab_id, frame_id, document_id, origin}`; it names no record, because the owner chooses the login in the app and the extension never receives a list of vault items. The desktop session releases a login only after that choice, in the unlock it was made under. The response is bound to the same request and HTTPS origin. No protocol message accepts a master password. A missing desktop session returns unavailable.

### Implemented fill protocol (Phase 5, stop 1)

Implemented: the origin rule, the messages, the native host, the desktop session's end, the desktop app that serves it, and the extension (both below).

**Origin.** `osm-origin` is the one implementation, used by the core, the host, and the session. `Origin::of_url` gives the origin of an address stored with a login: the scheme must be `https`, there must be no user name or password, the path, query, and fragment are ignored, the host is taken as the URL standard serializes it (lower case, an international name in its ASCII form), and a missing port is 443. `Origin::parse` reads an origin from a message and accepts it only if it is already exactly that serialization, such as `https://example.com` or `https://example.com:8443`: a trailing slash, upper case, a written default port, or anything else that merely resembles an origin is refused. Two origins match only if host and port are equal. `https://example.com.` (trailing dot) is a different origin from `https://example.com`, as it is to a browser. An address without a scheme, such as `example.com`, has no origin, and its login is never offered. Redirects are not a concern of this rule: the extension reports the origin of the document it will fill.

**Messages.** Every message is a JSON object of at most 64 KiB with a `type`, and field names in camelCase. A message with an unknown field is refused. The extension sends:

| `type` | Fields | Rules |
| --- | --- | --- |
| `fill_request` | `version`, `requestId`, `tabId`, `frameId`, `documentId`, `origin` | `version` is 1. `requestId` and `documentId` are 1 to 64 ASCII letters, digits, or hyphens. `tabId` is not negative. `frameId` is 0: only the page itself is filled. `origin` must pass `Origin::parse`. |
| `cancel` | `version`, `requestId` | Withdraws a request that is waiting. Nothing is answered if none is. |
| `card_request` (since Phase 17) | `version`, `requestId`, `tabId`, `topOrigin`, `frames` | `version` is 2: a card's request came later, and an app that does not know it refuses it as `unsupported_message` or `unsupported_version`, while a login's request stays at 1 for good, as the extension updates apart from the app. `topOrigin` is the page's origin, from the tab. `frames` names 1 to 8 documents of the tab, each once by `frameId`: `{frameId, documentId, origin, fields}`, where `origin` is the document's own, passing `Origin::parse` (the page itself, frame 0, must have the page's), and `fields` names what its card fields ask for, each once and at least one, of `number`, `cardholder`, `expiry` (month and year in one field), `expiry_month`, `expiry_year`, and `security_code`. A frame of another origin than the page's is refused with `frame_rejected` only as frame 0. |
| `passkey_create`, `passkey_get` (since Phase 18, stop 6) | `version`, `requestId`, `tabId`, `origin`, `options` | `version` is 2, as for a card's. A page's call of `navigator.credentials.create` or `get` for a passkey, made in the page itself (frame 0). `origin` is the page's, as the browser reported it to the extension, and must pass `Origin::parse`. `options` is the call's options as WebAuthn's JSON (`PublicKeyCredentialCreationOptionsJSON` or `PublicKeyCredentialRequestOptionsJSON`), as text of 1 to 32 KiB, which the desktop session reads (see Which sites a passkey is for): one it does not answer is refused as `passkey_refused`. |

The extension receives:

| `type` | Fields | Meaning |
| --- | --- | --- |
| `waiting` | `requestId` | The desktop session has the request and the owner has not decided. Sent at once and then every 20 seconds. |
| `fill_reply` | `requestId`, `tabId`, `frameId`, `documentId`, `origin`, `username`, `password` | The owner's choice. The first five repeat the request. |
| `error` | `requestId` (or `null`), `code` | The request ended without a login. |
| `passkey_reply` (since Phase 18, stop 6) | `requestId`, `tabId`, `origin`, `credential` | What the page's call returns. The first three repeat the request. `credential` is the credential as WebAuthn's JSON (`RegistrationResponseJSON` or `AuthenticationResponseJSON`, see What a passkey sends), as text; it holds no secret. |
| `card_reply` (since Phase 17) | `requestId`, `tabId`, `topOrigin`, `frames`, `card` | The owner's card. The first four repeat the request exactly. `card` is `{cardholder, number, expiryMonth, expiryYear, securityCode}`: the number's digits only, and a value only for a field some document asked for (the month and year for `expiry` too), the others empty. |

`code` is one of `invalid_message`, `unsupported_message`, `unsupported_version`, `extension_not_allowed`, `origin_rejected`, `frame_rejected`, `desktop_session_unavailable`, `busy` (another request is waiting), `replayed` (the request ID was used before), `denied`, `cancelled`, and `expired`, and since Phase 18, stop 6, for a passkey's request, `no_passkey` (the vault holds none the site takes), `passkey_refused` (a request the app does not answer), `passkey_exists` (the vault holds a passkey the site says it has for the account), and `use_browser` (the owner chose the browser's own passkeys). A request ID that is not of the allowed form is not repeated in the answer. `messages-2-passkeys.json` holds the passkey's messages as frozen.

**Native host.** Frames on standard input and output carry the browser's native-endian length. A length of zero or above the limit, or input that ends inside a frame, ends the host with a failure status and no answer. The browser names the calling extension on the host's command line: a Chromium browser passes the extension's origin, `chrome-extension://<id>/`, and Firefox passes the path of the host's manifest and then the add-on ID. The host passes a request on only if that names the allowed extension: ID `hjgekjgkjnakgmiopldddikdkcjhnmge` in Chromium, which follows from the `key` in `manifest.chromium.json`, or `extension@opensecretmanager.org` in Firefox. Otherwise the answer is `extension_not_allowed` and no connection is made. The private half of that key was not kept; an extension published through a store has another ID, and the constant changes with it. The host holds at most four requests open and refuses a request ID that is already open.

**Socket.** The desktop session listens on the Unix socket `browser.sock` in the app's data folder (`OpenSecretManager` in the account's data folder), with mode 0600. The host connects only if that path is a socket owned by the account it runs as; the session answers only a connection from the account it runs as. Frames carry a big-endian 32-bit length and the same 64 KiB limit. Each connection carries one request: the host sends `{caller: {browser, extension}, request}`, where `browser` is `chromium` or `firefox` and `request` is the `fill_request` without its `type`, or, since Phase 17, `{caller, card}` with the `card_request` without its `type`. The session answers with the `waiting`, `fill_reply` (or `card_reply`), and `error` messages above and closes after the first that is not `waiting`. Closing the connection withdraws the request, and so does sending anything more on it. The host hands a response to the extension only if it parses and answers the request it forwarded: the same request ID, for a `fill_reply` the same tab, frame, document, and origin, and for a `card_reply` the same tab, page, and documents with the same fields; a login's reply never answers a card's request, nor the reverse. Anything else, a closed connection, or 60 seconds of silence becomes `desktop_session_unavailable`. A socket path longer than the operating system allows (about 104 bytes) cannot be bound.

**Desktop session.** `osm-vault-browser` checks the caller and the request again, since any program of the account can reach the socket. One request waits at a time; it ends after 120 seconds without a decision. The IDs of the last 1024 requests taken in are refused. `Desk::choices` gives what the owner is asked: the origin, the kind of browser, and, if the vault is unlocked, the logins from `Vault::logins_for_origin` together with `Vault::unlock_session`, 16 random bytes that name the current unlock and exist only in memory. `Desk::approve` takes the request, the chosen item, and that session. It releases the item's user name and password only if the vault is still in that unlock, the request is still the one waiting, and `Vault::credentials_for_origin` accepts the item for the request's origin, which it does only for a login whose address has exactly that origin. A locked vault, or one that was locked and unlocked again, refuses the choice and leaves the request waiting. A request can arrive while the vault is locked and waits for the unlock. Since Phase 17 a card's request waits the same way, one at a time with a login's: `Choices` then has, as `card`, the documents it names and every card of the vault but those in conflict (none while locked), and `Desk::approve_card` releases a card's fields under the same conditions, if the item is a card not in conflict, and only the fields some document asks for; `approve` refuses a card's request and `approve_card` a login's. `osm-fill` prints a card's request with its documents and cards, takes `approve-card`, and adds a card with `add-card`.

**A passkey's request (since Phase 18, stop 6).** The host forwards `{caller, ceremony, passkey}`, where `ceremony` is `create` or `get` and `passkey` the request without its `type`, and hands back only a `passkey_reply` that repeats its request, tab, and origin, or an `error` that names it. The session reads the site's options before it takes the request in, with the page's origin and the rule for pages, and refuses one it does not answer as `passkey_refused`. A sign-in that the unlocked vault holds no passkey for is refused as `no_passkey` at once, before the owner is asked anything, so the browser's own passkeys answer it without the app coming forward; the app tells the session so through `Desk::answer_sign_ins_with`, which only reads the vault, and a vault that is locked, or in use at that moment, cannot say. A page's request waits as any does, but a login's or a card's request, which the owner started, takes its place: the page's is then refused as `busy`. The owner's choice: `Desk::approve_passkey_create(request, session, vault, into, verified)` makes the passkey, saves it on the login `into` or on a new login (see A login's passkeys), and answers with the registration; a site that has one of the vault's passkeys for the account, by its `excludeCredentials`, is answered `passkey_exists` instead, only now. `Desk::approve_passkey_get(request, session, vault, item, credential, verified)` signs, for a passkey the site takes. The client data in either is made by the session for the page's origin (`crossOrigin` false). `verified` says the owner was verified in this request; a site that requires it gets nothing without it. `Desk::use_browser` answers `use_browser`.

`osm-fill` is a development stand-in for the app: it opens a vault, serves the socket, and plays the owner from command-line options or commands on standard input.

### Desktop app and host manifests (Phase 5, stop 2)

The app binds the socket when it starts and serves it until it exits. If the socket is already served, by another copy of the app on the same data folder, this copy does not listen and says so in its Browser panel. A socket left behind by a copy that is gone is replaced.

The window learns of a request through the event `fill-request`, sent whenever a request arrives, ends, or is decided, and reads it with the command `fill_request`. That returns nothing, or `{requestId, origin, browser, secondsLeft, session, logins, notOffered, card}`; `card`, for a card's request (since Phase 17), is `{documents, cards}`: each document as `{origin, page, fields}` (`page` for the page itself), and each card as `{id, title, brand, ending}`, the last four digits of its number and nothing more of it. `passkey`, for a passkey's request (since Phase 18, stop 6), is `{ceremony, rpId, rpName, userName, userDisplayName, verification, passkeys, logins, ownerCheck}`: to sign in, the site's passkeys as `{itemId, title, credentialId, userName, userDisplayName}`, never a key; for a new one, the logins of the site it may go on; `ownerCheck` says the computer can check the owner itself. `approve_passkey(requestId, session, into, itemId, credentialId, password, ownerCheck)` answers it: when the site asks to verify the owner, the owner is verified then, by the system when `ownerCheck` (on macOS through LocalAuthentication, `LAPolicyDeviceOwnerAuthentication`: Touch ID or the Mac's own password, in `osm-desktop-session`), or by this device's vault password, checked as an unlock checks it (`Vault::check_password`) and not kept; it fails with `not_verified` or `wrong_password` otherwise. `use_browser_passkey(requestId)` leaves it to the browser. `approve_card(requestId, itemId, session)` answers it as `approve_fill` answers a login's; a login refused there is `not_a_card`. `session` is `Vault::unlock_session` as 32 hexadecimal digits, or null while the vault is locked or missing, in which case `logins` is empty. Each of `logins` is `{id, title, username, url, conflict}`; no password crosses to the window. `notOffered` names logins that cannot be chosen but whose address would have the page's origin if `https://` were put in front of it (`no_scheme`) or in place of `http://` (`not_https`), so that the app can say what to change; it is computed outside the origin rule and decides nothing. `approve_fill(requestId, itemId, session)` hands the owner's choice to `Desk::approve` and fails with `locked`, `fill_ended`, or `not_for_this_page`. `deny_fill(requestId)` turns the request down.

When a request arrives the app unhides, shows, and focuses its window. Whether an app in the background may take the front is the operating system's decision; if the window was behind, the app also asks for attention, which on macOS makes its icon signal until the owner comes or the request ends. After the owner fills or denies a request that the window came forward for, the app hides (on macOS) or minimizes, so that the browser is in front again. The rule that a covered window locks the vault is unchanged, so the vault locks at that point.

`browser_status` reports whether the app is listening, where the host program is, whether that place lasts (`temporaryPlace`, below), and each known browser whose own folder exists under the home folder: for Firefox on Linux, `.mozilla/firefox` or, since Phase 9, `.config/mozilla/firefox`, where Firefox makes a new profile now (seen with Firefox 157); its manifest stays in `.mozilla/native-messaging-hosts`, the only one of the two places where Firefox 157 found a host. `connect_browser(id)` writes the host's manifest, `org.opensecretmanager.native.json`, into that browser's folder, replacing a file of that name; `disconnect_browser(id)` removes it. The manifest is `{name, description, path, type: "stdio"}` with `allowed_origins: ["chrome-extension://hjgekjgkjnakgmiopldddikdkcjhnmge/", "chrome-extension://pnjdoenkfffomcidikbkcegcpgipdjog/"]` for a Chromium browser (the extension loaded unpacked and the Chrome Web Store's copy, since 2026-11-16) or `allowed_extensions: ["extension@opensecretmanager.org"]` for Firefox, and `path` is the absolute path of the host program. A browser is `connected` only if the file is exactly that; any other content is reported as `other`. The folders, relative to the home folder:

| Browser | macOS | Linux |
| --- | --- | --- |
| Google Chrome | `Library/Application Support/Google/Chrome/NativeMessagingHosts` | `.config/google-chrome/NativeMessagingHosts` |
| Chromium | `Library/Application Support/Chromium/NativeMessagingHosts` | `.config/chromium/NativeMessagingHosts` |
| Brave | `Library/Application Support/BraveSoftware/Brave-Browser/NativeMessagingHosts` | `.config/BraveSoftware/Brave-Browser/NativeMessagingHosts` |
| Microsoft Edge | `Library/Application Support/Microsoft Edge/NativeMessagingHosts` | `.config/microsoft-edge/NativeMessagingHosts` |
| Firefox | `Library/Application Support/Mozilla/NativeMessagingHosts` | `.mozilla/native-messaging-hosts` |

The host program is `osm-native-host` beside the app's own program. A development build also looks where the repository's workspace builds it. On a system without Unix sockets the commands exist and report that filling into a browser is unavailable.

**Packaging (Phase 5 close-out).** `npm run tauri:build` in `apps/desktop` packages the app with the host inside it. It adds `src-tauri/tauri.bundle.conf.json` to the app's configuration, which does two things: before the app is compiled, `scripts/host.mjs` builds `osm-native-host` in release mode from the repository's workspace and copies it to `src-tauri/binaries/osm-native-host-<target>`; and the packaging tool takes that file as an external program, which puts it beside the app's own program: `Contents/MacOS/osm-native-host` in a macOS app. The copy in `binaries/` is not kept in the repository. The app's main configuration does not name the host, because it would then have to be built before every check and test of the app; so a plain `tauri build` packages no host, and such an app says in its Browser panel that it found none.

The app does not point a browser at a host whose path has a folder named `AppTranslocation` or one whose name begins with `.mount_`. macOS runs an app that was downloaded and not moved since from a copy in a folder of the first kind, and an AppImage runs from a folder of the second kind; both are gone when the app quits, and a manifest naming them would name nothing afterwards. `browser_status` then has `temporaryPlace: true`, `connect_browser` fails with `temporary_place`, and the panel says to install the app first. This is a rule on the path only.

### Extension (Phase 5, stop 3)

One source builds an extension for Chromium and one for Firefox (`dist/chromium`, `dist/firefox`), each with its manifest. Both ask for `activeTab`, `scripting`, and `nativeMessaging`, and for nothing else: no host permissions, no content script declared for any page, no storage. Since Phase 18, stop 6, both may also be given access to all `https` sites (`optional_host_permissions: ["https://*/*"]`, not `<all_urls>`, which would also take plain http pages and the computer's own files, a second switch in Firefox), only by the owner, on the extension's options page (below); Firefox's minimum is then 128. The Chromium manifest's `key` gives the extension the ID the host allows.

The extension acts on a press of its toolbar button (or the keyboard shortcut the owner may assign to it), which is what gives it access to that one tab:

1. The tab's address, from the browser, must be an `https` address without a user name or password; its origin is what is asked for. Otherwise the press ends with an explanation.
2. A script is put into the tab's top document (frame 0) and connected to. It answers with a name for the document, 1 to 64 letters, digits, or hyphens, made at random when the script first ran there; the document's own origin (`self.origin`), which must equal the tab's; and which of a user name field and a password field it found. With no field found, nothing is asked. A document its site serves sandboxed (`Content-Security-Policy: sandbox`) has the site's address but an opaque origin, `null`: it is refused, and nothing is asked (since 2026-10-21; until then the script reported the origin of its address).
3. The `fill_request` goes to the host with a request ID made at random, the tab ID, frame 0, that document name, and the origin.
4. A `waiting` response updates the button. An `error` ends the request. A `fill_reply` is taken once: the request stops waiting before anything else happens, so a repeated reply meets no request. It is filled only if it names the same request, tab, frame, document, and origin, and only if the browser, asked again, says the tab still shows a page of that origin and still shows that document. For the second, the script leaves its document's name in the extension's own scope of that document, and the extension reads it back through the browser from whatever document the tab shows now; a document loaded since has none.
5. The script fills the fields it found when asked, if they are still in the document, by setting each value and sending `input` and `change` events. It sends no key events and does not submit. It fills once per request and only if the document name and origin it is handed are its own.

The connection to the script closes when its document goes away, and the script closes it itself when its page is left (`pagehide`), because Firefox can keep a document it has left, connection included, for the Back button; it usually does and sometimes does not. That ends the request: the extension sends `cancel` to the host and drops any reply that comes later. A document that was left is not filled even if the browser shows it again. The extension itself gives up after 150 seconds. When no request waits, it closes its connection to the host, which ends the host's process.

The script looks for the login form in the form of the field that has the focus, and otherwise in the whole document: the first visible password field, and the last visible text, email, or telephone field before it; or, with no password field, the focused field of those kinds or one whose `autocomplete`, `name`, or `id` names a user name or email. It does not look inside shadow roots or frames.

**Cards (since Phase 17, stop 3).** A press now puts the script into every document of the tab the extension may reach (`allFrames`): with activeTab, that is the page itself and the frames of its origin; a frame of another origin, as a payment provider's, is not reached (a browser that refuses the whole call is asked for the page itself alone). Each script answers as above and, besides, with its card fields: those whose `autocomplete` says `cc-number`, `cc-name`, `cc-exp`, `cc-exp-month`, `cc-exp-year`, or `cc-csc`, or, when it says nothing else (only `on`, `off`, `shipping`, `billing`, or a section), whose name, id, placeholder, label, or `aria-label` names one, as the Android app reads a field's names; inputs of the kinds text, telephone, number, password, and search, and lists (`select`), only if enabled, not read-only, drawn with a size, visible, and not transparent. A document of a sandboxed or non-https origin has none. When one of the documents has a field for the number, the press is a card's request, naming each document with card fields (at most eight), its own origin as its script reports it, and its fields; otherwise a login form in the page itself is a login's request as before; otherwise the press ends with the reason, one of them that a card's number is in a frame of another site, which the extension cannot reach. A `card_reply` is taken once and filled only if it answers the request exactly, the tab still shows a page of the page's origin, and each document named is still the one asked for; each document's script is then handed only the values of its own fields. It fills the number whole into one field or in turn over several, each taking as many digits as its `maxlength` says (four where it says none, the last the rest); the month as two digits; the year in two digits into a field of two and in four otherwise; an expiry in one field as `MMYY`, `MMYYYY`, or `MM/YYYY` for a field of 4, 6, or 7 characters (`MM/YYYY` for a placeholder that says `YYYY`), and `MM/YY` otherwise; and in a list the option whose value or text is the value, or whose first number is the month or the year. It sends `input` and `change` events, no keys, and does not submit. A frame of another origin is reached once the owner gives the extension access to all sites (Phase 18, stop 6).

**Passkeys (since Phase 18, stop 6).** The options page (`options.html`) has one switch: "Take part in sign-ins with passkeys, and fill card fields in a payment provider's frame". Turning it on asks the browser for access to all sites, which the browser asks the owner about; turning it off gives the access back. While the extension has that access, the background keeps two scripts registered (`scripting.registerContentScripts`), for every `https` page, in the page itself only, at the document's start: `passkey-page.js` in the page's own world, and `passkey-bridge.js` in the extension's. Without the access they are not registered and nothing runs in pages. The access also lets a press reach a card form's frames of other sites.

`passkey-page.js` replaces `navigator.credentials.create` and `get` (on `CredentialsContainer.prototype`, named and shaped as the browser's). A call goes on to the browser's own unless it asks for a passkey only (`publicKey`, with nothing but `signal` and a `mediation` of `optional` or `required` beside it; a `conditional` one, for a form's list, is the browser's), in the page itself, of an `https` page whose document's origin is its address's. It writes the options as WebAuthn's JSON (`creationJSON`, `requestJSON` in `passkey.ts`: the fields the app reads, binary values in base64url; extensions are not passed) and posts `{channel: "osm-passkey", type: "ask", id, kind, options, timeout}` to its own window and origin; an aborted `signal` posts `withdraw`. The answer, `{channel, type: "answer", id, outcome}`, ends the call: with a credential made from the credential's JSON, an object on `PublicKeyCredential.prototype` whose `id`, `rawId`, `type`, `authenticatorAttachment`, `response`, `getClientExtensionResults`, and `toJSON` are its own, its response on `AuthenticatorAttestationResponse.prototype` (with `getTransports`, `getAuthenticatorData`, `getPublicKey`, `getPublicKeyAlgorithm`) or `AuthenticatorAssertionResponse.prototype`; with an error of `NotAllowedError`, `InvalidStateError`, or `AbortError`; or by going on to the browser's own, once the page has the focus back if the app's window took it. The script holds no secret and decides nothing.

`passkey-bridge.js` takes only messages whose source is the page's own window and whose origin is the document's, and answers only to that origin. A call made without the owner's activation (`navigator.userActivation.isActive`, read in the extension's world), or with options above 32 KiB, is answered at once with the browser's own. Each request is handed to the background over a connection of its own (`runtime.connect`, named `passkey`), which the browser ties to the document; the page's `pagehide` closes them all, and the document going closes them too.

The background takes a passkey's connection only from the page itself (frame 0), with the origin the browser reports for its sender (`sender.origin`, or the origin of `sender.url` where the browser does not give it), which must not be `null` and must equal the origin of the sender's address and of the tab's. One request per tab, and none from an origin for a minute after the owner denied one of its requests or let one run out. The request goes to the host as `passkey_create` or `passkey_get`, and the extension gives up after the page's own limit, kept between 10 seconds and 2 minutes. The connection closing withdraws it (`cancel`). A `passkey_reply` that answers it, while the tab still shows a page of its origin, ends the call with the credential; `denied` and `expired` end it with `NotAllowedError`, `passkey_exists` with `InvalidStateError`, a withdrawal with `AbortError`, and every other refusal, an app that does not answer, and a host that is not there, by going on to the browser's own (`use_browser` and `busy` once the page has the focus back). A press of the button on a tab whose page's request waits takes its place, as in the session.

What the button says: `…` while the request waits, `✓` after a fill, `!` when nothing was filled, with the reason in its title. The button's icon and the extension's are the desktop app's icon at 16, 32, 48, and 128 pixels (`icons/`), drawn from it by `node icons.mjs` and kept in the repository.

The Firefox manifest differs from the Chromium one in three places: the background is a script rather than a service worker, `browser_specific_settings.gecko.id` gives the ID the host allows, and `action.default_area` puts the button in the toolbar. Firefox reports why a native connection closed on the connection itself (`port.error`), Chromium beside it (`runtime.lastError`); the extension reads both.

## Phone interface (Phase 6b, stop 2)

`crates/mobile` (`osm-mobile`) is what the phone apps call. It is built as a static and a dynamic library, and UniFFI 0.32 generates its Kotlin bindings (package `org.opensecretmanager.vault`, loaded through JNA) and Swift bindings (module `OSMVault`, with the C header and module map `OSMVaultFFI`) from the library itself, with the names in `crates/mobile/uniffi.toml`. The bindings are generated at build time and not committed; their shape is fixed by the Rust declarations.

The interface is one object, `Device`, opened on a folder of the app's own, which holds what the desktop keeps beside its vault under the same names: `vault.sqlite3`, `peers.sqlite3` (transport identity and address book), `control.sqlite3`, once the device has learned it was removed, a `removed` marker, and since 2026-11-04 `app-logins.json`, the logins the owner chose for each app on this phone only: a JSON object from each app's key to the IDs of its logins, holding no secret, not synced, written whole (to `app-logins.json.partial`, then renamed); a file missing or of another form is taken for none and replaced at the next choice, and an ID no longer in the vault is passed over. Every call blocks until done; the apps make them off their main thread. `state` is one of no vault, joining, locked, unlocked, and removed. `unlock` and `lock`; `change_password` (since 2026-10-12), while unlocked, takes the current password and a new one of at least 12 characters, and refuses a wrong current one as invalid credentials, changing nothing; `items` (summaries without secrets), `item` (a detail with whether it has a password and a one-time code and, since Phase 10, the names of its other fields in the vault's order, not the secrets), and `password`, `one_time_code`, and `field` (since Phase 10: the value of one other field by name, `NoSuchField` for a name the item lacks), which return a secret for copying. `join_start` takes an invitation and returns the code to compare; `join_finish` takes the new device password (at least 12 characters), waits up to two minutes for the vault's devices to enroll the device, and makes its vault unlocked. The inviting device decides whether the phone votes; the desktop app asks. `go_online` runs the device's control-plane node and accepts members on port 47820 (or any free port), as the desktop does, and announces it; `go_offline` stops both. While online the device keeps its vault in line with committed membership, verifies what arrived while locked once unlocked, gives members the keys they lack, and syncs every 60 seconds and on `sync_now`. `sync_in_background` (Phase 8) goes online if the device is not, waits for any sync under way, syncs, waits again, and goes offline again if it was; it never unlocks. `sync_status` says whether it is offline, idle, syncing, synced, in error, or removed, how many members it knows an address for, when a sync last finished, and how many received changes wait for an unlock. Errors are named: locked, invalid credentials, not found, no vault, vault exists, unreadable vault (with the reason), not joining, password too short, not confirmed, enrollment timeout, removed, invalid invitation, no one-time code, invalid origin, not for this page, not a login, and network or storage with a reason; since 2026-11-04 also not chosen (a login not chosen for the app that asks), not for this form (a save into a login the form could not be filled with), and invalid requester.

For writing (Phase 7, stop 1), `create_item`, `update_item`, and `delete_item` take an `ItemDraft` (title, kind, username, website, notes, favorite, and a password and a one-time code secret that are kept when absent and removed when empty; its debug form prints only the kind), and an edit or a deletion names the revision `item` returned, so that one made from an older reading is refused. They write logins and secure notes only, and since Phase 17 cards: a draft's `card` (`CardDraft`: cardholder, expiry month and year as given, and a brand, a number, and a security code of which `None` keeps what the card has; a brand of `None` with a number given is the one the number names) writes a card's fields as above, and `item` gives a card's as `CardDetail` (cardholder, expiry, brand, the number's last four digits, and whether a number and a security code are set), its other fields' names leaving the card's out; `check_card_number` tells the editors a number's brand and whether it passes the check, for a warning; errors are added for an invalid item (with the reason), an item changed since it was read, an item in conflict, and a kind edited on a computer. `generate_password` makes a password with the shared generator, given since Phase 19 a `PasswordOptions` (length, the four kinds, and whether to leave out look-alikes, as the generator above takes them), and `default_password_options` gives the shared code's choice. A write starts a sync at once while the device is online. For an edit refused as changed elsewhere, `rebase_edit` (Phase 12) takes the revision the edit was read at and the draft, and returns a `RebasedEdit`: the draft put on top of the item as it is now (each field the draft changed from that version keeps the draft's value, the others take the current one, and a password or one-time code secret the draft leaves stays absent, so no secret of the item enters it), the revision to save it at, and the names of the fields changed since. It writes nothing; a version the item never had is not found, and an item in conflict is refused.

Both apps show an item's other fields (a card's number and security code, an identity's name and address, a login's own extra fields) by name after its website, each masked with a Copy that puts the value on the clipboard as a secret, cleared after 30 seconds, as the desktop's item page does; an identity is still edited only on a computer (Phase 10, stop 2). Since Phase 17 a card is shown as a card: its cardholder, its number by its last four digits, its expiry, its security code masked, and its brand, and the list names it by its brand and those four digits; both apps edit it, and restore its versions.

Since Phase 10, `rows_changed` says whether an unlock found rows taken out of the vault file or changed in it (see the row seal above), false while locked, and `confirm_rows_changed` stops saying so; both apps show it at the top of the list until the owner confirms. The desktop has the same pair as commands, `rows_changed` and `confirm_rows_changed`, and shows it in a card above the recovery key's. The phones say "Something in this vault's file was taken out or changed"; the desktop, which since 2026-10-14 also sets the flag for a file set back to an earlier copy (see Rows seen) and, when the owner confirms, takes the file as it is, says "Something in this vault's file was taken out, changed, or set back". Each names what such records are and points to the next sync.

For autofill (Phase 6b, stop 4; since 2026-11-04 decided in one module, `crates/mobile/src/fill.rs`) the phone names who asks as a `Requester`: `Page` with the origins its system vouches for, each `https://host` or `https://host:port` exactly as a browser serializes it (anything else is an invalid origin, and no origin at all an invalid requester); `App` with a key the phone makes from what the system says of the app (on Android `<package>:<original certificate SHA-256>`, with `:<claimed domain>` after it when the app said it shows a page; on iOS the App ID; an empty key is an invalid requester) and the domains its links were verified for (Android 12 and later; none on iOS); or `Unnamed`. What a form asks for is `Asks`: `Login`, `OneTimeCode`, or `LoginAndOneTimeCode`. `offer` returns an `Offer`: for a page, the logins whose address has one of its origins, by the rule the desktop's browser fill uses (HTTPS, the exact host, the exact port); for an app, the logins chosen for it and, apart (`suggested`), those not chosen whose address is https on port 443 and on a verified domain (taken without `*.`, `www.`, or a trailing dot) or a host under one; for no one named, none; for a code alone, only logins with a one-time code secret. `fill` returns what fills the form, a `Filled` of a username and password (`FillCredentials`) and a current one-time code, each only if asked (their Rust debug forms print neither; the Kotlin and Swift records they become would print both, and the apps log nothing): for a page only a login of its origins (refused as not for this page), for an app only one chosen for it (`NotChosen`), for no one named nothing (`NotChosen`). A code goes only where its login would; a form that asks for the password too is filled without one when the login has none, and one that asks for a code alone is refused (no one-time code). `fill_chosen` is the same for a login the owner chose on the phone's own screen just now: any login for an app, which is then remembered for it, or for no one named, which is not; a page still gets only its origins' logins. `logins_to_choose` lists every login (with a code secret, for a code alone) for the owner to choose from. Each refuses an item that is not a login.

For saving what a form sent (Phase 7, stop 4), `save_candidates_for` takes the requester and the username and password the form sent, and returns the logins the form could be filled with (for a page its origins', for an app those chosen for it, for no one named none) that are not in conflict and have that username (every one, if the form sent none; usernames are compared without surrounding spaces), each as a `SaveCandidate`: ID, title, username, the revision it was read at, and whether it has that password already. `update_saved` changes only a login's password, from the revision named, refusing an empty password (invalid item), an item that is not a login, one in conflict, one that is not such a candidate for that requester and username (`NotForThisForm`), and an older reading. `save_new` makes a login of the title, username, and password given: for a page, saved for its first origin; for an app, with no address, and remembered for it; for no one named, with no address. Like any write, each starts a sync at once while the device is online.

For history (Phase 8, stop 3), `history` lists an item's versions newest first as `HistoryEntry` records (revision, whether it deleted the item, is current, made the item, or settled a conflict; the title, username, and website it held, or for a deletion those of the version before; the fields it changed by name; the first eight hex digits of the device that made it, and whether that is this device); `deleted_items` lists `DeletedEntry` records (the item's ID, title, kind, username, and website before the deletion, the version a restore brings back, the deletions it follows, and who deleted it); `restore` brings back a version of a login or secure note, refused for an identity (and until Phase 17 for a card), for an item in conflict, for a deletion, and from an older reading. A restore starts a sync at once while online.

One-time codes in autofill (Phase 7, stop 5) are offered and filled by `offer` and `fill` above. For the owner's own screens, and for iOS's text insertion, `one_time_code` gives a login's current code, as `password` and `field` give its other secrets, whoever asks.

### The Android app (Phase 6b, stop 3)

The app (`apps/mobile/android/app`, `org.opensecretmanager.app`, Android 9 and later, 64-bit ARM only) keeps the device's files in its private `files/vault` folder. Background sync (since Phase 8) is the WorkManager job `background-sync`, periodic at 15 minutes, needing a network and a battery that is not low, which calls the phone interface's `sync_in_background`; it is on unless the private preferences file `settings` has `background-sync` set to false. How long the vault stays unlocked once the app is left is `stay-unlocked-minutes` there: 0, 1, 5, or 15, and 1 if it is not set. Since Phase 19 the generator's choice is there too, once the owner changes it: `generator-length` (8 to 64), and the booleans `generator-lowercase`, `generator-uppercase`, `generator-digits`, `generator-symbols`, and `generator-avoid-look-alike`; a choice with no kind, or a length out of range, is the shared code's default. Unlocking with a fingerprint keeps the device's password in the app's private preferences file `biometric-unlock`: the password encrypted with AES-256-GCM (`ciphertext`) and its nonce (`iv`), each as base64. The key is the Android keystore key `device-password`, made in the phone's secure hardware for encryption and decryption with GCM, usable only after a strong biometric check for each use, and invalidated when a biometric is enrolled. Turning it off, or a key found invalidated, deletes both. The app allows no backup and no device-to-device transfer of any of its data. A secret it copies is marked sensitive (`EXTRA_IS_SENSITIVE`, or its name on Android 12 and earlier) and is cleared from the clipboard after 30 seconds: unless something else was copied since, which only an app in front can tell, so an app in the background clears it regardless.

### Android autofill (Phase 6b, stop 4)

The app is an Android autofill service (`.autofill.VaultAutofillService`, declared with `android.permission.BIND_AUTOFILL_SERVICE` and `res/xml/autofill_service.xml`, which sets `supportsInlineSuggestions` since 2026-10-13), active once the owner picks it in the phone's settings. For a screen with a password field or a one-time code field (an autofill hint `2faAppOTPCode`, or `one-time-code` in a page's `autocomplete`; a code field is never taken for the password or the username) it answers, while the vault is locked, with one dataset whose values are empty and which needs authentication, presented as "Open Secret Manager · unlock to fill" (each entry is the app's own `res/layout/autofill_entry`, with colours of its own). While the vault is unlocked it answers instead with one such dataset for each login a fill would offer there, at most 10, presented as the login's title and username, and one more, presented as "Open Secret Manager…", or as saying that a page has no login, or to choose a login for an app, which opens the fill screen as before. When the keyboard asks for the entries in its strip (Android 11 and later, `FillRequest.getInlineSuggestionsRequest`), each dataset, up to the number the keyboard asks for, also has an inline presentation in the keyboard's spec for its place, made with `androidx.autofill`'s `InlineSuggestionUi` version 1 (none for a spec of another style): the app's icon, untinted, and a short title, "Unlock to fill", the login's title with its username beside it, "Open Secret Manager…", "Choose a login…", "No login for this site" or "No code for this site"; long pressed, it opens the app. The logins are then at most one fewer than the keyboard's number, so that the last entry fits. Either way it asks for a save (`SaveInfo` of type password, plus username when the screen has a username field, which is then optional; the password field required, since Phase 19 the first new password field when the form has one; flag `FLAG_SAVE_ON_ALL_VIEWS_INVISIBLE`, so that a form hidden rather than closed counts as sent). Since Phase 19, a form with new password fields (an autofill hint `newPassword`, or `new-password` in a page's `autocomplete`; or else two or more password fields that hide what is typed, are drawn with a size, and are not numbers', less one hinted `current-password` or named current, old, 현재, or 기존, or the first of three) gets first, locked or not, a dataset presented as "Open Secret Manager · make a strong password" ("Make a strong password" in the strip, the logins then two fewer than the keyboard's number), with empty values for the username field and the new password fields, needing authentication, which opens `.autofill.GenerateActivity` with the form's extras, its new password fields and the fewest characters any of them takes (`maxlength`, else the field's `maxTextLength`) among them. That screen saves the password made where the owner chooses, as the save screen does, and returns a dataset with it in each new password field, and the username given in the username field. Choosing it opens the fill screen (`.autofill.FillActivity`, not exported) with the screen's package, the first web domain that is not empty and its scheme, as reported, and the IDs of the username, password, and code fields, in the intent's extras, and for a login in the list its ID (`item`). Given a login's ID while the vault is unlocked, the fill screen fills it without showing anything. The fill screen returns a dataset with the login's username and password (the username left out when the login has none) and, for a code field, the login's current code as `EXTRA_AUTHENTICATION_RESULT`, which the system fills at once.

When the owner chooses Save in the system's offer, the service reads the username and password fields of the form's last screen and keeps them, with the form, in the app's memory (`PendingSave`, which holds only the latest save, until its screen closes); it answers with an intent sender for the save screen (`.autofill.SaveActivity`, not exported), whose intent carries only the save's number. A form without a password is answered with a failure. A new login saved there has the title the owner confirms, the username, the password, and for a trusted browser's page the website `https://<domain>`; one saved for an app has no website and is added to the logins chosen for that app, below.

The app's manifest declares that it sees the apps that have a launcher activity (`<queries>` with the intent `MAIN` in category `LAUNCHER`): without that, Android 11 and later hide other apps' packages and certificates from it.

Who asks is decided there. A page counts as a page of `https://<domain>` only when its scheme is `https` and the app showing it is on the trusted list with a signing certificate the installed app has; Android reports a page's host and scheme but not its port, so the origin never has one. Every other request is an app's, known by its package and the SHA-256 of its original signing certificate, plus the domain it claims to show, if any.

The trusted list is `res/raw/trusted_browsers.json`, made by `apps/mobile/android/trusted-browsers.mjs` from the list Google publishes of the apps a password manager may trust to report a page's origin (`https://www.gstatic.com/gpm-passkeys-privileged-apps/apps.json`): an object with `about`, `source`, `fetched` (the date), and `apps`, each with `package` and `sha256`, the SHA-256 of each release signing certificate in upper-case hex without separators. Only release certificates are kept. The list of 2026-10-03 has 66 apps, as has that of 2026-10-21; it changes only when the script is run again and the change committed. Since Phase 18, stop 5, the script writes the same apps in Google's own form beside it, `res/raw/privileged_browsers.json`, which the passkey provider hands to Android's Credential Manager library (see Android passkeys): `{"apps": [{"type": "android", "info": {"package_name", "signatures": [{"build": "release", "cert_fingerprint_sha256"}]}}]}`, each fingerprint in upper-case hex pairs joined by colons.

**Card forms (since Phase 17, stop 2).** A screen with a field for a card's number is a card form (`autofill/CardForm.kt`). Its fields are found by what they say to autofill (the hints `creditCardNumber`, `creditCardExpirationDate`, `creditCardExpirationMonth`, `creditCardExpirationYear`, and `creditCardSecurityCode`; a page's `autocomplete` of `cc-number`, `cc-name`, `cc-exp`, `cc-exp-month`, `cc-exp-year`, and `cc-csc`), or, when a field says nothing, or only `on` or `off`, by its names as for a login's fields (card number, 카드번호, expiry or 유효기간 with month or 월 and year or 년, CVC, CVV, 보안코드, cardholder, name on card); a field that says it is something else is not a card's. Only fields of the types text, list, and date, drawn with a size, in views that are all shown, count. A card form is answered when the screen has no login form, or when one of its fields has the focus. Its offers are as a login's, "Open Secret Manager · unlock to fill a card" while locked and, while unlocked, every card by its title, brand, and the last four digits of its number, each opening the card fill screen (`.autofill.CardFillActivity`, not exported), whose intent carries the form's fields and, for a card chosen in the list, its ID; nothing is offered to save. The values: the number's digits, whole in one field or in turn over several, each taking as many as its maximum length says (four where it says none, the last the rest); the month as two digits; the year in two digits for a field that takes two and in four otherwise; an expiry in one text field as `MMYY`, `MMYYYY`, or `MM/YYYY` for a field of 4, 6, or 7 characters and `MM/YY` otherwise, and in a date field as the first of the month; and a list's choice whose first number is the month, or the year in four digits or two. A list whose choices the app does not tell autofill (a list made in code: Android tells only choices from an app's resources) is left as it is. The phone interface lists the cards a card form is offered, every card not in conflict, as `offer_cards`, and gives a card's fields as `fill_card` (`CardFill`: cardholder, the number's digits, expiry month and year, and security code; its debug form prints none), refused for an item that is not a card (`NotACard`) and for a card in conflict.

The logins the owner chose for an app are kept by the shared code (since 2026-11-04) in `app-logins.json` in the device's folder (see the phone interface above), under the app's key, `<package>:<certificate SHA-256>` or `<package>:<certificate SHA-256>:<claimed domain>` when the app said it shows a page. Before, the app kept them in its private preferences file `app-logins`, under the same keys, as sets of item IDs; the first time the device opens, the app hands them to the shared code (`import_app_choices`) and then empties that file. The file is not backed up, like the rest of the app's data.

### Android passkeys (Phase 18, stop 5)

From Android 14 on, the app is a provider for Android's Credential Manager, for passkeys only: passwords stay with autofill. The provider is `.passkey.PasskeyProviderService`, declared with `android.permission.BIND_CREDENTIAL_PROVIDER_SERVICE`, the action `android.service.credentials.CredentialProviderService`, and `android.credentials.provider` pointing to `res/xml/passkey_provider.xml`, whose one capability is `androidx.credentials.TYPE_PUBLIC_KEY_CREDENTIAL` and whose settings are the app's own screens (`settingsActivity` the main activity, `settingsSubtitle` "Passkeys"). It and its screen, `.passkey.PasskeyActivity`, are enabled by `@bool/provides_passkeys`, true only in `values-v34`. It is built on `androidx.credentials:credentials` 1.6.0 alone, never its Google Play services part. The owner turns it on as the phone's service for passwords, passkeys, and autofill, which on Android 14 and later picks the autofill service of the same app too.

Asked to make a passkey, it offers one place, "Your vault", described "On all your devices with Open Secret Manager", whether the vault is locked or not, so the asking app learns nothing of the vault. Asked for one, it offers, while the vault is locked, only "Unlock Open Secret Manager", and while it is unlocked an entry for each passkey the vault holds for the site that asks (of those it names, if it names any), by the account's name and, when it differs, the name the site shows; it waits for the vault at most 3 seconds, as for autofill, and offers the unlock after that. A request it does not answer, by the check below (`check_passkey_request` in the interface, which needs no vault), gets nothing from it, and the system offers the other providers; so does a request from this app itself. Each entry opens the screen with a `PendingIntent` that is mutable, so the system can add the request, not one-shot, and of a request code of its own, the actions `org.opensecretmanager.app.passkey.CREATE`, `GET` (with the extras `item` and `credential`, the passkey chosen), and `UNLOCK`.

Who asks is decided from what Android says of the calling app. A page's origin is believed only when the calling app gave one and the library's `CallingAppInfo.getOrigin` finds the app, by its package and signing certificate as installed, in `privileged_browsers.json`; then the client data hash the browser gave is what is signed, and the response's `clientDataJSON` is the placeholder `{}`, as Android's guide for providers says, since the browser sends the site its own (a browser that gave no hash has its client data made for the page's origin). An app that gave an origin but is not on the list is offered nothing. Any other app is itself: its origin is `android:apk-key-hash:` and the base64url SHA-256 of its current signing certificate, as WebAuthn and Android's guide have it; its client data is made with that origin, and a hash it gave is ignored. A page's RP ID follows the rule for pages (see Which sites a passkey is for); an app's is only checked to be one a passkey may be for, and the first time an app asks for a site's passkeys the screen says it is an app, not a browser, and whether Android verified that the site names it as its own (the app's verified links, as for logins), and goes on only when the owner chooses. That choice is kept in the app's private preferences file `passkey-apps`: under the key `<package>:<original certificate SHA-256>`, a set of RP IDs. Saving a passkey for an app counts as that choice.

The screen unlocks the vault if it is locked, names who asks, and for a new passkey asks where it goes: a new login, titled with the RP ID, its username the account's name and its address `https://<RP ID>`, or one of the logins of that site (whose address is on it or under it, and not in conflict). The passkey is made only then, and a request that excludes a passkey the vault holds is refused then (InvalidStateError), not before. The owner is verified as the site asks: the vault unlocked on that screen verifies the owner; otherwise the phone's own check does (`BiometricPrompt`, a strong biometric or the screen lock), each time, unless the site discourages it. A site that prefers it on a phone without a screen lock gets an answer without verification; one that requires it is refused (NotAllowedError), and the interface refuses to make or sign without verification for such a site whatever the app says. A sign-in chosen in the system's list from an unlocked vault draws nothing but that check; if the vault locked since the list, the screen unlocks it first, which verifies the owner. A conditional create, which a browser makes without asking, is refused (NotAllowedError). The site is told why an answer is refused as a WebAuthn error: a request this app does not read is a DataError, a site no passkey may be for a SecurityError, a site that takes no ES256 key NotSupportedError; the owner's cancel is a cancellation; anything else is an unknown error.

The interface (Phase 6b, stop 2) gains `PasskeyCaller` (`Page {origin, client_data_hash}`, `App {certificate_sha256}`), `Device::passkey_creation`, `create_passkey`, `passkey_sign_in`, and `sign_in_with_passkey`, which read the site's request as WebAuthn's JSON each time they are called, the free function `check_passkey_request`, and the errors `PasskeyRefused` (with `Malformed`, `Site`, or `Algorithm`), `PasskeyExists`, and `NotVerified`.

### The iOS app and its AutoFill extension (Phase 6b, stop 5)

The app (`apps/mobile/ios`, bundle `org.opensecretmanager.app`, iOS 17 and later, iPhone) and its AutoFill extension (`org.opensecretmanager.app.autofill`) share the app group `group.org.opensecretmanager.app`. The device's files are in the group container's `vault` folder, marked excluded from backup. The password kept for Face ID or Touch ID is a generic-password keychain item (service `org.opensecretmanager.device-password`, account `device`, access group the app group), stored only when the phone has a passcode, on this device only (`WhenPasscodeSetThisDeviceOnly`), with an access control that requires the current set of enrolled biometrics; the app also asks LocalAuthentication for the check before it reads the item. The logins chosen for an app the system names by its App ID are kept by the shared code in `app-logins.json` in the device's folder, under the App ID; before 2026-11-04 the extension kept them in the group's user defaults under `app-logins`, a dictionary from App ID to item IDs, which the app and the extension hand to the shared code the first time either opens the device, and then remove. Since Phase 19 the generator's choice is there under `generator`, once the owner changes it: a dictionary of `length` (8 to 64) and the booleans `lowercase`, `uppercase`, `digits`, `symbols`, and `avoidLookAlike`; one missing a key, with no kind, or with a length out of range is the shared code's default. A copy goes to the pasteboard local-only, and a password or code with an expiration 30 seconds later. The app and the extension each carry a privacy manifest (`PrivacyInfo.xcprivacy`): no tracking, no data collected, and two kinds of API used for a declared reason, files' metadata in the app group container (C617.1) and user defaults shared within the app group (1C8F.1).

The extension declares the extension point `com.apple.authentication-services-credential-provider-ui` with `ProvidesPasswords` and `SupportsSavePasswordCredentials` (and `ProvidesTextToInsert`, below), registers no credential identities with the system, and returns an `ASPasswordCredential`. Who asks is read from the service identifiers the system gives (`Shared/FillRequester.swift`): a URL with the scheme https gives `https://host`, or `https://host:port` for a port other than 443; a domain gives `https://domain`; when any origin results, those origins are offered their logins by the exact-origin rule. Otherwise an App ID (from iOS 26.2; a save request gives it as `app://<App ID>`, read without the `app://`) is used for the logins chosen for that app; otherwise an http URL fills nothing; and with no identifier at all the owner chooses among every login, warned, and the choice is not remembered. The extension opens the device on the shared folder, never goes online, and locks and lets go of it when the request ends. It has a mode for one-time codes (`prepareOneTimeCodeCredentialList`, from iOS 18) but does not declare `ProvidesOneTimeCodes`, since iOS offers a provider's codes only for the sites registered in its credential identity store, and the extension registers none. **Since Phase 17, stop 3** it also declares `ProvidesTextToInsert` (iOS 18 and later): in any field, the owner chooses AutoFill in the field's menu, then Passwords, then Open Secret Manager among the providers, and the extension's screen (`prepareInterfaceForUserChoosingTextToInsert`), titled Insert text, unlocks, lists every item by title, and a card by its brand and the last four digits of its number, and, for the item chosen, what of it can be inserted: a card's number, security code, cardholder's name, expiry as `MM/YY`, month, and year; a login's username, password, current one-time code, and website; any other field by its name; and the notes. Secrets are not shown. The text chosen goes to the system (`completeRequest(withTextToInsert:)`), which puts it into the field. iOS says nothing of the field or of the app, so nothing is checked: it is the owner's choice, as a paste is. iOS lets no other app fill cards (the iOS 27.1 SDK has providers of passwords, passkeys, one-time codes, and text to insert only), and this is how a card goes into a form there.

From iOS 26.2 the system can ask the extension to save a password. Asked to save without its screen, the extension declines: with `userInteractionRequired`, so that the system shows its save screen, or, for a password the system generated and filled into a form not yet sent (`generatedPasswordFilled`), with `failed`. The save screen reads who asks from the request's one service identifier, as above, and the username, password, and suggested title from its credential and title; it ends with `completeSavePasswordRequest` once a login has the password, or `userCanceled`. A new login saved for an app named by its App ID is added to the logins chosen for that app.

A debug build reads three variables at launch, for the UI tests (`App/TestSupport.swift`): `OSM_TEST_VAULT` empties the device's folder and puts the named vault file there (`none` for no vault), `OSM_TEST_BIOMETRICS=off` forgets a kept password, and `OSM_TEST_CHANGE_WHILE_EDITING` (`<item id>|<notes>|<password>`) changes that item's notes through a second device object on the folder when the editor opens for it. A release build has none of them.

**What the tests hold to.** A vault file written by each of formats 1 to 8, made by that format's own code at the last commit that wrote it (`crates/vault-core/examples/make_fixture.rs`; the commits are in each `expected.json`), opens with its password, shows the content it was written with, is upgraded to format 8 without reporting anything taken out, keeps every signed revision as it was (format 1, which had no signatures, is signed anew), still belongs to its recovery key, and can then be edited, backed up, and restored. The format 8 file, which also holds a conflict between two authors, a removed device, held and staged revisions, two key epochs, and a recovery key not yet confirmed, is read without being written to. A second test reads that file's rows with the encodings in `vectors.json` and `vectors-8.json` alone and no vault code above them, so the vectors describe the file: its seal opens to the marks of its rows, and its heads are the revisions no other names as a parent. A flipped bit in any authenticated value of the vault file, and a changed byte anywhere in a backup, is refused as not authentic; a file, backup, revision, invitation, or message of a later version is refused by its version and the file left untouched. Checksums of the binary fixtures are checked, because opening an older vault where it lies would upgrade it; tests work on copies. The bounds are tried on both sides: an item of exactly 16 MiB and one byte more, 16 parents and 17, an item ID of 128 bytes and 129, epoch 2^32 and one past it, 1,024 epoch keys and one more, and the stored password hashing cost at and outside 8 to 256 MiB, 1 to 10 iterations, and 1 to 16 lanes. Not tried at their edge, because of what filling them costs: 10,000 held revisions, 100,000 staged revisions or 512 MiB of them, and a 512 MiB backup.

**Device-local stores.** The control-plane database, the peer store, and the invitation store carry their layout version in SQLite's `user_version`. A store that says 0 is a new one or one written before the mark existed, and is layout 1; it is marked when opened. A store marked with a later version is refused before anything is written to it, which happens only when an older build is run on a newer build's files. Since Phase 8 the desktop app then shows only why it cannot start, naming the peer or invitation store and the folder, and runs nothing else; a phone says that its vault cannot be opened, naming the peer store. A refused control-plane database keeps the device out of the vault's control plane: the desktop app now says so in its sync status, naming `control.sqlite3`, where it used to say nothing, and a phone shows an error when it tries to take part. A vault file the desktop app cannot open, a later format's or a damaged one, now also leaves the files beside it as they are: the app used to delete its control-plane database at launch, taking it for what an abandoned join leaves.

**What the vault file proves and what it does not.** Every value that decides what is shown or who may write is under a key: the wrappers, the device's own identity, each author's and each removed device's mark, each epoch key, and every revision's header, content, and signature. Since format 8 so is which of the rows that are never removed exist, and the heads are checked against the revisions (see the row seal above): a revision, an author, a removal, or an epoch key taken out of the file, a head taken out or set back to an earlier version, and a revision's row changed, as by marking an edit as a deletion, are found at the next unlock and the owner is told. Until format 8 they were missing without an error. What the seal cannot see is the file set back in time: the whole file replaced by an older copy, or the sealed rows set back to an earlier moment together with the seal written then and heads made to agree. By itself that shows nothing, and what was added since is missing on this device until a sync brings it from another. Since 2026-10-14 the desktop finds either from the count of sealed rows it keeps in the system's keystore (see Rows seen), which the file cannot set back; a set-back that undoes only writes adding no sealed row, such as a password change, is still not found, and the phones find none. The recovery key kept until confirmed (`unconfirmed_recovery`) is not sealed: taking it out loses only the reminder to store it. `current_epoch` and `write_fence` are plain numbers; under a control plane both are set again from committed state at every unlock. The triggers that keep rows from being changed stop a mistake, not someone who can write the file.

**The fields of an item** are part of signed revision 2: `id`, `title`, `kind`, `username`, `password`, `url`, `notes`, `totp_secret`, `custom_fields`, `tags`, `favorite`, in that order, as JSON, and since Phase 18 `passkeys` after them when a login has a passkey (see A login's passkeys). All but `passkeys` must be present. Since Phase 8 a build keeps the fields it does not know (`unknown_fields`), with any JSON value, as they were read, and writes them back after its own whenever it writes the item again: an edit, a saved password, a restore, a resolution, an accepted held change, a copy from a put-away vault, and a backup. A field given twice is refused, and an item whose unknown field takes the name of a known one is not written. An item this build makes has none, so its JSON is unchanged. History names a change to them as "fields of a later version". Builds from before Phase 8 read an item without the fields they do not know and drop them at their next edit, so a field added later is safe only once every device of a vault runs Phase 8 or later. **Since Phase 15** a revision's content also has `saved_at` after the item's fields: when it was saved, in whole seconds since 1970, by the saving device's clock; a deletion's content, empty before, is `{"saved_at":<seconds>}` alone. It is not one of the item's fields: an item read leaves it out, so two items with the same fields are the same item, and an edit writes its own time. A `saved_at` that is not one whole number is taken for none, and the item is read as before. An item's size limit (16 MiB) counts it, so the fields of the largest item are about 23 bytes fewer. Builds from before Phase 15 keep it as a field they do not know (see above), and take a deletion with content, which they do not read.

**Domain labels.** Each is followed by a NUL byte unless noted: `osm-key-wrap-v1` (wrapping a key; then the vault ID and `password`, `recovery`, or `unconfirmed-recovery`), `osm-device-signing-key-v1`, `osm-recipient-key-v1`, `osm-epoch-key-v1`, `osm-epoch-key-check-v1`, `osm-recovery-check-v1`, `osm-device-authorization-v1` and `osm-device-revocation-v1` (with their subkey labels `osm-device-authorization-key-v1` and `osm-device-revocation-key-v1`, no NUL), `osm-item-revision-v2`, `osm-revision-signature-v2`, `osm-revision-id-v2` (and `osm-item-revision-v1`, `osm-revision-id-v1`, read only when upgrading format 1), `osm-portable-backup-v1`, `osm-pairing-signature-v1` (then `join-request` or `enrollment-grant`, each with a NUL), `osm-pairing-transcript-v1`, `osm-pairing-token-v1`, `osm-pairing-sas-v1`, `osm-control-signature-v1`, `osm-control-request-v2`, `osm-control-request-id-v1`, `osm-epoch-key-hpke-v1` (HPKE `info`, no NUL), and `osm-invitation-token-v1` (no NUL). Text forms: `OSM-RK1-` (recovery key), `OSM-PAIR1-` (invitation), `OSM-BACKUP` (backup magic), `OSK1` (envelope magic).

**Changing a format.** Give it the next version number where it is marked. Keep reading the previous version, or refuse it by its number; never try an older reading after authentication fails. Add a fixture written by the new code, in a new folder or file, and a test that takes the previous version's fixture through the upgrade. Leave every existing fixture as it is: `make_fixture` and the tests that write vectors refuse to replace a file. Update this document in the same change.
