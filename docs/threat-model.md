# Threat model

This document is for contributors deciding whether a change may handle real credentials. It describes the intended security boundary, the attacks that must be tested, and the limits the product must explain. It is a design contract, not evidence that every control exists. See [implementation status](implementation-status.md) for delivery gates and [formats](formats.md) for storage and protocol rules.

## Scope and ownership

The owner keeps an encrypted password vault on their devices. A Rust core owns cryptography and vault state; desktop, browser, and eventual mobile clients are adapters. No provider account, hosted control plane, or third-party recovery service is required. Directly reachable peers exchange ciphertext. Internet discovery, NAT traversal, a relay, and mobile background execution are separate features requiring their own evidence. Since Phase 16 a device listens over IPv6 as well as IPv4, and an invitation names up to four of its addresses, a VPN's or a global IPv6 one among them: whoever sees an invitation learns them, and where a network lets connections in over IPv6, which many home routers do not, the listener is reachable from the internet. What it takes before a peer is authenticated is unchanged: the TLS handshake with pinned certificates, and frames of at most 64 KiB until then (see the formats).

The owner controls enrollment and recovery. A device is an authorized replica, not a separate human principal. Consensus establishes one membership history; it does not establish that several humans approved an action.

The protected assets are passwords, usernames, notes, TOTP seeds, payment cards' numbers and security codes, recovery material, private device keys, epoch keys, membership authority, and the integrity of revision history. Titles and origins are also sensitive and belong inside record ciphertext. Public routing metadata may reveal vault/device identifiers, revision relationships, approximate sizes, update frequency, and network addresses.

## Trust boundaries

| Boundary | Required behavior |
| --- | --- |
| Disk to unlocked core | Authenticate encrypted envelopes before accepting plaintext. Reject unsupported versions and bounded-but-invalid KDF settings before allocation. |
| Frontend to Rust | Treat every command argument as untrusted. Rust enforces lock state, origin policy, file limits, and authorization. |
| Network to receiver | Pin peer identity, authenticate the connection, bound frames and queues, and distinguish stored ciphertext from accepted history. |
| Received revision to materialized record | Validate signature, authorized author, vault, epoch, ancestry, and AEAD before exposing content. |
| Membership log to active key epoch | Activate a rotation only through committed state and durable envelopes. Resume or fail closed after a crash. |
| Browser page to extension | Page scripts cannot request arbitrary vault reads. User action, current frame identity, and exact HTTPS origin constrain disclosure. |
| Extension to native host | Accept only the installed extension identity and bounded protocol messages; use authenticated local IPC to the desktop session. |
| Recovery artifact to live membership | Restore offline first. A stale backup must not silently recreate an existing live device identity or override current membership. |

Tauri capabilities and a restrictive content security policy reduce frontend authority. They do not excuse missing authorization in Rust. Do not load remote application code, execute arbitrary shell commands, or expose generic filesystem and network commands to the webview. Tauri documents this boundary in its [IPC model](https://v2.tauri.app/concept/inter-process-communication/).

## What the design protects against

- A stolen locked database or encrypted backup must require the correct password or recovery secret to reveal record content.
- A network observer or unpaired machine must not obtain vault plaintext or enroll itself by guessing a device name or address.
- A peer that retransmits, truncates, rearranges, or modifies messages must not silently change an accepted record or membership transition.
- Concurrent offline edits and delete/edit races must remain visible until explicitly resolved; arrival time must not silently select a winner.
- A removed device must not receive future epoch keys after removal completes.
- A malicious web page must not cause automatic fill or obtain credentials for a different origin.

## Limits that must remain explicit

An administrator, debugger, injected process, compromised extension, or compromised operating system can observe secrets while a device is unlocked. Zeroization reduces residual exposure but cannot guarantee erasure of compiler copies, webview strings, swap, crash dumps, clipboard managers, or screenshots. JavaScript must retain revealed secrets only as long as the user action requires.

Encryption does not erase plaintext a peer previously learned. Removing a device cannot retract old epoch keys, old backups, or already copied passwords. Rotating a vault key also does not rotate passwords at external websites; the owner must change exposed credentials there.

Immutable signed revisions reveal tampering, but a completely rolled-back local database can still look internally valid. Without a fresh trusted peer or external checkpoint, the product cannot prove that an isolated snapshot is current. Backup restoration must display that limit. The same holds within one file. Every value that decides what is shown or who may write is under a key, and since vault format 8 (Phase 10) so is which rows the file holds: an item or an edit hidden by taking rows out of the vault file, or by changing them, is found at the next unlock and the owner is told, and a missing revision comes back from another device at the next sync. Until then such an item or edit was missing without an error. The seal does not find the file set back in time, whether the whole of it or only the sealed rows together with the seal written at that time, for the reason above. Since 2026-10-14 the desktop keeps that external checkpoint: how many of the sealed rows, which are never changed or removed, it last saw the file hold, in the system's keystore (see Formats). An earlier copy holds fewer, and an unlock that finds fewer tells the owner as it does for rows taken out. It does not find a set-back that undoes only writes adding no sealed row, such as a password change or turning recovery on; nor one that sets the keystore back with the file, as restoring the whole home folder does. Whoever can write the keystore's entry can lower the count: on macOS a program the Keychain lets in, on Linux any program of the session, as for the TLS key below. Without a Secret Service nothing is kept or checked. The phones keep no count: their files are in the app's own storage, which no other app can write on a phone that is not rooted, and are left out of its backups.

A member device can fill another's queue of received revisions with revisions it signed that name parents nobody has; they wait there, up to the queue's bound, and once it is full nothing more is received until they are gone. Nothing but processing takes them out, so this is a way for a compromised member to stop a device receiving, and the remedy is removing that member and starting the device over. Raft assumes crash faults, not Byzantine participants. A malicious enrolled voter is outside its consensus safety model. Signatures authenticate an author; they do not make an authorized compromised device honest. OpenRaft is the consensus implementation, not a substitute for application authorization.

A device takes part in Raft under its transport identity, whose key is stored unencrypted so that a locked device can receive. Whoever copies that key and the control-plane database from a device, locked or not, can act as that voter: vote, lead, and write unsigned membership entries. That can stall or corrupt the control plane for the other devices, and the remedy is then recovery into a new trust domain. It must not yield keys or authority, so both follow signed enrollment rather than Raft membership: only a member whose enrollment a member signed can make a request or be given an epoch key, and a removal seals the next key to enrolled members only. Since Phase 6b a member may be enrolled without a vote, as a Raft learner; it holds the keys and may make requests like a voter, and counts toward no majority. Unsigned membership entries can still change who votes, making such a member a voter or a voter a learner; that changes who the majority is, not who holds keys or authority. A removal ends an enrollment for good: a removed device that such entries make a voter again is not enrolled, so it gets no key and its requests count for nothing. Until Phase 6a stop 2 it counted as enrolled again, and every unlocked member would have sealed the newest epoch keys to it.

Availability depends on device reachability. A single device can use its local vault offline. Membership changes need a majority of the configured voters; a two-voter vault needs both voters. Members without a vote, such as phones, count toward no majority: a vault of one voter and any number of them can remove any of them with that voter alone, and cannot change anything without it. The only voter cannot be removed: Raft makes no change to a membership without a voter, so the state machine refuses such a removal rather than leave it pending. Losing quorum must not enable an unauthenticated emergency removal. An explicit recovery fork creates a new trust domain.

The recovery fork is not a removal. It does not take anything back from a lost device, which keeps every key and record it already had, so the owner must change the passwords it could have seen. It protects what is written afterwards: the new vault has a new identity and new keys that no device of the old vault holds. It needs only one unlocked device and its password, so anyone who can unlock a device can start a new vault from it, but that vault is separate and the old one and its other devices are unaffected. The old vault's files stay on the device in an archive folder, still encrypted under the same password; deleting them is the owner's decision. Nothing tells the other devices that the vault was replaced, and no device's word is taken for it: on each one the owner has its copy put away, with that device's password, before it joins the new vault. That action changes nothing in the old vault's membership. Used on a device of a vault that is still in use, it leaves a member that never answers, which the remaining devices must remove, and with two devices they cannot; the app says so before it is confirmed. The app suggests the action when, at a member's address, something answers with a certificate other than the one membership records. The device refuses such a connection either way. The suggestion proves nothing about why it happened: anyone who can answer at that address can cause it, so it only asks the owner whether they started over on that device, and the action still takes the owner and the device's password. Earlier revision history and revisions held for review are not carried into the new vault.

An archived copy is as protected as the vault was: encrypted under the password it had, with that device's keys inside. It is not weakened by sitting in the archive, and it is not strengthened either; a password that was changed since still opens the copy made before the change, and a device's removal from the vault does not make its archived copy unreadable to whoever has that password. An opened copy is closed when the vault locks. Items copied out of it never cross to the interface: the copy is made between the two vaults in the Rust process. Deleting an archived copy removes its files without overwriting them.

A recovery key that the owner has not yet confirmed storing is kept in the vault, encrypted under the device's root key, so that it can be shown again if the app stops first. Until the owner confirms, anyone who can unlock that device can read the recovery key, and it opens every device of the vault that has recovery turned on, given that device's vault file. Unlocking the device already gives the vault's contents and keys; what the kept recovery key adds is the other devices' own identities. The exposure ends when the owner confirms, which the app asks for after every unlock.

## Local encryption and lock lifecycle

Use a randomly generated 256-bit vault/epoch key to encrypt records with XChaCha20-Poly1305. Bind record identity, vault identity, format version, key epoch, and revision metadata as authenticated additional data. Generate each 24-byte nonce from the operating system random source. Passwords wrap keys; they are not record-encryption keys.

Argon2id derives the local wrapping key using a random salt and persisted parameters. Parameters need upper and lower bounds and device-specific latency measurement. The vault uses 64 MiB, three iterations, and one lane (see Formats), not yet tuned to any device; benchmark it on each supported device rather than treating it as a universal mobile setting. The memory-constrained recommendation and tuning rationale are in [RFC 9106](https://www.rfc-editor.org/rfc/rfc9106.html).

Lock clears vault decryption keys, signing authority, decrypted record caches, visible secrets, pending fill grants, and sensitive clipboard ownership. A transport identity may remain available for locked ciphertext receipt, but it must be distinct from vault-decryption and membership-signing keys. Persist any transport key only through a documented restricted local credential store. Transport possession alone must never authorize record access, enrollment, removal, or key rotation.

Enforce inactivity and operating-system sleep/session-lock behavior in the native shell. The desktop app locks after five minutes without input (the owner can set 1, 5, 15, or 60 since Phase 8, and 240 since 2026-11-17). Until 2026-11-17 it also locked as soon as its window was hidden or covered, except during a pairing; since then, at the owner's request, a hidden or covered window keeps to the same time, so whoever has the computer, unlocked, within it can bring the window back and read the vault without its password, as with the window left in view. A hidden window's timers can run late, so on being hidden the window hands the rest of the time to the native side, which locks the vault on time, and it checks the time by the clock when it comes back and when a browser's request arrives, before it shows anything. Only input in the window counts as activity: being shown again, as a browser's request does, does not, so a page or program cannot keep the vault open by asking. On macOS it also locks when the computer is about to sleep, the displays sleep, the screen locks, the screen saver starts, or another user takes the screen, and then takes a one-time code or password it copied off the clipboard if it is still there. Locking waits for a vault operation in progress, so a computer can go to sleep with its vault unlocked and lock on waking. Since Phase 10 it does the same on Linux when logind says the computer is going to sleep, tells its session to lock, reports the session locked, or reports that the session left the seat, but it hears nothing of a screen saver or of displays sleeping there; on Windows only the timer locks. A copied code, password, or other field (the desktop copies a password since Phase 8; before, its Copy copied the dots) is put on the macOS clipboard for this Mac only and marked for clipboard history apps to leave out, and on the Linux clipboard with the password-manager hint (`x-kde-passwordManagerHint`), which only apps that honor the marks do (of the clipboard managers Ubuntu 22.04 ships, KDE's Klipper honors it and CopyQ 6 keeps the secret, as Phase 11 found); on Windows it is plain text on the clipboard. Everywhere it comes off after 30 seconds unless something was copied since. Recheck lock state at the point of disclosure, including after an asynchronous confirmation. Password change atomically replaces the local wrapper; it must not alter a peer's independent unlock password or require plaintext re-encryption of every record. Since 2026-10-12 each app changes its device's password on its own screens, given the current one, and the native side of each refuses a new password under 12 characters: the desktop's too, which until then left that to its window for a new vault, a restored backup, and a reset with the recovery key, so a caller of its commands that bypassed the window could set a shorter one.

## Revision integrity and conflicts

Each signed revision belongs to one vault and record and names its parent revisions. Accepted heads are revisions without an accepted descendant for that record. Two heads represent a conflict. A resolution creates a new signed revision naming all resolved heads; it must not delete the history or accidentally include unrelated parents.

Deletion is a revision containing an encrypted tombstone. Delete/edit races remain conflicts. The core rejects cross-record parents, self-parenting, duplicate parents, invalid signatures, impossible epochs, unsupported versions, and oversized payloads. Missing parents are pending dependencies, not permission to invent history.

Receipt may happen out of order. Deduplicate by a cryptographic revision identity, preserve exact signed bytes, and quarantine unsupported or unverifiable entries. Do not report a quarantined entry as successfully merged. An entry from a removed or unknown signer must not become authoritative because its timestamp looks old; timestamp alone does not prove pre-removal authorship.

## Pairing, transport, and locked receipt

An invitation contains a fresh high-entropy one-use secret, short expiry, inviter identity, and an authenticated pin or transcript binding. Verify the device identities through the transferred invitation or an explicit short-authentication-string comparison. Displaying a QR code is not by itself proof of endpoint authenticity. Never log invitations. The desktop shows a phone's invitation as a QR code as well as text: the same one-use secret, to whoever can see the screen or a picture of it, as the text is. A phone uses its camera only when the owner chooses to scan, keeps no frame, and checks what it reads as it checks a pasted invitation; the code comparison is still what authenticates the two devices.

TLS must validate proof of possession and the expected peer pin in both directions. Disable broad “accept any certificate” paths. Address discovery is untrusted and cannot replace the identity check. Retry cannot downgrade authentication. Network parsers need size/time limits and rejection before expensive cryptography where possible.

Since 2026-10-13 each device tells the members it connects to up to four of its own addresses (its home network's, a VPN's, a global IPv6 one), over the members' TLS, and they keep them ahead of what others said of it. A member therefore learns where the others can be reached, as an invitation already told it of the inviter; the relay, which sees TLS records only, does not. A member can make the others try any IP address and port for itself, as it could already suggest one for any device, but no host name, and an answer elsewhere still has to show the device's pinned certificate.

A device's TLS key has to work while its vault is locked, so it is not under the vault's password. Since Phase 14 it is sealed by the system's keystore (the macOS Keychain, the Linux Secret Service, the Android Keystore, the iOS Keychain; see Formats), so that a copy of the device's files, in a backup or on another computer, holds it only sealed, and cannot act as the device toward the others. This is protection at rest, not from this account: the key is opened into the app's own process, where rustls signs with it, and any program running as the owner that the keystore lets in (on macOS, the app itself; on Linux, any program of the same session, as the Secret Service allows) can open it too. Where no keystore answers, the key is kept in the file as before, with owner-only permissions, and the desktop says so. Sealing an earlier build's key overwrites it in the file, but SQLite's rollback journal held the page while it was written and is deleted, not overwritten, so what remains of the old key on the disk is up to the file system. A keystore entry is not removed when a device is reset or its files are put away; it then seals nothing anyone still holds.

**A relay (since Phase 16).** The owner may run a relay (`osm-relay`) that joins two of the vault's devices when neither can reach the other, such as a phone on mobile data and a computer at home. The devices run their usual TLS with both certificates pinned over the connection the relay joins, so the relay cannot read what passes, cannot alter it without the session failing, and cannot pass for a device: it holds no device's key and no vault key. It does see which certificate pins ask for which, when, from which addresses, and how many bytes pass, and a network observer between a device and the relay sees the one-use tickets the relay joins connections by, in the clear, but not the pins, which travel over TLS. A relay that misbehaves, or one that stops, can refuse or drop connections: an outage, not a breach; devices still reach each other directly where they can. The relay's code, with its address, its certificate's pin, and its token, is kept in the vault, so every device that can read the vault learns it, and in each device's peer store, unsealed, so that a locked device can use it; the token lets its holder register with the relay under its own certificate's pin and ask for others by theirs, nothing more. A device removed from the vault keeps the token until the owner gives the relay a new one (and the devices the new code), and can reach the vault's devices through the relay only to be refused by them, as it would be directly; it can also hold some of the relay's 64 places, which a new token frees. Pairing never goes through the relay: a device joins on a network it shares with the inviter.

Control-plane connections accept the certificates of the devices a node's own log names and refuse removed devices. A node whose log is behind, or a device still being enrolled, also accepts a certificate that a member vouched for: in the signed enrollment grant, or in the member list a device it already counts as a member sends when a connection opens. This adds no principal that could not already act: a device trusted to send Raft messages can already feed a lagging node a log of its choosing. It does mean a lagging node trusts whatever its last known members trust, including a member that has since been removed, until it catches up. A Raft message is attributed to the device whose certificate the connection presented, never to the sender it names. Revision sync is narrower than the control plane: each end requires the other to be an enrolled member by its own committed state, not removed and not being removed, so a device still being enrolled or merely vouched for exchanges no revisions. A removed device's connection is completed only to tell it that it was removed. It believes that from any member, and the desktop app then resets the device: its copy of the vault is moved to an archive folder beside it, not deleted, and the device is left without a vault until it joins again. A member can therefore make another device put its copy away, including edits that had not synced; they stay in the archive, which the owner can open in the app with the password that copy had, to copy what is missing into the vault the device has now. This is within what members are already trusted with, since every member is one of the owner's devices and could already refuse the device, but it is the one place where a single device's word, rather than committed state the device has itself applied, changes what another device holds.

When locked, the receiver may store bounded encrypted envelopes and public signed control messages. It cannot decrypt, approve invitations, sign membership changes, or unwrap a new epoch. Verify everything possible with committed public membership, and defer remaining checks. Unlock processes the quarantine transactionally. A disk-full or malformed-message failure must leave existing vault state intact.

HPKE protects epoch material for an enrolled recipient; application signatures and committed membership authorize the sender and recipient. HPKE alone does not provide replay prevention or durable membership semantics, as explained in [RFC 9180](https://www.rfc-editor.org/rfc/rfc9180.html#section-9.7).

## Membership, removal, and rotation

Keep record convergence separate from the membership control plane. Offline record edits are allowed with the last usable epoch, but enrollment, removal, and epoch activation require a committed control-plane decision. Serialize owner-initiated membership proposals and make retries idempotent.

Use OpenRaft's learner catch-up and joint membership transition. Persist votes, logs, applied state, snapshots, and membership with crash-safe ordering before acknowledging durability. A set of signatures, an in-memory vote count, or a local “majority” function is not a running Raft cluster. OpenRaft describes learner promotion and joint transitions in its [dynamic membership documentation](https://docs.rs/openraft/latest/openraft/docs/cluster_control/dynamic_membership/index.html).

Removal has an explicit pending state. Stage the new epoch and recipient-specific envelopes for retained members, commit the membership transition, and activate the associated epoch only through a durable state-machine decision referencing that transition. If any step is incomplete after a crash, resume it or block new current-epoch writes; never report a fully revoked device while continuing to issue future secrets under an exposed key.

Old-epoch edits may arrive after removal. A device that has learned of a removal holds the removed device's revisions it had not yet accepted for owner review. The owner keeps or rejects each one on any unlocked member: keeping it has that device write a revision with the same content on top of it under the current epoch, and rejecting it has that device write a revision on top of it that keeps the item as it was. Either way the removed device's revision enters each member's history as it was signed, already superseded, and the decision reaches the other members by sync, including one that had taken the revision in before it learned of the removal. The review shows what a held revision would change but never a password or one-time-code secret, only that it differs. This trades automatic convergence for an explicit boundary against a removed signer forging supposedly old edits. There is one causal exception: a held revision that a current member's revision names as a parent is accepted as-is with that child, because the member accepted it and its own history depends on it. So that devices which never saw the removed device's last accepted edits (later joiners in particular) need not review them, the device that made the removal writes, as itself, a revision on top of each of the removed device's remaining heads. The exception means a removed device can still get an edit accepted through a member that had not yet learned of the removal and then built on it; that window lasts until each member applies the committed removal.

## Browser disclosure

Fill requires an explicit user gesture and selection. Match normalized HTTPS scheme, host, and effective port exactly. Neither a registrable-domain match nor a suffix match is sufficient. A credential for `https://example.com` may match `https://example.com:443`; it must not match HTTP, a subdomain, a lookalike host, or port 8443.

The extension obtains the top-level URL and frame identity from browser APIs. The native host repeats origin validation. Bind a short-lived, single-use grant to request ID, tab, frame/document, origin, selected record, and unlocked session. Revalidate immediately before disclosure and immediately before insertion; navigation, lock, timeout, and replay cancel the grant. Initially support only the top-level frame and reject cross-origin iframes. Never auto-submit a form.

The owner selects the login in the desktop app, for every fill. The extension never receives a list of vault items, so neither a page nor a compromised extension can learn which logins exist. What an extension can do is ask, and the owner sees the origin it asked for and is offered only logins stored for exactly that origin. A request may arrive while the vault is locked; it waits, for a limited time, while the owner unlocks in the app. The owner's selection counts only in the unlock it was made under: if the vault locks before the login is released, nothing is released, and unlocking again does not bring the selection back.

Native messaging permits a declared extension allowlist and framed JSON transport; neither feature alone authenticates a website or a desktop unlock session. Follow the browser's [native messaging protocol](https://developer.chrome.com/docs/extensions/develop/concepts/native-messaging), and test forged, truncated, and oversized input. A host with no authenticated desktop session must return unavailable, not read a plaintext export or unlock the vault itself.

The native host has no vault and no key; it passes requests to the desktop session and passes back only a response that answers the request it forwarded. What authenticates the socket between them is the operating-system account: the host connects only to a socket that account owns, and the session answers only a connection from that account. Any program running as the owner can therefore connect and pose as the host, naming the allowed extension and any origin. It gets nothing unless the owner then picks a login in the app, for the origin the app shows, but it can time its request to coincide with one the owner expects. The extension allowlist has the same limit: the browser enforces it from the host's manifest and the host and the session check it again, which stops another extension and does not stop a program that starts the host itself. Both are instances of the limit above on a process of the owner's account while a device is unlocked.

Unless the owner turns on its access to all sites (below), the extension has no access to a page until the owner presses its button on that page, and then only to that tab; it holds no standing permission on any site. It runs no script in pages otherwise, keeps nothing between requests, stores nothing, and shows nothing inside a page, so a page has nothing of the extension's to read, imitate, or click. The script it puts into a page runs apart from the page's own scripts. A page cannot start a request, and a frame inside a page is never given a login; since Phase 17 a frame of the page's own origin may be given a card's fields (below).

Since Phase 18, stop 6, the owner can give the extension access to all sites, on its options page, for passkeys and for a card form's frames of other sites; it is off until then, and the browser asks before it is on. With it on, the extension can read and change every page the owner opens, and a compromised extension, or one updated by whoever controls its publishing, could take what any page shows and types; with it off, only the page whose button was pressed. It puts two scripts into the page itself of every `https` page: one in the page's own world, which the page can read, change, or remove, and which therefore holds nothing and decides nothing, and a bridge in the extension's own world. And a page can then start a request, by calling WebAuthn for a passkey: the app's window comes forward for it, as for a press. What keeps such a request honest is not the page's word. The origin is the one the browser reports for the bridge's connection, held to the document's address and the tab's, and only the page itself is served, not a frame. The call must come while the owner is using the page (the browser's own record of the owner's activation, read in the extension's world), so a page cannot raise the app as it loads; and after the owner denies a site's request, or lets it run out, the site's requests go to the browser's own for a minute. The app reads the site's options itself and applies the rule for which sites a passkey is for to the reported origin, and makes the client data itself, for that origin and not from another's frame, so a page can ask only for the passkeys of its own site, and the signature it gets is good only for its own origin. The owner chooses each time, sees the site and the account, and is verified when the site asks: on a Mac by Touch ID or the Mac's own password, otherwise by this device's vault password, each time; an unlocked vault alone is presence, not verification. Once a page has a credential, its scripts have it, as with the browser's own passkeys. A request the app does not answer, one for a site whose passkeys the vault does not hold while it is unlocked, and every request while the app is not running, go to the browser's own passkeys as if the extension were not there; so the extension does not take a sign-in away from the browser's own, but it does see, while the switch is on, which sites ask the browser for passkeys and when. Once a login is filled, the page has it: filling is disclosure to that page, which is why the origin is taken from the browser and checked at each step. A page its site serves sandboxed (`Content-Security-Policy: sandbox`) has the site's address but an origin of its own, and its scripts are not the site's: the extension takes the document's own origin, not its address's, and refuses such a page. Until 2026-10-21 it took the address's, so a login could have been filled into a sandboxed page on a site that serves what its users upload under its own name. A page can still mislead the owner about itself; the app shows the origin the browser reported, and that is what the owner should read.

A reply is filled only if it names the request, tab, frame, document, and origin the extension asked with, and only once. This is checked by the host and again by the extension, so that neither trusts the other for it. Before filling, the extension also asks the browser which origin and which document the tab shows now. Whether a page was left is not taken on the page's word alone: a page can keep the extension's script from noticing, and a browser may keep the document it left. In that case the request keeps waiting in the app until it is decided or expires, and a login chosen then is not filled. What the extension's script in the page says back, what it found and which fields it filled, is believed only in its exact form, the two fields' names each at most once; until Phase 13 the answer to a fill was taken as given, so a renderer that forged it could have left the request unfinished on the button or put words of its own in the button's title.

Since Phase 17, stop 3, a press on a page with a card form asks for a card instead. A card belongs to no site, so it may go to any https page the owner chooses it for: the app shows the page's origin and, for each document to be filled, its origin and which of the card's fields go there, and offers every card; the owner chooses each time. The documents are the page itself and frames of its origin, the only ones the press gives the extension (a frame of another origin, as a payment provider's, is not reached until the owner gives the extension access to all sites, Phase 18). Each document's origin is the one its script reports from the document (`self.origin`), which the page's scripts cannot change, and the page itself is held to the tab's address, as for a login; a frame's is not checked against anything the browser says outside the document, so a compromised renderer could name another. That mattered little while only frames of the page's own origin were reached; with access to all sites, frames of other sites are reached too, and a renderer compromised in a frame's process could name another origin for its frame, which the owner would read in the app. The reply carries only the fields some document asked for, and each document's script is handed only its own; a field the owner cannot see (of no size, hidden, or transparent) is not one, so a page cannot hide a second field to have the security code with the number. Once filled, the page has the card, as it would one typed there. On iOS, which lets no other app fill a card, the extension gives a chosen field's text (a card's number, a password) for the field the owner chose AutoFill in; iOS says nothing of where it goes, and the owner decides, as with a paste.

A request makes the desktop app's window come forward. Only one request waits at a time. A page cannot make one, but for a passkey once the owner turns access to all sites on (above), and then a fill the owner starts takes the page's request's place; any program of the owner's account can make one, so such a program can interrupt the owner with a request screen. The screen shows where the request claims to come from and nothing is sent unless the owner chooses. After a fill or a denial the window steps back. Until 2026-11-17 being covered then locked the vault, so that unlocking for one request did not leave it open behind the browser; since then, at the owner's request, it stays unlocked behind the browser for the rest of the time without input set in Settings, so that the next fill does not ask for the password again, and a request that comes meanwhile shows the logins for its origin without an unlock, for the owner to choose from.

The app tells a browser where the native host is only when the owner connects that browser in the app, by writing a manifest into the browser's own folder. The manifest allows the project's extension and no other: in Firefox its one ID; in a Chromium browser two, the copy loaded unpacked (whose ID follows from the key in its manifest) and the Chrome Web Store's (whose key the store keeps), since 2026-11-16. A manifest in that place that names another program or allows another extension is shown as not this app's rather than as connected, and the owner can replace it. A program of the owner's account can rewrite the file again; the browser would then start whatever it names, which reaches no vault unless it is this app's host talking to this app.

A packaged app has the host inside it, beside its own program, and the manifest names that file. The host is therefore as trustworthy as the app's own files: whoever can replace a file inside the app can replace the host, and equally the app. Packages built here are not signed with a developer's identity, so nothing but the file system's permissions guards either; signing is release work that has not been done. The app refuses to point a browser at a host in a place that is gone when the app quits (a downloaded Mac app run before it was moved, an AppImage), so that a manifest is not left naming a path that something else could later occupy.

## Phones

A phone is a device of the vault like any other, with its own password and root key, enrolled by the owner's comparison of codes, and, as the desktop app invites it by default for a phone, without a vote. The shared code runs on it as it does on a computer. While the app is in front it accepts the vault's members on a port of the network it is on, and nothing else gets past the handshake; in the background nothing runs, and the other devices keep what they have for it. Since Phase 8 an Android phone also syncs now and then while the app is closed (at most every 15 minutes, on a network, as Android schedules it, unless the owner turns it off): for those few seconds it takes part as it does in front, accepting members on its port and reaching those it knows, but it never unlocks the vault, so it only passes on revisions already encrypted and signed, and keeps what arrives for verification at the next unlock. An iPhone does not sync while closed. A password or one-time code that the app asks for, to copy or fill, crosses into Kotlin or Swift as a string, which the shared code cannot wipe there, as with the desktop app's window. A lost phone is removed like any device, and keeps what it already held.

The Android app (Phase 6b, stop 3) stops taking part as soon as it leaves the screen, unless it is joining, and locks the vault then too or, since the owner tried it on a phone (2026-10-12), once the time the owner chose has passed: at once, or after 1, 5, or 15 minutes, a minute unless changed, and since 2026-11-17 also after an hour or 4 hours. The time runs from when the app, or its fill or save screen, last left the screen. Until 2026-11-17 the phone's screen turning off locked the vault at once whatever the time chosen; since then, at the owner's request, it keeps to the time chosen on a phone with a lock screen (a PIN, pattern, or password), which guards the vault meanwhile as far as the phone's own settings let it (Smart Lock, for one, can keep a phone unlocked in a pocket), and it still locks the vault at once on a phone without one. The timer that locks it does not run while the phone sleeps, which it can do for most of the time the screen is off, so the vault's keys can stay in the app's memory past the time chosen until the phone wakes; the screen turning on, the app coming back, and the system's list under a field each check the time by the clock first, and lock the vault if it has run out, so none of them shows or fills from the vault past it. Meanwhile the vault's keys are in the app's memory as while it is in front, so whoever has the phone, unlocked, in that time can open the app and read the vault without its password. The app keeps the vault out of screenshots, screen recordings, and the recent-apps preview. It allows no backup or transfer of its data, which would make a second device under its identity. It can keep the device's password for unlocking with a fingerprint, encrypted with a key in the phone's secure hardware that is usable only after a strong biometric check; whoever can pass that check on the phone, with an enrolled fingerprint of theirs, can therefore unlock the vault, and a newly enrolled fingerprint makes the key unusable until the password is typed again. Changing the phone's password deletes the kept one, which is the old password, so the fingerprint unlocks nothing until it is turned on again at an unlock. Since Phase 19 the phone asks for the fingerprint by itself, without a tap, when it shows the vault locked after the app starts or comes back, or when a fill, card, save, or passkey screen opens; never after the owner's own Lock, and once only, so that "Use the password" or a cancel leaves the screen as it is. It is the same check, so this changes who can unlock nothing: a finger on the sensor is still needed, and a fill screen unlocked so still fills only what the owner then chooses there (or, for a login already chosen in the system's list, what was chosen). A copied password or code is marked sensitive and cleared after 30 seconds, but any app in front when it is pasted, or a keyboard, can read it meanwhile.

Autofill on Android (Phase 6b, stop 4) fills nothing from a locked vault until the owner unlocks it on the app's own fill screen and chooses a login there; until then a form is told nothing about the vault, not even whether it holds a login for it. When the fill screen goes, the vault locks as when the app is left, at once or after the time chosen. While it is unlocked (since 2026-10-12), the system's list under another app's field names the logins a fill would offer there, by title and username, on the rules below, and choosing one fills it without the fill screen showing. That list is drawn by the system, not by the app that asked, which learns nothing from it until a login is chosen; but anyone who sees the screen meanwhile, and an accessibility service with the permission, can read the titles and usernames in it. Since 2026-10-13 a keyboard that asks for the entries in its strip gets them there instead: the system draws them into the keyboard's window, and Android's documentation says the keyboard is not given what they say until one is chosen; it learns how many there are. Anyone who sees the screen, and an accessibility service with the permission, can read the strip as they can the list. The password goes to the system only when a login is chosen, and the vault is checked then to be unlocked still and the login to be for that page or app. Since Phase 13 the fill screen's window is marked translucent, though it draws an opaque screen, so the app that asked stays visible to the system beneath it, paused rather than stopped; that app gains nothing from it: it cannot draw over the fill screen or read it, and the fill screen still refuses screenshots. A web page's origin is believed only from an app on the list Google publishes of apps trusted to report it, checked against the signing certificate of the app as installed, and only over https; such a page is offered only the logins for its origin. A page such a browser shows over http is filled, saved into, and offered nothing, not even a card or a password to make, as on the desktop and on iOS (since 2026-11-04; before, it was taken for a page of an app that is not a trusted browser, and a login the owner chose for it was then offered on every http page of that host, whose content anyone on the network path can write). Android reports a page's host but not its port, so this is weaker than the desktop's exact-origin rule: a page on another port of a host is offered the logins saved for the host's usual port, and a login saved for another port is never offered. A browser on the list that misreports the page it shows, or is compromised, can be given a site's login once the owner chooses it; the list is Google's as fetched and committed, and changes only with a commit. Any other app, a browser not on the list included, gets no matching at all: the owner chooses a login for it, warned that an app cannot be checked against a login's address, and the choice is offered again only to that app, known by its package and original signing certificate, and by the domain it says it shows when it says one, so that a login chosen for one page of an untrusted browser is not offered on its other pages. Since 2026-10-15, on Android 12 and later, the fill screen also suggests, before that choice, the logins saved for a site that names the app as its own: a domain of the app's links that Android verified, by fetching the site's `/.well-known/assetlinks.json` when the app was installed or updated. Nothing is fetched at a fill, and neither the site nor the app learns of it. A login is suggested when its https address, on the usual port, is on such a domain (taken without `*.` or `www.`) or on a host under it; a login for another port, or over http, is not. A suggestion fills nothing until the owner chooses it, and is then remembered for the app like any other choice. Links that the owner only set an app to open, in Android's settings, count for nothing. This trusts whoever controls a verified domain, and Android's verification: an app verified for a whole domain is suggested the logins of every host under it, including sites that others run there, as on a domain of hosted pages. An app that copies another's name and look is a different app here, but the owner can still be fooled into choosing a login for it; the fill screen names the app and its package to help. What is filled passes through the system's autofill to the other app, which then holds it like a typed password, and a keyboard or accessibility service with the permission can read it there.

Since 2026-10-15 the owner can also turn on the Android app's accessibility service, which fills the other field of a login on a page that told autofill of one field only, as a web view does when the ID and the password are each in a form of their own: autofill then fills only the field that asked. Android warns, rightly, that an accessibility service can read the screen and act in it. This one asks Android for no events and reads a window only in the 4 seconds after the owner chooses a login for such a page, and only while the window in front says it is the app that asked; it sets the text of one field there, the page's one password field or, for the username, the field before it, and keeps nothing of what it read. The window's package is what the window's own views report: an app that reported another's would have to be in front in those seconds to be given the value. It never acts for a browser's page, trusted or not (an app that opens a link to any site, as Android tells), whose next page can be another site's before the other field is filled. In any other app it does not check the page: the app is who asks, and whatever page the app shows in those seconds is given the other value, as the app could be by choosing the login again. What it fills reaches the page as typing would. While the service is on, Android keeps the app's process running; the vault locks as before. A fault in the service, or in Android's accessibility, could put a value where it does not belong, which is one reason it stays off unless the owner turns it on. Android marks the setting restricted for an app installed from a file until the owner allows it in the app's info.

Since Phase 17, stop 2, a card form on Android is filled too: the number, the cardholder's name, the expiry, and the security code. A card belongs to no site, so unlike a login it is offered to any app or page that asks, a trusted browser's or not; what stands between a card and a form that should not have it is the owner, who sees on the fill screen who asks and what the form asks for, and chooses the card each time, and nothing is remembered for an app. A page or an app that collects what is filled sees the card, as it would one typed there. To keep a form from taking more than the owner sees, only fields drawn with a size are filled: a field of no size, or one inside a view that is not shown, takes nothing, so a page cannot hide a second field to have the security code beside the number (a test fills such a page and app, and the hidden field got the code before the rule). A field can still be shown somewhere the owner does not look, or under another; that is the limit of what autofill can tell. A card two devices changed at once is not filled until a computer settles which version is meant.

The iOS app (Phase 6b, stop 5) keeps the device's files in a container it shares with its AutoFill extension, excluded from backups. When it leaves the screen it locks the vault, stops taking part, ends a join under way (one already waiting for the other devices is cut off when iOS suspends the app), and closes the vault's files, so that iOS does not suspend it holding them. iOS lets no app keep its screen out of screenshots or recordings; the app hides the vault only in the app switcher's picture. Face ID or Touch ID, once turned on at an unlock, unlocks with the device's password kept in this phone's keychain, readable only after a biometric check and lost when the enrolled faces or fingers change or the phone's password is changed, and the app asks for that check itself as well (the simulator's keychain does not require it); whoever can pass the check on the phone can unlock the vault. Since Phase 19 the check is asked for by itself, as on Android, when the app opens or comes back locked and when the AutoFill extension's screen opens locked, and not after the owner's own Lock. A copied password or code stays off the owner's other Apple devices and is removed from the pasteboard after 30 seconds, but an app that reads the pasteboard meanwhile can have it.

The iOS AutoFill extension fills nothing until the owner unlocks the vault in it and chooses a login, and it registers no logins with the system, so neither iOS nor the asking app learns anything of the vault before. iOS itself names who asks, and nothing the asking app says changes that: a page by its address, and an app by the web domains Apple verified the app with or, in some requests from iOS 26.2, by its App ID. An address is offered only the logins for its exact origin, port included, which makes this stricter than Android, where the port is not known. An app that iOS names by nothing, as it named the simulator's stand-in app, is offered no login on its own: the owner chooses one, warned, and the choice is not remembered, because the extension cannot tell that app from any other. The extension opens the vault from the shared container, never goes online, and locks and lets go of it when the request ends. What is filled passes through iOS to the other app, which then holds it like a typed password.

Since Phase 7 a phone also writes: it creates, edits, and deletes logins and secure notes, signed with its own device key like any device's changes, so whoever has an unlocked phone can change or delete them on every device, not only read them. A deletion is a revision like an edit: earlier versions stay in each device's vault history and in backups, although no screen restores one yet. Identities, cards, and conflicts between devices are left to a computer. The desktop app deletes too, with the same confirmation.

Saving what another app's form or a page sent (Phase 7, stop 4) writes nothing until the owner unlocks on the save screen and chooses there, and it reads the vault by the fill rules. A save can change only the password of a login that the same form could be filled with, under the username the form sent (since 2026-11-04 the shared code refuses any other, whatever the app asks): for a trusted browser's page on Android, or an address iOS names, a login for its origin; for an app, a login the owner chose for that app. Anything else becomes a new login, saved for the page's origin only on those same terms, and otherwise for the app alone, by package and certificate on Android or by App ID on iOS. So an app cannot write into a website's login by claiming its domain, and a page cannot change another site's login. The owner can still be fooled into updating a login with a password a hostile form made up, or into saving a login for a look-alike app; the earlier password stays in the item's history. On Android what the form sent is held in the app's memory from the system's save request until the save screen closes, and only the latest one; the intent that opens the screen names it and carries nothing of it. Since Phase 11 it is held for 10 minutes at most. Android 15 and later start the save screen only while the form's app is on the screen or has just left it, so when the screen did not open, the app's own screen offers the save, with Save and Discard, for those 10 minutes. Android can start the held-back screen later, when the form's app is opened again; for a save already saved or discarded it then closes at once. The app keeps the IDs of such saves for that, and nothing else of them. To learn which app asks, the Android app now declares that it sees the apps with a launcher entry, which Android otherwise hides from it; an app without one is not identified, and is filled and saved nothing.

Since Phase 19 a sign-up's or a change of password's form on Android is also offered "make a strong password": its new password fields are those that say they take one (a page's `new-password`, an app's `newPassword`), or two or more that hide what is typed, less one that says or is named the current password, and only fields drawn with a size, as for cards. The offer tells nothing of the vault, so it is shown while locked too. Choosing it opens the app's screen, which unlocks as the fill screen does, names who asks, and shows a password made with the generator's choice; the owner then chooses where it goes on the save rules above, an existing login of that form under the username given or a new login for the page's origin or the app, and it is written then, before the form is sent, and filled into the new password fields, with the username if one is given. It is written then because Android offers no save for values a fill put in a form unchanged, and a password kept back until the form is sent is the one most easily lost, as when Android does not start the save screen. iOS differs: it sends the password it filled again when the form is sent, so the iOS extension still declines the save iOS asks for when it fills its own password. A form that asks for no reason, or a hostile app that marks a field `newPassword`, gets a fresh random password it would be given anyway, saved only for that app; the owner sees which app asks before choosing. What the owner can be fooled into is an update: a change of password made up by a form, or one the site then refuses, replaces a login's password, and the earlier one stays in its history, from which it can be restored. A sign-up that then fails leaves a login for an account that does not exist, which the owner deletes; the screen says so as it closes. The username given there is the one the form had when it asked, if Android showed it (on the emulator it showed none, neither one typed before the offer was chosen nor one a page filled in itself), else what the owner types or chooses among the usernames of the logins saved for that page's origin or chosen for that app, which the screen lists; a field that takes fewer characters than chosen (`maxlength`, or an app's filter) gets a password of that many, at least one of each kind chosen, so that the vault holds what the field took.

One-time codes (Phase 7, stop 5) are filled on Android by the same rules as passwords: a field that asks for a code from an authenticator app is offered nothing until the owner unlocks and chooses, a page gets the code only of a login saved for its origin, and an app only of a login chosen for it. A code is current for a short while and needs the password with it, but a phone that fills both into a look-alike app the owner was fooled into choosing a login for gives that app both factors. On iOS no code is filled: iOS offers a provider's codes only for the sites it has registered with the system, which would tell iOS which sites have codes in the vault, and the extension registers nothing.

Since 2026-11-04 these rules are decided in one place, the phones' shared code (`crates/mobile/src/fill.rs`), and not by each app's screens. The app works out who asks from what its system says (a page by its origin, an app by its package and certificate or its App ID, or no one named) and hands that over; the shared code chooses what that requester is offered, fills only a login it would offer or one the owner chose on the app's own screen at that moment, and saves only into a login the same form could be filled with. Before, the shared code filled any login into any app it was given, and the rule that an app gets only a login chosen for it lived in the apps' fill paths, where one that left out the check would have filled an app any login. This guards against such a mistake in an app, not against the app: its process can still read any item's secrets, as its own screens must to copy them, and iOS's text insertion hands any field of the item the owner picks to any field. The logins chosen for each app are now kept by the shared code, in a file of the device's folder, on that phone only and never synced, in the clear as the apps' preferences held them before. They name no secret, but they say which apps, and which domains apps that are not trusted browsers claimed to show, the owner has logins for, which the rest of the vault keeps inside its record ciphertext (see the protected assets above); whoever reads the phone's app files learns them. Sealing them under the vault's key is left to do.

An Android phone takes an update of the app only if it is signed with the same key as the installed app, so whoever holds the owner's release keystore can make an update every such phone installs; the keystore is kept like the Developer ID. On iOS the app reaches phones only signed through the owner's Apple developer team, and whoever controls that team's account can do the same. Neither exists yet.

## Passkeys

Since Phase 18 a login can hold passkeys. A passkey's private key is kept in the vault with its login, encrypted, synced, and backed up as a password is. Whoever can unlock a device of the vault, or holds the recovery key and a backup, therefore holds the key, and can sign in as the owner wherever the site takes the passkey alone. A passkey here protects against a phishing page, which cannot use it (see below), and against a site's own stored credentials leaking; it does not protect against the vault being compromised, and, unlike a passkey kept in a phone's secure hardware, it can be copied off an unlocked device like any other secret of the vault. Removing a passkey removes it from the login's newest version only: its key stays in the earlier versions and in every backup made since, as a changed password does, so a passkey that must be retired is removed at the site too.

A page may use only the passkeys of its own host or of a domain it is under, never those of a public suffix by the public suffix list, its private section included: a site under a shared domain such as `github.io` cannot claim its neighbours' passkeys, nor a page another site's. The rule is the core's (see Which sites a passkey is for in [formats.md](formats.md)), and the requests it reads are bounded and fuzzed. The origin it is given has to be the page's own, which is the browser's and the app's to tell. Since Phase 18, stop 5, the Android app answers sites' requests as a provider for Android's Credential Manager (below), and since stop 6 the desktop app answers a page's through the browser extension, once the owner turns that on (see Browser disclosure).

On Android, a page's origin is believed only from a browser on the list Google publishes of the apps a password manager may trust to report one, checked by the library against the browser's certificate as installed, and only then is the client data the browser made signed as it is. Any other app is itself: the client data is made for its own origin, `android:apk-key-hash:` and its certificate's hash, and a hash it sends is ignored, so an app cannot have a passkey sign for a site's pages, whose server checks the origin. An app may still ask for a site's passkeys as that site's own app, which is how a site's app signs in, and the site's server decides whether it takes passkeys from that app; nothing on the phone can tell a site's own app from another that names the site. So the first time an app asks for a site's passkeys the owner is told it is an app, not a browser, and whether Android verified that the site names it as its own, and goes on only by choosing to; the choice is kept on that phone for the app's package and certificate. A browser that is not on the list, or one whose certificate is not the listed one, gets nothing from this app, which the system then leaves to other providers. While the vault is locked the system's list says only "Unlock", so an app learns nothing of the vault before the owner unlocks; once unlocked, the list names the site's passkeys by account, which only the system shows. The phone's own check of the owner, a fingerprint, the face, or the screen lock, is what verification means there, besides the vault's password typed on that screen; whoever knows the phone's screen lock and holds the phone while the vault is unlocked, within the time the owner chose, passes it.

A passkey says the owner was verified only when the owner was verified in that same request; an unlocked vault alone says only that the owner was present. A passkey made here has a counter of 0, as devices that share it cannot agree on one, so a site cannot tell a copy from its counter; one imported with a counter answers with the time, so that a site that kept its counter does not take it for a copy.

Settling a conflict, or restoring an earlier version, keeps the passkeys of every version it follows, so that keeping a version whole, or bringing back one from before a passkey was made, loses no passkey: a passkey that one device removed while another edited the login comes back with the resolution, for the owner to remove again. A passkey of a later build, or a field of one that this build does not know, is kept as it was read and never used.

## Recovery and imports

Generate recovery material from operating-system randomness and display it deliberately. An encrypted backup must carry enough versioned metadata and wrapped keys to restore without a provider. Restoration authenticates the whole archive before replacing anything and creates a separate destination by default. A recovery secret is as sensitive as the vault it can unlock.

In the desktop app (since Phase 6a stop 5) the recovery key opens a backup file, and on a device with recovery turned on it sets a new password in place of a forgotten one. Whoever holds the recovery key and either a backup or a device's vault file therefore has the vault's contents as they were in that file; that is what the key is for, and why it belongs offline and apart from the backups. A backup holds every item's history, including earlier versions of items since deleted, so an old backup can reveal a password that was changed or an item that was removed after it was made. Restoring makes a new vault with new keys: a device lost before the restore cannot sync with the restored vault, but keeps what it already had. The app writes a backup only where the owner chooses in the system's dialog and never replaces a file; where that file goes afterwards, and who can copy it, is outside the app.

Since Phase 8 an unlocked desktop lists an item's earlier versions and the items deleted, and brings either back as a new version on every device. The history shows titles, usernames, and websites, and which fields changed, not passwords; but whoever has an unlocked device can restore an earlier password and then copy it, as the vault always kept it. A restore follows only the versions it was shown, so a change that arrived meanwhile is not overwritten unseen.

Keep encrypted backup and plaintext export separate actions. Imports are bounded, parse without evaluating formulas or markup, report unsupported rows, and require an explicit preview/commit boundary. Do not log import content. Plaintext source files remain on the user's filesystem unless the user removes them; the application must not promise secure deletion on modern storage. In the desktop app (since Phase 8) the owner picks the export in the system's dialog; the native side reads it, keeps the parsed items until the owner confirms or the vault locks, and sends the window only counts and the skipped entries' reasons. The window tells the owner to delete the export afterwards; any program of the account could read it while it is there.

## Dependencies, output, and memory

The program is mostly other people's code: 291 Rust crates in the core's workspace and 603 in the desktop app's (591 before the file dialogs of Phase 6a stop 5), counting the ones only Linux and Windows builds use, and 135 and 53 npm packages for the two interfaces, most of them build tools. Each comes from the official registry, pinned with a checksum in a lockfile, and the check script builds with `--locked`, so nothing changes without a change to a lockfile. Each is under a license a GPL-3.0 program may include. The RustSec and npm advisory databases knew of no vulnerability in any of them on 2026-10-03; the warnings the project accepts, all for crates used only on Linux or only to read Tauri's configuration, are listed with their reasons in `.cargo/audit.toml`. None of this is a review of what the code does: a crate that is malicious as published, or becomes so in a later version someone updates to, is trusted like the project's own code. Signed release provenance is release work (Phase 6a stop 6).

Nothing in the program writes a log, and no logger is installed for the libraries that could write one. A value that holds a secret prints a redacted form or none, and no error repeats a password, a key, an item's content, a recovery key, or an invitation's token; tests hold this for the core and for invitations. Keys, decrypted content, and the items read from an import file are wiped when they are dropped, and the desktop app wipes the passwords, recovery keys, and invitation codes its commands receive. What is not wiped: the copies the bridge between the window and the Rust process makes on the way, and the window's JavaScript strings, which nothing can wipe; the CSV parser's own buffers and the import file's bytes, which belong to whoever read the file; memory the system swapped to disk; and copies the compiler makes.

## Release acceptance

Before describing this as suitable for real credentials, require evidence for wrong-password and corruption rejection; authenticated metadata substitution tests; plaintext disk/WAL checks; revision conflict and tamper tests; restore round trips; RFC TOTP vectors; duplicate and out-of-order sync; locked receive; invitation replay; TLS pin mismatch; multi-process partition/restart tests; interrupted removal and rotation; browser navigation/replay/iframe tests; and native session-lock behavior. Dependency review, signed release provenance, platform packaging, and an independent security review remain release work even after unit tests pass.
